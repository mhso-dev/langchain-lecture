1|커널과 작업 폴더|같은 이름의 파일을 두 폴더에 두면 상대 경로는 커널이 시작된 위치에서 해석된다.|문의 CSV 세 줄을 직접 만들고 pathlib로 열어 지점별 건수를 저장한다. 새 커널에서 입력부터 재실행하고 없는 파일의 경로도 출력한다.
2|자료형·집계·중복|문자열 '0'은 참으로 평가된다. 접수 여부와 실제 대기 시간이 0인 경우를 구분해야 한다.|대기 시간이 0인 문의와 시간이 빈 문의를 추가해 정상 건수와 검토 건수를 각각 예측하고 원장으로 검산한다.
3|입력 계약과 예외 범위|변환을 시도하는 함수와 한 행의 실패를 기록하는 반복문을 나누면 다음 정상 행을 살릴 수 있다.|숫자 대신 미정이 적힌 행을 중간에 삽입한다. 원본 행 번호와 오류 사유를 남기고 마지막 정상 행까지 처리한다.
4|상태 전이와 객체 수명|두 문의가 하나의 이력 목록을 공유하면 A의 재접수가 B에도 보인다.|문의 두 건을 생성하고 한 건만 다시 연다. 상태와 이력 길이를 검사하는 테스트를 작성해 공유된 가변값을 찾는다.
5|파일 왕복과 결측값|CSV에 기록한 0과 빈칸은 다시 읽을 때 모두 문자열이다. 원본 의미를 복원하는 규칙이 필요하다.|재개한 커널에서 CSV 세 개를 조합해 누락된 사건을 검출한다. 같은 파일에 다시 저장해도 행 수가 늘지 않게 한다.
6|HTTP 응답과 재시도|200 응답도 본문에 필요한 필드가 없으면 처리 실패다. 상태 코드와 데이터 계약을 따로 확인한다.|정상 응답, 빈 목록, 잘못된 필드 세 입력을 재생한다. 재시도할 실패와 원본을 고쳐야 하는 실패를 구분해 기록한다.
7|작은 변경과 회귀 검사|두 사람이 같은 정렬 기준을 다르게 바꾸면 병합에 성공해도 대기열 순서가 틀릴 수 있다.|동료의 변경을 받아 대기 시간이 같은 두 문의의 순서를 재현한다. 기대 순서를 테스트에 고정한 뒤 수정한다.
8|모델 응답과 원문 대조|두 답변이 같은 날짜를 말해도 한쪽은 다른 지점의 공지를 인용했을 수 있다.|같은 질문을 실제 모델에 보내고 공지의 대상·날짜·근거 문장을 표시한다. 다른 지점 질문에서 보류가 필요한 이유를 쓴다.
9|프롬프트 변경 실험|규칙과 예시를 동시에 바꾸면 어떤 변경이 결과를 개선했는지 알기 어렵다.|동일한 세 질문에서 예시 한 개만 바꿔 다시 호출하고 새로 생긴 오답을 보존한다.
10|검증과 재작업|날짜 형식이 맞아도 종료일이 시작일보다 빠르면 게시할 수 없다.|실제 모델이 쓴 안내문을 구조 검사와 의미 검사로 나눈다. 실패 항목만 돌려주고 수정 전후를 대조한다.
11|SDK 응답과 사용량|응답 본문과 사용량은 서로 다른 필드다. 빈 본문을 성공으로 세면 사용량만 늘어난다.|같은 질문 길이를 바꾸고 실제 응답 본문·모델명·사용량을 저장한다. 사용량을 제공하지 않는 경우도 처리한다.
12|구조화 출력과 스트리밍|스트리밍 중간의 JSON은 아직 닫히지 않았을 수 있다. 화면에 보이는 조각과 검증할 완성 문서를 분리한다.|공지의 날짜 하나를 삭제한 입력으로 다시 호출한다. 완성된 결과만 검증하고 원문에 없는 필드를 찾아낸다.
13|순차 처리와 입력 전달|요약에서 고객의 요청 날짜가 사라지면 다음 분류 모델은 복구할 근거가 없다.|두 단계 호출의 중간 결과를 보관한다. 날짜 보존 규칙을 한 곳에 추가하고 누락 사례 한 건을 재검증한다.
14|분기와 보류|어느 분류에도 맞지 않는 요청을 첫 번째 처리기로 보내면 엉뚱한 안내가 나간다.|복합 문의 한 건을 넣어 모델의 분류와 실제 실행한 처리기를 기록한 뒤 보류 기준을 정한다.
15|도구 명세와 인자 검증|주말을 숫자로 받는 함수에 모델이 문자열을 보내면 호출 이름만 맞아도 실패한다.|두 도구의 인자 설명을 고친 뒤 실제 모델이 낸 인자를 비교한다. 잘못된 값은 함수 실행 전에 거절한다.
16|실행 결과와 호출 ID|서로 다른 조회 두 건은 먼저 끝난 순서대로 나열해도 원래 요청과 연결되어야 한다.|실제 응답에 든 도구 요청을 실행하고 대응 ID로 되돌려준다. 하나의 결과가 빠지면 다음 호출 전에 알려 준다.
17|종료 조건과 추적|도구 결과가 있어도 모델이 추가 조회를 요청할 수 있다. 종료는 마지막 응답의 호출 목록으로 판단한다.|최대 호출 횟수를 정하고 성공과 한도 도달을 분리해 기록한다. 한 실행의 중간 메시지로 종료 이유를 설명한다.
18|작은 팀 통합|답변 담당자가 필요한 필드를 조회 담당자가 보내지 않으면 각자의 셀은 성공해도 서비스는 실패한다.|둘이서 문의 처리기를 연결하고 서로 만든 반례를 교환한다. 첫 실패의 입력과 수정 후 실행을 제출한다.
19|LCEL 입력·모델·파서|프롬프트의 메시지는 맞지만 답변이 틀릴 수 있다. 파서가 반환하는 문자열만 보면 어디서 틀렸는지 놓친다.|대출 기간을 14일에서 7일로 바꾸고 프롬프트 메시지와 실제 모델 응답을 나란히 확인한다.
20|원문과 검색 단위|페이지 번호가 사라지면 질문에 맞는 문장을 찾아도 근거 위치를 설명할 수 없다.|PDF에서 표지와 운영 기록을 골라 제외하고 남은 쪽에 판본과 원문 위치를 붙인다.
21|청크 경계와 문맥|단서 조항이 다음 청크에만 있으면 일반 규정은 맞고 예외는 틀리는 답이 나온다.|같은 문서를 두 방법으로 나누고 예외 질문의 근거와 단서가 함께 검색되는지 확인한다.
22|벡터 거리와 메타데이터|가까운 문서가 현재 지점의 유효한 규정이라는 보장은 없다.|같은 질의 벡터를 두 색인에서 조회하고 후보 ID를 비교한다. 구판 필터를 적용한 뒤 빠진 정답도 살핀다.
23|검색 후보와 문맥 예산|후보를 늘리면 근거를 찾기 쉽지만 전달 순서에 따라 예외 문장이 잘릴 수 있다.|상위 후보 수와 전달 길이를 따로 바꿔 검색 목록에만 있고 최종 문맥에 없는 근거를 찾는다.
24|인용과 생성 검증|문서 ID가 실제로 존재해도 주장의 근거가 다른 문서에 있을 수 있다.|실제 모델의 답변을 주장 단위로 나누고 각 인용 원문을 대조한다. 근거 없는 질문의 호출 여부도 기록한다.
25|팀별 RAG 점검|다른 사람이 만든 평가 질문은 작성자가 예상하지 못한 판본 충돌을 드러낸다.|두 명이 문서와 질문을 교환하고 상대의 질문으로 첫 실패를 재현한다. 검색과 생성 중 수정할 단계를 고른다.
26|상태·노드·간선·종료|근거가 없는 검색 결과도 고정 간선을 따라 답변 노드로 간다. 같은 그래프에 보류 경로를 연결해 차이를 본다.|정상 질문과 근거 없는 질문을 실행하고 노드가 반환한 필드와 종료 경로를 각각 제출한다.
27|분기·재검색·한도|검색어를 그대로 되돌려 보내면 두 번째 검색이 첫 검색과 같은 일을 한다.|검색어가 달라졌을 때만 다시 찾고 같은 검색어와 횟수 초과 두 조건을 따로 시험한다.
28|상태 병합과 메시지 ID|같은 ID의 수정 메시지를 새 메시지처럼 추가하면 화면에 답변이 두 번 표시된다.|메시지 추가와 수정 두 입력을 처리하고 실행 후 메시지 수와 최종 본문을 검사한다.
29|체크포인트와 대화 격리|두 사용자가 같은 thread_id를 쓰면 이전 질문이 다른 사람의 후속 질문에 섞인다.|두 대화를 번갈아 이어 가며 마지막 질문과 복원 위치를 대조한다. 같은 사용자 안의 새 대화도 시험한다.
30|검색 노드와 입력 계약|검색 함수가 목록을 반환해도 그래프는 그 목록을 어느 상태 필드에 기록할지 알아야 한다.|리트리버를 노드로 감싸고 빈 결과·복수 결과에서 원래 질문이 최종 상태에 보존되는지 확인한다.
31|출처 검증과 보류|인용 번호가 남아도 판본이 만료됐다면 답변 근거로 쓸 수 없다.|기준일을 바꾼 같은 질문으로 통과와 보류를 재현한다. 보류 이유가 검색 실패인지 판본 탈락인지 기록한다.
32|노드 조합과 회귀 질문|검색을 고친 뒤 원래 성공하던 질문까지 다시 실행해야 변경의 영향을 알 수 있다.|두 명이 검색과 답변을 나눠 구현하고 기존 성공·신규 실패·무근거 질문 세 건으로 합친 그래프를 시험한다.
33|검색 도구의 명세와 실제 인자|k가 크면 검색은 성공해도 불필요한 문서가 늘어난다. 스키마에서 허용 범위를 정한다.|실제 모델이 만든 검색 인자를 기록하고 0과 상한 초과를 직접 시험한다. 정상 결과에 쪽 번호를 보존한다.
34|필수 검색과 선택 검색|운영 규정 질문에는 검색이 필요하지만 인사까지 검색하면 호출만 늘어난다.|두 질문을 실제 모델과 검색 도구에 보내고 검색 실행 여부와 답변 출처를 나누어 비교한다.
35|평가 문항과 판정 기준|표현이 달라도 같은 조항이 답이 될 수 있다. 문자열 일치만 검사하면 올바른 답이 탈락한다.|개발 질문과 보류 질문을 만들고 각 질문에 정답 근거 ID와 허용할 답변 범위를 적는다.
36|순위와 인용 품질|정답이 1위에서 3위로 내려가도 Recall@3는 같고 MRR은 낮아진다.|한 질문의 후보 순서만 바꿔 두 지표를 손으로 검산한 뒤 답변의 인용까지 평가한다.
37|검색 개선과 비교 조건|질문과 청킹을 동시에 바꾸면 어느 쪽이 결과를 바꿨는지 모른다.|고정 질문으로 한 설정씩 바꾸고 좋아진 질문과 나빠진 질문을 하나씩 골라 근거를 읽는다.
38|재정렬과 후보 누락|재정렬기는 후보에 없는 문서를 1위로 올릴 수 없다.|정답이 후보 밖에 있는 질문과 후보 안에 있는 질문에서 재검색과 재정렬 효과를 분리한다.
39|평균과 사용자 집단|전체 평균이 올라가도 예외 조항을 묻는 질문만 계속 떨어질 수 있다.|일반·예외 질문을 나누고 집단별 변화를 계산한다. 적용할 후보와 보류할 후보를 근거로 선택한다.
40|화면 재실행과 대화 상태|Streamlit은 입력 때 스크립트를 다시 실행한다. 목록을 매번 새로 만들면 이전 답이 사라진다.|두 질문을 연속 입력한 뒤 새 요청만 모델에 보내고 이전 답변과 근거가 화면에 남는지 확인한다.

54|트랜잭션과 중복 요청|수정은 성공했는데 응답이 끊기면 같은 변경을 다시 보낼 수 있다.|요청 ID를 저장해 중복 차감을 막고 중간 실패에서 두 테이블이 함께 복구되는지 검사한다.
55|도구 요청·결과·최종 답변|에이전트가 복수 도구를 요청할 때 호출 ID가 함수 결과와 최종 답변을 연결한다.|실제 모델에 복합 질문과 인사를 보내고 요청 목록과 실행된 도구를 비교한다.
56|실행 한도와 관찰|도구 한도 2는 최대 두 번이라는 뜻이다. 실제 실행한 횟수는 함수 안에서 센다.|두 조회가 필요한 질문으로 한도를 1과 2로 바꾼다. 요청했지만 막힌 경우와 모델이 요청하지 않은 경우를 나눈다.
57|업무 지침과 도구 분리|환불 가능 조건은 지침, 주문 금액은 조회 결과다. 지침에 특정 주문 값을 적으면 다음 문의가 틀린다.|두 주문에 같은 지침을 적용하고 달라져야 할 값과 유지될 조건을 구분한다.
58|목록 탐색과 상세 자료 로딩|모든 지침을 처음부터 주입하면 관련 없는 예외도 서로 경쟁한다.|요약만 보고 지침을 고른 뒤 본문을 추가한다. 잘못 고른 사례에서 누락된 단서를 찾아 요약을 수정한다.
59|대화 이력과 요약|이전 턴의 거절 조건이 요약에서 빠지면 모델이 이미 거절한 작업을 다시 제안할 수 있다.|연속 세 턴에서 보존할 조건을 지정하고 새 대화에는 이전 요청이 섞이지 않는지 확인한다.
60|기억의 소유자와 갱신|대화 상태와 장기 선호는 수명이 다르다. 사용자가 바꾼 선호는 다른 대화에도 적용돼야 한다.|동일 사용자의 새 대화와 다른 사용자 대화를 만들고 선호 변경이 정확한 범위에서 보이는지 비교한다.
61|MCP 도구 발견과 직접 호출|서버가 노출한 이름과 인자 스키마를 먼저 확인하면 연결 오류와 인자 오류를 분리할 수 있다.|서버의 tools 목록을 읽고 올바른 인자와 잘못된 인자로 호출한다. 최초로 실패한 단계를 기록한다.
62|MCP·모델·HTTP 전송|서버 직접 호출이 성공해도 에이전트가 다른 요일을 보내면 답은 틀린다.|실제 모델로 평일·주말을 각각 물어 요청 인자, 서버 시간, 최종 안내를 대조한다. 같은 질문을 HTTP 세션에서도 시험한다.
63|소유권·검색·선택 도구|사용자 권한을 검사한 뒤 근거를 찾고 필요한 경우에만 모델이 보조 도구를 쓴다.|권한 없는 대화, 근거 없는 질문, 근거 있는 문의를 비교해 어느 경로에서 모델 호출이 발생하는지 설명한다.
64|승인과 재개·중복 방지|승인 뒤 네트워크가 끊겨 재개를 반복해도 실제 신청은 한 건이어야 한다.|거절·수정·승인을 서로 다른 요청 ID로 실행하고 승인 요청을 재전송해 저장 건수를 검증한다.
65|분류와 비용 있는 도구 선택|규칙으로 구별할 수 있는 요청도 모델로 보내면 비용이 늘어난다. 애매한 표현은 별도 경로가 필요하다.|규칙 일치·애매함·업무 외 요청을 넣고 실제 모델 경로의 결과, 호출 수와 실패를 비교한다.
66|역할 분리와 근거 인계|조회 모델의 마지막 인사는 다음 역할이 사용할 근거가 아니다. 도구가 돌려준 문서 ID를 함께 넘긴다.|조회와 작성을 두 실제 호출로 연결한다. 근거 없음과 정상 인계에서 작성 호출 수 및 최종 인용을 비교한다.
67|팀별 에이전트 인수 시험|최종 답변이 맞아도 승인 전에 작업을 확정했다면 실행 경로는 실패다.|둘이 서로의 서비스에 승인·거절·재시도 사례를 넣고 답변과 도구 실행 이력을 각자 판정한다.
68|API 계약과 입력 오류|서버가 검증하지 않고 받은 빈 질문은 모델 비용을 쓰고도 쓸모 있는 답을 주지 못한다.|정상·빈 질문·필수 필드 누락을 보내고 상태 코드와 모델 호출 여부를 함께 검사한다.
69|스트림 이벤트와 재접속|마지막 문자가 도착했다는 사실만으로 전체 응답이 끝났는지 알 수 없다.|데이터·완료·실패 이벤트를 분리하고 중간에 끊긴 요청을 재접속했을 때 화면이 중복되지 않게 한다.
70|데이터 저장과 요청 격리|대화 ID만으로 조회하면 다른 사용자의 기록을 돌려줄 수 있다.|두 사용자에게 같은 제목의 대화를 만들고 문서 추가·조회에서 소유자가 보존되는지 시험한다.
71|이미지와 실행 환경|이미지를 다시 만들었다고 기존 컨테이너의 환경 변수가 바뀌지는 않는다.|설정값 하나를 바꾸고 새 컨테이너와 이전 컨테이너의 응답을 비교해 재생성이 필요한 이유를 적는다.
72|Compose와 준비 상태|DB 프로세스가 시작된 시점과 쿼리를 받을 시점은 다르다.|빈 볼륨에서 서비스를 시작하고 첫 연결 실패를 재현한다. 준비 확인 후 재연결되는 로그를 남긴다.
73|pgvector·필터·원문 회수|벡터 검색의 상위 후보가 다른 지점 문서이면 최종 답변의 근거도 잘못된다.|지점 필터 적용 전후 후보 ID와 실제 원문을 대조하고 정답이 사라진 경우를 설명한다.
74|배포와 상태 확인|홈 화면 응답이 정상이어도 실제 조회 API가 데이터베이스에 연결되지 않을 수 있다.|정적 화면, API, DB 조회 세 경로를 각각 점검하고 실패가 처음 발생한 경계를 표시한다.
75|Codex 4H · 배포본 복구|배포 성공 직후에도 기존 사용자의 할 일을 읽을 수 있어야 한다. 상태 점검은 프로세스와 데이터 읽기를 따로 검사한다.|Codex에 기존 데이터 한 건을 이용한 읽기 검사를 먼저 작성시킨다. 빈 DB에서 실패하는 것을 확인한 뒤 복구 절차를 적용하고 같은 ID로 다시 읽는다.
76|Codex 4H · 테스트부터 작성|생성된 코드가 자기 테스트만 통과하면 사용자 요구를 빠뜨릴 수 있다. 실패 조건을 먼저 사람이 정한다.|동명 할 일 두 개 중 하나만 수정하는 실패 테스트를 커밋한다. Codex의 최소 수정 diff를 검토하고 CI에서 두 ID 상태를 확인한다.
77|Codex 4H · 배포와 되돌리기|검사가 실패한 변경도 배포 단계에 도달하면 CI의 성공 여부를 검사한 의미가 없다.|Codex로 배포 조건과 이전 이미지 복구 명령을 작성한다. 테스트 실패 커밋과 성공 커밋으로 배포 실행 여부를 비교한다.
78|Codex 6H · 화면과 상태|화면의 행 번호를 ID로 쓰면 필터 후 다른 항목이 수정된다. DOM에는 서버가 준 ID를 보존해야 한다.|Codex로 목록·필터·키보드 입력을 구현하고 같은 제목의 두 항목을 만든다. 필터 뒤 수정해도 지정한 ID만 바뀌는지 직접 시험한다.
79|Codex 6H · API 연동|버튼 클릭 때 화면부터 바꾸면 서버가 409를 반환해도 사용자에게 성공처럼 보일 수 있다.|Codex로 저장 중과 실패 상태를 구현한다. 정상 저장, 중복 클릭, 충돌 응답에서 화면과 서버 목록을 다시 대조한다.
80|Codex 8H · 변경 요청과 인수|처음부터 다시 생성하면 이전 회귀 검사가 사라질 수 있다. 기존 저장소에서 작은 요구 변경을 끝까지 처리한다.|두 명이 의뢰자·개발자로 역할을 나눈다. 완료 취소 기능을 이슈로 작성하고 Codex와 구현한 뒤 상대가 새 환경에서 등록·취소·새로고침을 시험한다.
81|추적과 버전 고정|같은 이름의 실험도 프롬프트나 색인 판본이 다르면 기준선이 달라진다.|실제 서비스 호출 한 건에서 모델·검색 단계와 버전을 기록하고 실패가 처음 생긴 실행을 찾는다.
82|검색과 답변 평가 분리|정답 수치는 맞는데 잘못된 문서를 인용하면 검색 지표와 답변 평가는 서로 다르게 나온다.|일반·예외·무근거 세 질문을 평가하고 검색 실패와 생성 실패를 별도로 분류한다.
83|도구 경로의 허용 범위|두 조회는 순서를 바꿔도 되지만 승인과 저장은 순서를 바꿀 수 없다.|허용되는 순서 변경과 허용되지 않는 저장 선행을 구분하는 평가기를 만들어 실제 실행 로그에 적용한다.
84|실험 비교와 회귀 기준|후보가 답하지 못한 문항을 평균에서 빼면 개선으로 오판할 수 있다.|기준선과 후보를 질문 ID로 맞춘다. 누락 문항을 포함한 결과를 바탕으로 배포·보류 사유를 기록한다.
85|시험 배포와 팀 인계|발견한 실패를 평가 데이터에 넣지 않으면 다음 변경에서 같은 문제가 돌아온다.|팀원이 재현할 수 있는 실패 한 건을 데이터셋에 추가하고 수정 전후 실험·버전·되돌릴 조건을 넘긴다.
