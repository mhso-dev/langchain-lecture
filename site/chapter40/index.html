05

관련 개념 더 읽기

화면에서도 질문과 근거의 연결을 유지하기

오늘의 자료는 가상 도서관 안내입니다. 검색은 교육용 벡터 규칙이고 답변은 고정 함수가 만듭니다. 화면을 붙이는 과정에서 실제 모델을 새로 연결하지 않습니다. 39일에 유지하기로 한 기준선과 알려진 실패를 함께 가져옵니다.

04·24·32·39일 산출물을 실제 파일로 읽기

04일의 package-layout/README.md에서 역할별 모듈을 나누었던 이유를 설명해 보세요. 여기서는 app.py가 화면을, response_logic.py가 질문·결과 상태를, backend39_api.py가 고정된 서비스 연결을 맡습니다. 함수가 돌려주는 값을 화면 함수 안에 섞어 바꾸지 않습니다.

24일 dev-01과 32일 첫 비교 행은 검색 문서가 두 개여도 실제 인용 sources는 한 개일 수 있음을 보여 줍니다. 39일에는 문서를 분할한 인덱스를 사용하므로 library-1:0처럼 청크 ID가 나옵니다. ID를 보기 좋게 바꾸지 말고 출처 객체와 함께 유지하세요.

39일의 선택 후보는 rerank이며 현재 실행에 유지한 방법은 baseline입니다. candidate_k=2, final_k=1, size16/overlap0을 유지합니다. 공개 확인의 반납 답변은 문장이 끊깁니다. 화면에 인용 ID가 보인다는 이유로 이 답변을 완전한 안내라고 판단하지 않습니다.

화면 입력이 바뀔 때 코드는 어디서 시작할까

Streamlit은 Python 스크립트로 화면을 만드는 도구입니다. 기본 동작에서는 위젯과 상호작용하면 스크립트를 위에서 아래로 다시 실행합니다. 일반 변수는 그 실행에서 다시 만들어집니다. 같은 브라우저 세션에서 이어서 보관할 값은 session_state에 둡니다.

스크립트 재실행은 서버 프로세스를 새로 시작하는 일과 다릅니다. 현재 앱의 메모리에 있던 세션 상태는 일반 재실행 사이에 유지할 수 있지만, 탭 새로고침이나 서버 재시작 뒤에도 기록이 영구 보관된다고 약속하지 않습니다. 일시적인 연결 끊김은 별도 세션 정책의 영향을 받을 수 있습니다.

질문 함수 호출을 스크립트 맨 아래에 조건 없이 두면 결과를 다시 그리기 위한 실행에서도 검색을 반복할 수 있습니다. 이 장의 앱은 submitted가 참일 때만 submit_question을 부릅니다. 결과를 보여 주는 부분은 이미 저장한 view를 읽습니다. 화면을 그리는 일과 새 질문을 처리하는 일을 구분하는 것입니다.

session_state에 현재 결과를 보관하기

completed와 answered는 다른 층의 값입니다. completed 안에도 no_evidence나 invalid_citation이 들어갈 수 있습니다. 함수가 정상적으로 “자료 없음”을 돌려준 것과 함수 실행이 실패한 것을 따로 기록합니다.

if "view" not in st.session_state 조건은 값이 없을 때만 초기 상태를 넣습니다. 이 조건 없이 매번 초기값을 대입하면 질문을 처리해 보관한 결과를 다음 실행에서 지워 버릴 수 있습니다. 반대로 초기화 버튼은 사용자가 의도적으로 결과를 지우는 사건이므로 새 initial_view를 대입합니다.

A1의 답변과 실제 인용 객체를 표시하기

service.answer는 A1 객체를 돌려줍니다. status는 answered/no_evidence/invalid_citation 중 하나이고, answer는 표시할 문자열이며, sources는 실제 인용한 R1 문서 객체 목록입니다. generation_calls는 이 예제에서 로컬 고정 생성 함수의 호출 수입니다. 유료 모델 호출 수라고 해석하지 않습니다.

화면 어댑터도 최소 계약을 확인합니다. 답변 문자열이 비었거나 출처 page가 없거나 answered의 인용 ID 집합과 sources가 다르면 자료 오류로 처리합니다. 다만 이 검사는 문장이 원문과 같은 뜻인지 판단하지 못합니다. source/text/page를 열어 주장을 직접 대조해야 합니다.

자료 없음과 실행 오류를 다른 결과로 남기기

주차 요금 질문에 검색 결과가 없으면 A1은 no_evidence를 반환합니다. 질문을 처리하는 과정 자체는 끝났으므로 화면의 execution_status는 completed입니다. 반면 검색 TimeoutError는 자료를 정상적으로 확인하지 못한 사건입니다. 이를 “자료에 답이 없다”로 바꾸면 관측 실패를 숨기게 됩니다.

submit_question은 새 빈 view에서 시작합니다. 예외가 나면 result=None과 오류 종류를 남깁니다. 예외 본문을 그대로 화면에 붙이지 않으므로 환경 정보가 섞인 긴 오류 메시지를 사용자 답변처럼 노출하지 않습니다. 개발자가 원인을 확인할 때는 실행 환경의 별도 기록을 사용합니다.

visible_sources는 completed 결과에 있는 sources만 돌려줍니다. error나 idle이면 빈 목록입니다. 반환할 때 복사본을 만들기 때문에 화면용 목록을 가공하다 저장한 결과 객체를 바꾸는 일도 막습니다.

결과 지우기 버튼은 폼 밖에 있습니다. 버튼을 누르면 view를 새로 만들고 질문 위젯의 키도 비웁니다. 이 대입은 text_input을 만드는 줄보다 앞에 있습니다. 이미 만든 위젯의 값을 같은 실행 뒤쪽에서 바꾸면 Streamlit의 상태 규칙과 충돌할 수 있기 때문입니다.

40일의 초기화는 현재 화면 결과를 지우는 동작입니다. 아직 Graph의 여러 대화 기록을 선택하거나 삭제하는 기능은 없습니다. 다음 장에서 thread_id와 체크포인트를 연결할 때 이 범위를 다시 구분합니다.

키 없이 분리 로직을 실행하고 경계를 확인하기

실습은 examples 폴더만으로 실행할 수 있습니다. 다른 장의 prototype 경로를 import하지 않습니다. backend39 폴더에는 고정 서비스와 필요한 자료가 같은 상대 경로로 들어 있습니다. 입력 스냅샷을 임의로 고쳐 실습을 통과시키지 말고, 변경 실험은 별도 사본에서 합니다.

기본 과제는 제공 흐름을 예측·실행·설명하는 것입니다. 먼저 끝낸 학생은 copy한 예제에서 상태별 안내 문구를 더 분명하게 바꿀 수 있습니다. A1 필드나 출처를 없애거나 실제 API·배포를 필수 기능으로 추가하지 않습니다.

검사 통과는 이 경계 입력에서 Python 함수가 예상 결과를 냈다는 증거입니다. 실제 Streamlit의 재실행·버튼·작은 화면·키보드 이동이 잘 동작한다는 증거는 아닙니다. 준비된 환경에서 별도로 관찰하고 같은 기록표의 실행 종류를 정확히 고르세요.

예상·관찰·미확인을 한 기록에서 구분하기

ui/rag-demo.md의 한 행에는 예상과 관찰을 따로 적습니다. 실제 실행했다면 명령·환경·결과 파일을 남기고, 코드만 읽었다면 “예상”이라고 적습니다. 작성자가 제공한 observations.json을 읽은 경우에도 자신의 직접 실행으로 바꾸지 않습니다.

O40-1은 실행 순서 설명, O40-2는 질문/답/출처 연결, O40-3은 초기화와 오류 뒤 출처를 증거로 판단합니다. 총점 대신 목표별 근거 충족·수정 필요·미확인을 표시합니다. 화면 환경이 없어도 개념 설명은 점검할 수 있지만 화면 수행 목표는 미확인으로 남습니다.

41일에 넘길 화면 상태와 남은 검사

넘길 것은 app/response_logic/backend의 역할, ui/rag-demo.md, 고정 입력 계약과 실제 관찰입니다. 실제 화면 미실행도 함께 전달합니다. 함수와 자료를 연결한 범위만 설명하고, 화면 연결이 모델 품질이나 서비스 준비를 보증한다고 말하지 않습니다.
