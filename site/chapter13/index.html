02

요약 출력을 분류 입력으로 전달

순차 워크플로에서는 앞 단계의 반환값이 다음 호출의 입력이 됩니다. 중간값이 비면 이후 단계가 어떤 자료를 잃는지 살펴봅니다.

각 단계는 받은 자료와 지시를 이용해 새 문자열을 반환합니다. 이번 실습의 mock_call은 정해 둔 답을 주는 대역입니다. 최종 글의 품질보다 단계 사이에 실제로 건넨 값을 확인합니다.

요약 단계의 정보 손실

순차 흐름의 뒤 단계는 앞 단계가 넘긴 정보에 의존합니다. 원문에 “영수증을 찾을 수 없고 로그인 오류도 난다”는 내용이 있는데 요약이 영수증만 남기면 분류와 안내도 한쪽으로 치우칠 수 있습니다.

요약 길이를 늘리는 방법과 원문을 뒤 단계에도 전달하는 방법은 서로 다른 설계입니다. 어떤 정보를 남겨야 하는지 먼저 정하고, 입력 크기와 확인 부담을 함께 비교하세요.

첫 번째 요청의 질문은 그대로 두고, 반환된 요약을 변수에 보관하세요.

실행 결과

사용자가 결제 영수증 확인 방법을 문의했다.

문의 내용을 ‘로그인이 안 됩니다’로 바꾸고 같은 summarize 단계를 호출하면 영수증 문장이 그대로 나옵니다. mock_call이 단계 이름으로 고정 응답을 조회하기 때문입니다. 이 예제로는 다음 호출에 건넨 문장을 확인할 수 있습니다. 새 문의까지 잘 요약하는지 평가하려면 실제 응답을 따로 받아야 합니다.

순차 호출의 단계 분할

여러 작업을 한 번에 요청하면 어디에서 잘못되었는지 구분하기 어려울 수 있습니다. 요약·분류·문장 작성을 따로 실행하면 중간 결과를 볼 수 있지만 호출 수와 대기 시간도 늘어납니다. 작업을 나눈다는 사실만으로 품질이 좋아진다고 단정하지 않습니다.

이번 흐름에서는 Python 코드가 항상 요약, 분류, 작성 순서를 정합니다. 모델이 다음 함수를 선택하는 에이전트가 아닙니다. 모델은 각 단계에서 입력을 받아 텍스트를 돌려줄 뿐입니다.

빈 중간값의 실패 처리

셀 04의 입력은 요약 단계가 돌려준 공백 세 칸입니다. strip()을 적용하면 빈 문자열이 되어 checked_text가 ValueError를 냅니다. 요약 실패를 분류기의 문제로 기록하지 않도록 예외 메시지에 단계 이름을 넣습니다.

이 예제는 오류를 예외로 알립니다. 실패 시 앞 단계 로그를 외부에 반환하는 구조까지 구현하지 않았습니다. 실제 운영 로그를 만들 때는 성공 단계와 실패 단계를 함께 보관하되 민감한 입력 전체를 무조건 저장하지 않습니다.

셀 05 · 호출 로그의 단계별 input

처음에 입력한 질문과 두 번째 호출에 실제로 건넨 문자열을 구분하세요.

두 번째 호출이 받은 것은 첫 단계의 요약 ‘사용자가 결제 영수증 확인 방법을 문의했다.’입니다. 분류 결과 billing은 그다음 작성 단계에서 요약과 함께 쓰입니다. result["log"][1]["input"]에서 분류 전의 요약을 확인하세요.

실행 결과

사용자가 결제 영수증 확인 방법을 문의했다.

두 번째 호출 기록의 input은 첫 호출이 만든 요약입니다. result의 answer는 세 번째 모의 호출이 돌려준 접수 안내입니다. 계정 조회나 환불을 실행한 기록은 없습니다.

단계 실행 함수

정상 실행에서는 log[0]의 output이 log[1]의 input에 전달됩니다. 시간은 호출 전후의 차이를 소수 셋째 자리까지 반올림한 값이어서, 고정 응답처럼 빠른 함수는 0.0초로 기록될 수 있습니다.

run_workflow의 call 인자는 모델 호출을 담당하는 함수입니다. 기본 실행은 mock_call을 전달합니다. 이처럼 호출 경계를 분리하면 인터넷 없이도 연결 순서와 실패 경로를 검사할 수 있습니다.
