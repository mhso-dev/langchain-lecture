관련 개념 더 읽기

13일의 고정 순서와 선택 분기 대조

첫 1H 중 15분에 본인의 sequential-workflow/trace.json에서 요약→분류→작성 순서를 찾습니다. 개인 기록이 없으면 13일 examples/workflow.py의 제공 모의 실행을 재현하고 제공 예제 재현이라고 표시합니다. 오늘은 분류 결과에 따라 작성 1회 또는 0회가 되는 이유를 비교합니다.

판단과 실행 결정의 역할

분류 모델은 입력이 어느 분야인지 문자열을 제안합니다. 그 문자열로 어떤 작업을 수행할지는 Python 코드가 결정합니다. 모델이 billing이라고 썼다는 이유만으로 결제나 환불이 실제 실행된 것은 아닙니다.

이번 예제는 접수 안내 문장만 만듭니다. 외부 계정 조회·환불·데이터 변경은 하지 않습니다. 경로 분류는 사용자 권한이나 작업 승인도 대신하지 않습니다.

분류 함수의 예외, 명시적 거절, 정상적인 모호 입력은 서로 다른 원인입니다. 빈 분류 텍스트와 미완료·통신 오류는 classification_error, 명시적 거절은 classification_refusal, 의도적인 clarify나 공백이 아닌 허용 목록 밖 문자열은 needs_clarification으로 남깁니다. 세 경우 모두 작성 함수는 호출하지 않습니다.

이 함수는 분류 실패를 결과에 담지만 작성 단계의 예외는 호출자에게 전달합니다. 모든 오류를 잡아 정상 답변처럼 반환하지 않습니다. 서비스 화면과 연결할 때는 작성 실패도 별도 표시하도록 확장해야 합니다.

SDK 분류와 작성 연결하기

ClassificationRefusalError는 ValueError를 바탕으로 만든 작은 예외 종류입니다. 같은 분류 실패 중 명시적 거절을 알아볼 수 있도록 이름을 붙였고 route_request가 이 종류를 먼저 처리합니다. 거절 내용을 정상적인 추가 질문으로 바꾸지 않습니다.

sdk_classifier는 먼저 completed인지 확인하고 assistant 메시지의 명시적 거절과 분류 텍스트를 읽습니다. completed여도 빈 output이나 공백 텍스트라면 실패입니다. 쓸 수 있는 문자열만 strip으로 정리해 돌려주며, 허용값 밖의 문장을 억지로 잘라 경로로 만들지 않습니다.

sdk_writer는 선택된 규칙과 원본 질문을 모델에 보냅니다. 실제 연결에서는 11장에서 준비한 클라이언트·모델을 두 함수에 전달합니다. 기본 실행은 연결하지 않으며 실제 API 성공은 미검증입니다.

경계 입력과 원인별 기록

분류는 쉬운 질문보다 모호·복합·범위 밖 입력에서 설계 차이가 드러납니다. 두 분야를 동시에 묻는 질문에 하나만 골라 답하면 나머지 요청이 사라질 수 있습니다. 이번 수업에서는 복합 입력을 추가 질문으로 돌려 범위를 좁힙니다.

분류 함수가 예상하지 않은 delete_all을 반환하는 테스트는 악의적인 실제 작업을 실행하지 않습니다. 그런 문자열이 와도 허용 목록 밖이면 작성 호출이 없다는 경계를 검사합니다.
