같은 질문의 수정 전후를 어떻게 짝지을까요?

질문 한 개에 방법이 여러 개 있으므로 question_id만으로 행을 덮어쓰면 결과를 잃습니다. case_id는 dev-01:baseline처럼 질문과 방법을 함께 나타냅니다. 질문 문장과 기대 원문은 question_id로 Q1에 연결하고, 실제 실행 결과는 case_id로 구분합니다.

paired 비교는 같은 질문의 기준선과 변경 결과를 나란히 읽는 방식입니다. 먼저 실패 여부와 관측 가능성을 확인하고, 그다음 반환 문서·답변·추가 작업을 비교합니다. 실패한 질문을 빼면 좋아 보이는 평균이 생길 수 있습니다.

찾은 조각보다 넓은 문맥을 언제 읽을까요?

작은 청크는 한 주제를 좁게 담을 수 있지만 답변에 필요한 앞뒤 조건이 잘릴 수 있습니다. Parent–Child 방식은 작은 자식 청크로 검색한 뒤 연결된 더 큰 부모 문서나 큰 청크를 반환합니다. 부모가 항상 전체 파일인 것은 아닙니다.

앞 장의 source-map은 청크와 원문을 연결하는 표입니다. 이 표가 있다고 Parent–Child 검색을 이미 구현한 것은 아닙니다. 반환 단위, 중복 부모 처리, 문맥 길이 제한, 출처 표시를 새로 정하고 실행해야 합니다. 지금은 선택 조건을 설명하며 실제 런타임은 만들지 않습니다.

Hybrid 검색은 다른 종류의 검색 결과를 결합한다

제품 코드처럼 정확히 같은 문구를 찾아야 하는 경우와 비슷한 뜻의 표현을 찾아야 하는 경우는 검색 신호가 다를 수 있습니다. Hybrid 검색은 흔히 키워드 검색과 벡터 검색처럼 다른 검색 방식의 결과를 결합합니다. 질의 표현을 여러 개 만드는 MultiQuery와는 변경 지점이 다릅니다.

두 검색기의 원점수를 그대로 더하면 척도가 다른 문제가 생길 수 있습니다. 순위를 이용해 결합하거나 점수를 조정하는 정책을 별도로 정해야 합니다. 이 수업에서는 결합 API를 구현하지 않고, 현재 실패 원인에 그 구성이 필요한지 설명하는 데 집중합니다.

틀린 숫자를 넣은 진단은 생성 함수만 바꿨습니다. 검색 결과와 원문 매핑은 유지되므로 Recall은 1입니다. 답변에 library-1:0을 넣으면 인용 형식도 통과합니다. 그래도 999일은 원문의 14일과 다릅니다.

판정 이유에는 단순히 틀림이라고 쓰지 말고 어느 숫자·조건·질문 적합성이 다른지 적습니다. 예제의 휴관 질문에 대출 999일로 답한 행은 주제도 맞지 않습니다. 평가자는 답변이 그럴듯한 문장인지보다 질문과 근거를 보존했는지 봅니다.

회귀는 이전에 되던 동작이 나빠진 경우다

bad_order는 후보를 역순으로 바꾸는 의도적인 진단입니다. 대출 질문의 원문 ID는 맞지만 마침표가 앞에 와서 기간 답변을 잃습니다. 휴관 질문은 다른 원문 청크가 반환되어 Recall도 0입니다. 작은 변경이라도 질문별로 결과가 다르게 나빠질 수 있습니다.

회귀를 발견하면 새 방법을 무조건 고치면서 다른 값까지 바꾸지 않습니다. 먼저 해당 변경을 되돌려 기준선이 다시 재현되는지 확인합니다. 이후 실패 원인을 좁힌 새로운 한 변수 실험을 설계합니다.

실패한 질문을 분모에 남기기

검색 Timeout 진단에서는 휴관 질문만 결과를 관측하지 못했습니다. 대출은 Recall 1, 주차는 empty_gold NA입니다. 답변 가능 질문은 여전히 2개이고 관측된 것은 1개입니다. 관측된 1개 평균은 1이지만 답변 가능 2개 전체 평균은 null로 남습니다.

전체 평균을 1로 적으면 실패한 휴관 질문을 조용히 제외한 셈이 됩니다. 오류가 해결되었다면 같은 질문을 다시 실행하고 새 결과를 기록합니다. 실패를 근거 없음으로 바꿔 정상 거절처럼 처리하지 않습니다.

시간·호출 수·비용은 같은 숫자가 아니다

판정은 새로운 기술을 썼는지보다 어떤 실패가 줄었고 무엇이 늘었는지를 설명해야 합니다. 추가 이익이 관측되지 않았다면 보류할 수 있습니다. 실패가 남아 있으면 결과를 더 확인해야 하고, 이전 동작을 깨뜨렸다면 변경을 되돌리는 것이 먼저입니다.

예제에서는 baseline을 현재 로컬 기준으로 유지하고 rerank와 multiquery를 보류했습니다. 이는 완성 서비스 승인도, 이 기법들이 항상 불필요하다는 뜻도 아닙니다. 다른 실패 유형·문서·질문에서는 새 근거를 수집해야 합니다.

student_decision.py의 함수는 사람이 확인한 failure·regression·benefit_evidence를 받아 다음 검토 상태를 고릅니다. 실패를 먼저 확인하고, 회귀가 있으면 되돌리기 대상으로 분류합니다. 이익 근거가 있을 때도 consider_adoption을 반환할 뿐 실제 배포나 서비스 채택을 승인하지 않습니다.

이 함수는 답변 의미를 자동 판단하지 않습니다. 앞서 읽기 대조와 실험 비교를 통해 만든 bool 값을 처리하는 연습입니다. 잘못된 문자열 False를 bool False처럼 받아들이지 않도록 자료형도 검사하세요.

40·46일에 넘길 결정과 실행 함수

40일 화면에서는 유지한 baseline의 A1 답변·출처를 보여 주고 실제 실행 모드를 함께 설명합니다. service.answer(question)는 같은 청크와 고정 생성기를 연결한 함수이며 실제 모델이나 Chroma 서비스가 아닙니다. 운영 예외는 정상 no_evidence 응답으로 숨기지 않습니다.

46일 팀 실험은 같은 판단 양식을 재사용하되 자신의 문서·질문·기준선으로 다시 평가합니다. 이 가상 도서관에서 보류한 결정을 팀 자료에 자동 적용하지 않습니다. 개선 기술을 모두 채택할 의무도 없습니다.
