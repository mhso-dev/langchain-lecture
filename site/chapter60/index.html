54장 저장 함수와 59장 정책을 이어받기

54장의 repository.py는 동적 값을 SQL에 이어 붙이지 않고 %s와 별도 인수로 전달합니다. get_document는 소유 문서가 없으면 None이고, list_turns는 소유 대화가 없으면 KeyError입니다. 접속 오류는 정상 빈 결과로 바꾸지 않습니다.

59장의 recent 정책은 같은 fixture에서 T3/T4를 고르고 장소·언어를 모델 입력에서 뺍니다. 그 결과가 장기 저장 필요성을 자동으로 결정하지는 않습니다. 오늘의 기억은 명시적으로 저장한 answer_style이며, 과거 대화 요약이나 답변 내용을 자동 추출한 값이 아닙니다.

네 저장 책임과 수명을 나누기

State는 현재 대화에서 갱신할 값입니다. 체크포인터는 그 State를 thread별로 다시 찾는 경로입니다. Store는 namespace와 key로 대화를 넘어 정보를 찾는 인터페이스이고, 서비스 DB는 사용자·문서·대화·질문/답변 같은 업무 관계를 저장합니다. 같은 PostgreSQL 제품을 쓴다고 이 네 역할이 같은 테이블이 되지는 않습니다.

namespace는 저장 영역을 구분하는 이름 묶음입니다. InMemoryStore에서 (alice, preferences)와 (bob, preferences)는 다른 영역입니다. 같은 Store 객체를 쓰는 동안 새 대화에서도 alice 값을 찾을 수 있지만 새 InMemoryStore 객체는 비어 있습니다. 대화를 넘는 범위와 프로세스 종료 뒤의 영속성을 구분합니다.

질문에 user_id=bob이라고 써도 그 요청의 사용자가 bob으로 바뀌어서는 안 됩니다. TrustedAppContext는 신뢰된 앱이 확인한 신원을 전달할 자리입니다. 이 수업에서는 제공 코드가 가상 alice/bob를 만들며 실제 로그인은 구현하지 않습니다.

frozen dataclass는 생성 뒤 값 변경을 막습니다. 올바른 타입을 받았다는 사실만으로 실제 사용자 인증이 끝나는 것은 아닙니다. 실제 서비스에서는 인증 어댑터가 context를 만들고 외부 입력으로 user_id를 고르게 하지 않아야 합니다.

put은 memory_key와 value 외의 필드를 거부합니다. user_id/thread_id를 추가하면 ValueError이며 DB를 부르지 않습니다. 사용자 식별자와 DB 접속 계정 course도 다릅니다. 이 owner 조건은 교육 계정으로 직접 SQL을 실행하는 사용자를 제한하는 RLS를 구현한 것이 아닙니다.

기존 B1에 기억 테이블을 추가하기

53~54장의 사용자·문서·대화 테이블을 그대로 둡니다. 060_memory.sql은 course_users를 참조하는 course_memories 하나를 추가합니다. owner와 memory_key의 조합을 기본 키로 삼으므로 alice의 answer_style과 bob의 answer_style이 공존합니다.

value는 문자열이고 updated_at은 갱신 시각입니다. Python 저장 경계는 공백 키·값을 거부합니다. SQL의 CHECK와 Python 검사가 같은 범위를 모두 검증한다고 가정하지 말고 실제 제약을 읽습니다. 이 테이블은 프레임워크 체크포인트 테이블을 대신하지 않습니다.

제공 apply_schema.py는 같은 적용 기록에서 053을 확인하고 060을 순차 추가합니다. 공통 도구의 트랜잭션·잠금·적용 흐름을 보존하고 선택 단계와 오류 안내를 54/60으로 제한한 60장 사본입니다. 기존 표를 지우거나 새 볼륨으로 갈아타는 절차가 아닙니다.

사용자와 키를 함께 넣어 CRUD 실행하기

put_memory는 새로운 키면 생성하고 같은 owner/key가 있으면 값을 갱신합니다. 이 동작을 upsert라고 부릅니다. ON CONFLICT의 두 열은 기본 키와 같으며, 값은 SQL 문자열 밖의 tuple로 전달합니다. 작은따옴표가 든 값도 SQL 명령으로 이어 붙이지 않습니다.

get_memory는 같은 owner/key를 조회해 문자열 또는 None을 반환합니다. delete_memory는 지운 행이 하나일 때 True이고 없으면 False입니다. alice의 삭제가 bob의 같은 키에 영향을 주면 안 됩니다.

표현 선호를 저장했다고 대화의 질문/답변 이력이 함께 저장되지는 않습니다. save_exchange는 54장의 save_turn을 호출하는 별도 경로입니다. 대화의 owner를 확인한 뒤 이력을 저장하며 기억 CRUD와 여러 호출을 묶은 원자적 트랜잭션을 제공한다고 주장하지 않습니다.

내부 체크포인트 키를 만들 때에도 대화 소유권을 먼저 확인합니다. UUID 문법이 맞는 대화 ID를 안다는 사실만으로 권한이 생기지는 않습니다. list_turns가 타인/없는 대화에 KeyError를 내면 키를 반환하지 않습니다.

같은 사용자의 새 대화 둘은 서로 다른 내부 키를 갖지만, 사용자 기억은 같은 owner/key로 찾습니다. 실제 인증과 HTTP 세션은 이후 69장의 경계입니다. 지금의 thread 문자열을 외부 사용자의 인증 정보로 사용하지 않습니다.

로컬 검사에서 확인한 것 읽기

현재 가능한 검사는 실제 Python 저장 함수에 연결 대역을 주입한 실행입니다. FakeDB는 코드가 전달한 SQL과 인수를 기록하고 제한된 동작을 메모리에서 수행합니다. PostgreSQL 문법, FK, commit/rollback, 디스크 영속성을 검사하는 DB 엔진이 아닙니다.

observe.py는 alice/bob CRUD, payload 신원 거부, 소유 대화, 접속 오류를 확인합니다. 별도로 설치된 InMemoryStore도 실행해 namespace 분리와 새 객체의 빈 결과를 관찰합니다. 두 실행 모드가 관찰 JSON에 구분되어 있습니다.

오류를 빈 기억으로 숨기지 않기

없거나 지운 기억을 읽으면 None이지만 DB 접속 실패는 ConnectionError 같은 실행 오류입니다. 둘을 같은 빈 응답으로 처리하면 사용자는 저장한 정보가 사라졌다고 오해할 수 있습니다. 재시도 전에 실패 위치와 실행 여부를 확인합니다.

다른 사용자 대화의 조회는 KeyError, payload에 신원을 추가하면 ValueError입니다. 현재 구현은 자동 재시도·중단 복구·실제 로그인·RLS를 제공하지 않습니다. 가상 context를 만들 수 있다는 사실을 인증 통과로 쓰지 않습니다.
