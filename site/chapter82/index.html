05

관련 개념 더 읽기

같은 API, 다른 저장소

81일차의 todo/api-tests.md와 같은 ID·제목·완료 사례를 가져옵니다. 54일차의 값 바인딩과 70일차의 저장 경계도 읽습니다. 이전 실제 기록이 없으면 제공 준비 앱과 고정 관찰을 읽고, 자기 HTTP 또는 DB 수행으로 바꾸지 않습니다.

첫 15분에는 이전 기록의 작업 폴더, 같은 사례의 입력·기대·관찰, 아직 확인하지 못한 항목을 짝에게 설명합니다. 첫 절의 30분 안에 포함되는 진입 활동입니다. 전반 1–6절과 후반 7–12절은 각각 240분이며 휴식·점심은 별도입니다.

저장소가 달라져도 추가·수정·삭제 요청의 뜻은 같습니다. 브라우저는 ID를 새로 발급하지 않고, title 수정은 completed를 바꾸지 않으며, 오류를 정상 빈 목록으로 숨기지 않습니다. 이번 장의 새 조건은 PostgreSQL 저장과 status/q 검색입니다.

Todo는 todo_t1.todos를 사용합니다. 이전 수업의 B1 대화·문서·기억이나 A1 응답, P1 프로젝트 작업 레코드를 Todo 행으로 바꾸지 않습니다. 접속 설정·트랜잭션 기법을 재사용하는 것과 데이터 계약을 합치는 것은 다른 일입니다.

영속성에는 어떤 증거가 필요한가

영속성은 프로그램의 메모리가 사라져도 필요한 데이터가 남도록 저장하는 성질입니다. 81일차에서 새 MemoryRepository가 빈 목록을 반환한 것은 메모리 저장소의 범위입니다. 82일차에서 실제 PostgreSQL에 저장한 행이 앱 프로세스 재시작 후에도 같은 ID·값으로 조회되어야 해당 조건의 지속성을 관찰했다고 말할 수 있습니다.

앱 재시작과 DB 재시작은 다릅니다. 앱만 다시 띄워 DB에서 읽는 경우, DB를 같은 데이터 볼륨으로 다시 시작하는 경우, 새 빈 볼륨을 연결하는 경우를 나누어 기록합니다. 브라우저 새로고침만으로 DB 재시작까지 검증했다고 적지 않습니다.

백업 복구는 재시작과 별도 과제입니다. 어떤 시점의 백업을 어디에 복구했고 어떤 ID·값을 대조했는지 필요합니다. 원본 볼륨이나 기존 데이터를 삭제하여 결과를 맞추지 않습니다. 이번 제공 자료의 실제 재시작·복구 칸은 비어 있으므로 학생도 자기 관찰이 없으면 미실행을 남깁니다.

독립 스키마와 T1 타입

스키마는 여기서 테이블 이름을 묶는 공간입니다. todo_t1.todos는 다른 수업 테이블과 이름을 분리합니다. id는 integer identity가 발급하고 completed는 boolean, title은 text로 둡니다. DB가 발급한 ID는 빈 번호가 생겨도 재번호하지 않습니다. 삭제나 실패한 트랜잭션 뒤 번호가 연속하지 않을 수 있습니다.

애플리케이션은 양끝 공백을 정상화한 제목을 저장합니다. DB CHECK도 빈 제목과 정상화되지 않은 제목을 거부하도록 같은 공백 문자 집합을 사용합니다. Python·JavaScript·SQL이 각각 다른 기본 trim에 기대지 않도록 하는 장치입니다. 실제 SQL 수용과 동일 결과는 준비된 PostgreSQL에서 별도로 대조합니다.

PostgreSQL text는 NUL 문자를 저장하지 못합니다. 81 메모리에서 보존되던 제목에 NUL이 있다면 82는 STORAGE_TEXT_UNSUPPORTED로 명시적으로 거부합니다. 조용히 문자를 삭제해 다른 제목으로 저장하지 않습니다. 이 저장 매체 제약은 T1의 공백 정책을 임의로 바꾸는 것이 아닙니다.

설정과 값을 SQL에서 분리하기

SQL 값 바인딩은 문장 안의 자리표시자와 실제 값을 나누어 드라이버에 전달하는 방식입니다. 제목을 f-string이나 문자열 더하기로 SQL에 붙이지 않습니다. 테이블명과 열 이름은 제공 코드에 고정하고 사용자 입력으로 바꾸지 않습니다. 값 바인딩은 임의의 SQL 식을 안전하게 허용하는 기능이 아닙니다.

search_spec는 status를 None/False/True로 바꾸고 q를 정상화한 뒤 SQL과 값 묶음을 반환합니다. 아래 출력의 튜플은 DB에 전달할 준비 값입니다. SQL 엔진이 검색해서 얻은 행이 아닙니다. 특히 q에 %나 _가 들어가도 값 자체는 문자 그대로 유지됩니다.

반환값은 commit 경계를 지난 뒤에

트랜잭션은 관련 DB 작업을 한 단위로 처리하는 경계입니다. 제공 저장소는 연결 문맥 안에서 SQL을 실행하고 반환 행을 검증합니다. 문맥을 정상적으로 빠져나온 뒤에 결과를 반환하므로 commit 전에 성공 데이터를 화면에 보내지 않도록 설계했습니다.

그래도 commit 단계에서 연결이 끊기면 서버가 실제로 반영했는지 응답만으로 알 수 없는 경우가 있습니다. failed_or_unknown은 이 불확실성을 보존합니다. data=null인 오류를 반환하고 자동으로 INSERT를 다시 보내지 않습니다. 연결 자체를 열지 못한 unavailable과 구분합니다.

아래 RecordingConnection은 SQL 호출과 문맥 이벤트를 기록하는 대역입니다. commit_requested_in_double이라는 문자열은 실제 DB commit 증거가 아닙니다. 실패 분기를 읽고 재전송 대신 확인해야 할 이유를 설명하는 자료입니다.

같은 CRUD와 저장 오류 대조하기

저장소만 바꾸어도 검증 순서는 유지합니다. 빈 제목·잘못된 bool·추가 필드는 DB 접속 전에 거부하고, 유효한 수정 필드는 고정된 한 UPDATE 문장으로 전달합니다. 제목과 완료를 함께 바꿀 때도 전체 입력을 검사한 뒤 실행합니다.

정상 조회에서 행이 없으면 []이고, 연결이나 SQL 실행 오류는 STORAGE_FAILURE입니다. 삭제할 ID가 없으면 NOT_FOUND입니다. 화면에서 모두 “검색 결과 없음”으로 표시하면 저장 장애와 실제 빈 결과를 구분할 수 없습니다.

실제 수업 DB가 준비됐을 때만 환경·기존 데이터·대상 스키마를 확인한 뒤 마이그레이션과 서버 진입을 수행합니다. 로컬 준비 대역은 실제 PostgreSQL의 문법·권한·제약·트랜잭션을 대신 검증하지 않습니다. 실행이 막히면 오류를 기록하고 아래 대역 분석으로 같은 학습 목표를 이어갑니다.

완료 필터와 검색의 뜻부터 정하기

필터는 이미 정해진 조건에 맞는 행만 고르는 작업입니다. status=all은 완료 여부를 제한하지 않고 active는 completed=false, completed는 completed=true입니다. q는 양끝 공백을 제거한 제목의 부분문자열이며 빈 q는 제목 조건을 제한하지 않습니다.

두 조건은 AND입니다. active와 q=Alpha면 미완료이면서 제목에 대문자 A로 시작하는 Alpha가 들어 있는 행을 고릅니다. alpha와 Alpha는 구분하고 Unicode 정규화나 임의의 소문자 변환을 추가하지 않습니다. 결과는 ID 오름차순입니다.

아래 고정 자료는 7개 T1 행과 공개 검색 사례 12개입니다. 다른 데이터를 섞으면 기대 ID가 달라질 수 있으므로 같은 자료에서 Python 기대와 실제 PG 관찰을 대응시킵니다. 사례를 봤다는 사실을 숨긴 성능 평가나 비공개 시험이라고 부르지 않습니다.

%와 _를 문자 그대로 찾기

SQL LIKE에서 %와 _는 패턴의 일부로 해석될 수 있습니다. 이번 요구는 패턴 검색이 아니라 제목에 그 문자 자체가 들어 있는지 찾는 것입니다. 제공 SQL은 strpos(title COLLATE "C", %s)>0을 사용하고 q를 값으로 바인딩합니다. 따라서 %를 입력했다고 모든 제목을 찾는 의미로 바꾸지 않습니다.

COLLATE "C"를 명시한 준비 검색과 Python의 부분문자열 기대를 같은 자료에서 비교합니다. 둘 다 이 수업에서는 대소문자를 구분하며, 빈 q는 별도 조건으로 제한을 해제합니다. 문자열의 표현·DB 설정이 다른 환경까지 동일하다고 확대하려면 실제 자료와 환경을 추가로 확인해야 합니다.

웹 주소에 %나 공백을 실어 보내려면 인코딩이 필요합니다. URLSearchParams는 전송 표현을 만들고, 서버가 읽은 q의 의미는 원래 문자열입니다. 수동으로 먼저 인코딩한 값을 다시 URLSearchParams에 넣어 이중 인코딩하지 않습니다.

보이는 조건과 확인된 결과 맞추기

검색 입력란에 새 값을 적었다고 그 조건의 결과가 확정된 것은 아닙니다. controller는 성공한 조회의 query와 rows를 함께 저장합니다. 새 조건의 조회가 실패하면 이전 확인 조건과 목록을 유지하고 stale로 표시합니다.

화면은 “마지막 확인 조건”을 별도로 보여 줍니다. 입력란의 completed/%와 이전 확인 조건 active/_가 다를 수 있으므로, 목록이 어떤 조건에 해당하는지 설명할 수 있어야 합니다. 실패를 감추기 위해 빈 목록으로 바꾸거나 새 query만 먼저 확정하지 않습니다.

성공한 조건으로 항목을 수정한 뒤에는 같은 조건으로 다시 조회합니다. active 목록에서 항목을 완료 처리하면 다음 정상 조회에서 사라지는 것이 기대일 수 있습니다. 이것을 삭제로 해석하지 말고 all 또는 completed 조건에서 같은 ID를 확인합니다.

재시작·실패 관찰을 안전하게 계획하기

재시작 실습은 저장 경로를 확인하는 실험입니다. 실제로 만든 시험 행의 ID·제목·완료와 접속 대상을 기록하고 앱만 재시작한 경우부터 비교합니다. 다른 학습자의 행을 삭제하거나 새 DB에 연결한 결과를 같은 DB의 손실로 판단하지 않습니다.

환경이 없으면 provided의 대역 사례로 정상 빈 결과·연결 실패·commit 효과 미확인을 분석하고 실제 실험 계획을 작성합니다. 계획과 대역은 실제 영속성의 증거가 아니므로 수행 목표의 실제 환경 부분은 미확인입니다. 백업 복구도 별도 격리 계획만 준비합니다.

작은 변경의 회귀와 diff

저장·검색을 붙인 뒤에도 81의 공백·ID·완료·제목 수정·삭제와 잘못된 응답 거부는 유지되어야 합니다. 같은 클라이언트와 경계의 원본 해시를 확인한 뒤 필요한 작업 사본에서 검사합니다. 검색의 새 기대와 기존 CRUD 기대를 한 표에서 추적합니다.

82의 15개 Python 검사는 SQL 문장·값·대역의 문맥 경계와 입력을 확인하고, 3개 Node 검색 검사는 전송 표현과 조건 상태를 확인합니다. 복사된 81 검사까지 다시 실행하더라도 새로운 기능 검사의 개수로 중복 계산하지 않습니다. 실제 DB·HTTP·UI 관찰은 별도입니다.

Codex 수정 요청은 “검색이 이상하다”보다 입력 q·status, 같은 자료의 기대 ID, 실제 응답 또는 대역 출력, 관련 SQL/제어기 파일을 포함해야 합니다. 원인을 바꾸기 전에 재현 조건을 고정하고 diff에서 요구와 무관한 데이터 초기화·타입 변환이 들어갔는지 확인합니다.
