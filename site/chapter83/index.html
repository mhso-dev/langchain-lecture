05

멱등적인 완료 상태 갱신 심화 읽기

결함 입력과 영향 범위

82일차의 T1 앱과 검색·저장 실패 기록을 가져옵니다. 첫 15분에는 같은 ID·완료 규칙, 실제 실행한 환경, 아직 확인하지 않은 HTTP·PG 항목을 설명합니다. 이전 기록이 없으면 제공 자료를 읽고 자기 수행으로 바꾸지 않습니다.

오늘의 결함은 강사가 일부러 만든 별도 사본입니다. 정상 reference와 오류 faulty가 같은 T1에서 출발하며 원래 82 앱에 결함이 있었다고 주장하지 않습니다. 완료 값을 명시 설정해야 하는데 현재 값을 반전시키는 차이를 다룹니다.

오류 재현은 기대와 실제가 어긋나는 조건을 고정하는 일입니다. “완료가 이상하다”보다 초기 false, 같은 ID, true 두 번, 기대 true/true, 실제 true/false를 적으면 다른 사람이 같은 경로를 따라갈 수 있습니다.

오류 재현 절차

재현 보고에는 작업 폴더, 버전, 입력 순서, 기대, 실제 출력과 종료 코드를 넣습니다. 콘솔의 마지막 줄만 복사하면 초기 데이터가 무엇이었는지 알 수 없습니다. 같은 제목이 있어도 ID가 다르면 다른 항목입니다.

7일차의 재현 기록 방식처럼 관찰과 가설을 분리합니다. “반전 코드가 원인 같다”는 가설이고 실제 true/false는 관찰입니다. 코드와 같은 검사가 그 가설을 지지하는지 다음 단계에서 확인합니다.

오류가 있는 기준 구현

faulty는 메모리 저장소와 PG 저장소의 update에만 반전 로직을 넣었습니다. 메모리에서 current를 읽어 반전하고, PG 경로에서는 get으로 읽은 현재 완료를 반전해 UPDATE에 전달합니다. 둘 다 사용자가 보낸 목표 값을 무시한다는 같은 오류입니다.

PG의 get과 UPDATE를 늘린 코드가 실제 DB에서 실행됐다는 뜻은 아닙니다. 제공 관찰은 메모리 실행과 PG 호출 대역입니다. 실제 HTTP·PG 재현 여부는 빈 기록에 따로 남깁니다.

정상 원본을 고쳐 오류를 만드는 대신 작업 사본을 사용합니다. 수정 전 파일을 보존해야 어떤 줄이 바뀌었는지 비교할 수 있습니다. 같은 파일 이름이어도 다른 폴더를 실행하면 다른 실험이 됩니다.

수정 전 실패 기록

실패 출력의 observed가 true/false인지 확인합니다. ModuleNotFoundError로 종료됐다면 아직 완료 규칙을 시험한 것이 아닙니다. 환경 오류를 기대한 테스트 실패라고 기록하지 않습니다.

같은 기대를 reference에 적용하면 true/true가 됩니다. 이 비교는 사용자가 요청한 상태를 그대로 유지하는 의미를 보여 주며 네트워크에서 정확히 한 번 실행을 보장하는 증거는 아닙니다.

Codex에 전달할 재현 입력

Codex에 전달할 맥락에는 현재 작업 사본과 수정 가능한 파일을 적습니다. 목표는 completed를 반전하지 않고 요청한 bool로 설정하는 것입니다. ID·제목·타입·검색·오류 외피는 유지합니다.

같은 재현 명령과 기대를 요청에 넣으면 수정 뒤 무엇을 다시 확인할지 분명해집니다. “모든 테스트를 통과시켜라”만 요청하면 검사 삭제나 범위 밖 변경을 놓치기 쉽습니다. 변경 이유와 검증 계획을 먼저 읽습니다.

도구를 사용할 수 없으면 제공 두 함수를 비교하고 같은 수정을 수동으로 검토합니다. 실제 Codex 응답·시간·커밋이 없으면 만들어 적지 않습니다. 제공 참조는 도구 실측 산출물이 아닙니다.

원인과 변경 diff 검토

diff에서 가장 먼저 보는 것은 요구와 줄의 관계입니다. 현재 값 반전을 제거하는 변경은 완료 설정에 필요하지만, 날짜나 인증을 추가하는 변경은 이번 오류와 관계없습니다. 한 번에 다른 기능을 바꾸면 효과를 나누기 어렵습니다.

검사 기대를 true/false로 바꾸거나 실패를 무조건 성공으로 처리하면 프로그램의 약속이 바뀝니다. 출력의 오류 메시지만 숨기는 것도 원인을 고친 것이 아닙니다. 같은 입력의 상태가 true/true로 회복되는지 확인해야 합니다.

PG 사본의 추가 get은 반전용 현재 값을 얻으려고 들어간 코드입니다. 명시 값을 그대로 UPDATE하면 필요하지 않습니다. 그 조회를 제거한 이유도 diff에 설명하되 실제 PG 지연 개선을 측정했다고 말하지 않습니다.

완료 상태 갱신의 최소 수정

작업 사본에서 요청값을 반전시키는 줄을 제거하고 이미 검증된 patch를 그대로 적용합니다. completed가 없는 제목 수정에서는 완료 상태를 건드리지 않습니다. 문자열 true를 실제 bool로 몰래 바꾸는 기능도 추가하지 않습니다.

수정 뒤에는 입력·검사 버전을 바꾸지 않고 같은 명령을 다시 실행합니다. 기대는 처음부터 true/true였고, 바뀐 것은 오류 사본의 처리뿐이어야 합니다. 원본 reference는 비교용으로 그대로 남깁니다.

학생이 직접 수행한 결과는 자기 작업 폴더의 출력입니다. provided의 복구 관찰을 복사했다면 제공 분석으로 표시합니다. 작성자 임시 사본에서 정상 코드와 바이트가 같아졌다는 근거는 학생 작업이 같다는 증거가 아닙니다.

경곗값과 회귀 사례

회귀는 새 수정이 기존 행동을 깨뜨리는지 보는 일입니다. 이번 변경은 완료 처리이므로 엄격한 bool과 제목만 수정하는 경우, 같은 제목 두 ID, 잘못된 patch 뒤 상태 보존을 먼저 확인합니다.

검색·저장 실패·UI stale은 수정 파일과 의존 경로를 읽어 영향 범위를 판단합니다. 값 설정만 고쳤는데 오류를 빈 목록으로 바꾸거나 클라이언트 응답 형식을 바꾸었다면 범위가 넓어진 것입니다. 기존 정상 참조의 검사 근거는 해시가 같을 때 재사용합니다.

같은 검사를 여러 번 실행한 수를 새 검사 수로 더하지 않습니다. 통과 행의 개수만으로 이해를 평가하지 말고 실패 입력과 유지한 계약을 설명하게 합니다. 실제 HTTP·PG 관찰이 없다면 남은 범위를 표시합니다.

검색 조건의 결함 사례

기본·보충 경로는 완료 결함의 재현·diff·설명을 마무리합니다. 기본을 마친 학생은 같은 40분 안에서 %와 _의 문자 검색을 선택 대조할 수 있습니다. 모든 학생에게 새 결함을 추가로 구현하게 하지는 않습니다.

예를 들어 %는 제목의 퍼센트 문자이고 와일드카드가 아닙니다. 공개 자료의 기대 ID와 준비된 strpos/바인딩 값을 읽습니다. 실제 PG에 요청하지 않았다면 아래 출력은 Python 기대입니다.

선택 과제를 하더라도 정상 원본을 바꾸지 않습니다. 별도 실험 사본의 한 조건만 바꾸고, 기대와 실제의 차이를 설명한 뒤 원래 계약으로 돌아올 수 있게 기록합니다.

수정 전후의 출력 대조

작성자 제공 관찰과 학생 실제 관찰은 나란히 둘 수 있지만 출처 칸은 다르게 둡니다. 사용자 만족·실제 모델 품질·운영 성능은 이 공개 완료 사례로 측정한 항목이 아닙니다.

동료 재현과 롤백

동료 재현은 다른 사람이 안내만 보고 같은 결과를 얻는지 확인하는 활동입니다. 실제 참여한 사람의 명령·도움이 필요했던 지점·실패를 기록합니다. 참여하지 않은 동료의 반응은 채우지 않습니다.

되돌리기는 자기 작업 사본의 특정 변경만 대상으로 합니다. 다른 파일의 진행 중 작업까지 전체 reset하거나 원본 자료를 삭제하지 않습니다. 저장해 둔 diff와 변경 전 사본을 기준으로 범위를 확인합니다.

부분 업데이트에 전달할 검증 기록

84일차에는 정상 완료 설정을 유지한 앱에 새 요구를 추가합니다. 수정한 버전·같은 검사·T1 불변 조건·실제 미확인을 인계합니다. 의도적인 오류 사본은 다음 정상 앱의 기본값으로 사용하지 않습니다.

O83-1은 재현 기록, O83-2는 최소 수정과 이유, O83-3은 같은 회귀·인계로 확인합니다. 목표별 근거충족·수정필요·미확인으로 피드백하고 코드 생성량이나 고정 합격점으로 대신하지 않습니다.

제공 정상 참조를 그대로 읽은 학생도 근거를 설명할 수 있지만 실제 수정 수행과는 구분합니다. 다음 장에서 무엇을 유지하고 무엇을 확장할지 자기 말로 정리합니다.
