실행을 확인한 커널은 Python 3.12.15입니다. 예제에 사용한 외부 패키지는 langgraph 1.2.16입니다.

02

질문을 다듬으면 어떤 값이 돌아올까요?

State는 한 질문을 처리하면서 여러 단계가 함께 읽는 값입니다. 여기서는 question에 질문, documents에 찾은 문장 목록, answer에 최종 안내를 담습니다. 노드가 값을 읽어 바꿀 부분만 돌려주면 그래프가 앞 상태에 합칩니다.

셀 01 · 질문 앞뒤 공백 지우기

normalize가 돌려줄 딕셔너리의 키를 예측해 보세요.

실행 결과

{'question': '대출 기간은?'}

question 하나만 보입니다. strip이 앞뒤 공백을 뺐고, normalize는 문서나 답변을 만들지 않았습니다. 이 반환값을 다음 단계의 전체 상태로 넘기면 나머지 키가 사라집니다.

셀 02 · 상태에 변경분 합치기

직접 호출에서는 딕셔너리를 합쳐 그래프가 하는 일을 한 번 따라 해 봅니다.

실행 결과

{'question': '대출 기간은?', 'documents': [], 'answer': ''}

documents와 answer의 빈 값이 남습니다. 두 칸은 이제 검색과 답변 노드가 채울 자리입니다.

03

검색 노드 뒤에서 답변 읽기

엣지는 어떤 함수를 다음에 부를지 정하는 연결입니다. START에서 normalize, lookup, compose 순으로 연결한 뒤 END에서 멈춥니다. 검색 결과를 미리 써 넣지 않고 질문에 들어 있는 낱말을 자료와 대조합니다.

셀 03 · 세 노드 연결하기

이번 셀의 lookup은 노트북 안에 넣어 둔 두 가상 문장에서 찾습니다. 등록된 노드 이름과 엣지의 이름을 맞춰 보세요.

초기값부터 normalize, lookup, compose 순서로 따라가세요. 한 노드가 돌려주는 사전은 이번에 바꿀 칸만 담습니다. 나머지 두 칸은 앞 상태의 값을 유지합니다.

실행 결과

도서 대출 기간은 14일입니다.

14일이라는 문장이 나옵니다. lookup이 대출 문장을 골라 documents에 넣었고 compose는 그대로 이어 붙였습니다. 모델에 날짜를 묻는 과정은 없습니다.

과제 04 · 휴관 질문의 근거 확인하기

질문을 ‘휴관 요일은?’로 바꾸어 실행하고 최종 상태에서 documents만 표시하세요.

풀이와 실행 결과 보기

실행 결과

['도서관은 월요일에 휴관합니다.']

휴관에 해당하는 문장 한 개가 목록에 남습니다. answer가 문자열인 데 비해 이 칸은 검색이 여러 건일 수 있어 목록입니다.

초기 상태와 세 노드의 변경값

질문의 공백을 지운 뒤 documents와 answer에 어떤 값이 남는지 예시에서 찾아보세요.

STEP 01 · 호출자

초기 상태 만들기

질문을 넣고 결과 칸은 비웁니다.

question  = '  대출 기간은?  '
documents = []
answer    = ""
STEP 02 · normalize

질문의 공백 제거

question만 갱신하고 다른 키는 유지합니다.

question  = '대출 기간은?'
documents = []
answer    = ""
STEP 03 · lookup

질문에 맞는 문장 조회

가상 문서 중 대출 키워드가 맞는 문장을 고릅니다.

question  = '대출 기간은?'
documents = ["도서 대출 기간은 14일입니다."]
answer    = ""
STEP 04 · compose

문서를 답변으로 연결

documents를 읽고 answer를 갱신합니다.

question  = '대출 기간은?'
documents = ["도서 대출 기간은 14일입니다."]
answer    = "도서 대출 기간은 14일입니다."
04

다시 풀어 보기

주차 질문을 넣었을 때 답변을 만든 노드와 빈 목록을 만든 노드를 구별해 보세요. 다음 장은 빈 검색 뒤 한 번 더 찾을지 결정합니다.

05

관련 개념 더 읽기

실행 순서와 상태를 나누어 보기

Node는 이번에 실행할 Python 함수입니다. Edge는 어떤 함수 다음에 어떤 함수를 실행할지 정한 연결입니다. State는 실행 중 공유하는 값의 묶음입니다. 문서가 어디에 저장되는지와 어느 함수가 다음에 호출되는지를 한 용어로 섞으면 오류 원인을 찾기 어렵습니다.

예를 들어 질문의 공백을 지우는 normalize는 question을 읽고 question만 갱신합니다. 문서를 고르는 lookup은 question을 읽고 documents를 갱신합니다. 답변을 만드는 compose는 documents를 읽고 answer를 갱신합니다. 이번 그래프에서는 모델이 다음 노드를 고르지 않고 코드의 고정된 연결을 따릅니다.

세 요소를 코드에 대응하기
요소예제변경의 의미
Nodenormalize, lookup, compose처리할 계산을 바꿈
Edgenormalize → lookup실행 순서를 바꿈
Statequestion, documents, answer전달하고 보관할 값을 바꿈
TypedDict로 세 필드의 약속 적기

State는 실행 중 사용할 딕셔너리의 키와 값 형태를 적은 타입입니다. question은 질문 문자열, documents는 문장 문자열의 리스트, answer는 답변 문자열입니다. 실제 값은 graph.invoke에 넘기는 initial에 들어 있습니다. 타입 선언만으로 질문이 자동 생성되지는 않습니다.

TypedDict는 정적 타입 확인을 돕는 선언입니다. 잘못된 자료형이나 빈 입력을 모든 경우 자동으로 막아 주는 런타임 검증기로 생각하지 마세요. 이번 예제는 question.strip() 결과가 비었는지 노드에서 직접 검사합니다.

초기 상태 예측
키초기 값누가 갱신하나요?
question" 대출 기간은? "normalize
documents[]lookup
answer""compose
노드는 상태를 읽고 변경분을 반환합니다

normalize가 반환한 딕셔너리에는 question 하나만 있습니다. 반환에서 빠진 documents와 answer를 지우라는 뜻이 아닙니다. 이번처럼 별도 갱신 규칙을 지정하지 않은 필드는 해당 키가 반환되면 새 값으로 바뀌며, 반환하지 않은 필드는 유지됩니다.

입력 딕셔너리의 값을 직접 바꿔 놓고 아무것도 반환하지 않는 방식을 피합니다. 갱신할 내용을 새 딕셔너리로 반환하면 노드의 책임과 검사할 결과가 분명해집니다. 이 장은 순차 실행만 다루며 여러 노드가 동시에 같은 키를 갱신하는 경우는 포함하지 않습니다.

노드 등록과 연결 뒤에 실행하기

StateGraph는 그래프를 만드는 빌더입니다. add_node의 첫 인자는 그래프에서 사용하는 이름이고 두 번째 인자는 실행할 함수입니다. add_edge는 등록한 이름으로 연결합니다. START는 입력을 받은 시작 위치, END는 종료 위치입니다.

compile로 실행 가능한 그래프를 만든 뒤 invoke를 호출합니다. 컴파일 단계가 실제 문서 내용의 품질이나 모든 런타임 오류를 증명해 주지는 않습니다. 문서 파일 누락처럼 실행할 때 드러나는 문제도 직접 검사해야 합니다.

변경분과 최종 상태를 각각 관찰하기

stream_mode="updates"에서는 실행된 노드 이름과 그 노드의 갱신 내용을 차례로 봅니다. invoke 결과는 실행이 끝난 뒤의 상태입니다. 예제는 관찰을 위해 두 호출을 모두 사용하므로 그래프 전체가 두 번 실행됩니다. 실제 API를 노드에 넣는다면 그만큼 호출이 다시 발생할 수 있습니다.

첫 번째 출력은 question만, 두 번째는 documents만, 세 번째는 answer만 담습니다. 그 사이 다른 값이 사라지는 것이 아닙니다. 출력된 변경분을 초기 상태에 차례로 적용하여 마지막 상태를 손으로 완성해 보세요.
