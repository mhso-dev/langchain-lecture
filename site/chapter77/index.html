CI 통과와 배포 검증

CI는 변경을 검사하고 이미지 후보를 준비합니다. CD는 그 후보를 특정 환경에 전달하고 적용·확인하는 흐름입니다. 테스트가 성공한 이미지라도 대상의 설정·DB 상태·권한·네트워크가 다르면 정상 서비스가 되지 않을 수 있습니다. 따라서 CI success를 배포 완료로 복사하지 않습니다.

첫 15분에는 76일의 후보 기록과 75일의 수동 배포·보존 기록을 엽니다. 현재 이미지, 후보 이미지, 되돌릴 이전 이미지와 각 설정을 구분하고 같은 문서·대화 ID 및 전체 A1·출처 확인 항목을 찾으세요. 실제 이미지·서버 기록이 없다면 제공 합성 자료와 빈 실제 양식을 나눕니다.

수동 배포 절차의 자동화

자동화는 이름을 붙인 서버 명령을 한 번에 실행하는 일로 끝나지 않습니다. 74–75일에 같은 앱·대상·DB를 확인한 수동 순서를 먼저 읽고, 각 단계의 입력·성공 근거·실패 때 멈추는 위치를 정합니다. 그 다음 검토한 단계만 자동화할 수 있습니다.

기본은 단일 환경에서 같은 Compose/B1을 유지하며 이미지 하나를 교체하는 경로입니다. 새 AWS 구조, 무중단 트래픽 전환, 자동 DB migration을 필수로 추가하지 않습니다. 접속 방식도 앞 장에서 검토한 방법을 유지하며 호스트 검증을 끄거나 넓은 권한을 주는 것으로 막힌 부분을 우회하지 않습니다.

수동 입력과 승인

workflow_dispatch는 사람이 workflow 실행을 요청하는 이벤트입니다. 이 기능으로 입력받은 commit과 digest는 후보를 찾는 값이며, 입력했다는 사실만으로 그 이미지가 실제 신뢰한 CI 결과라는 뜻은 아닙니다. 수동 실행 버튼을 누른 것도 환경 승인을 받은 것과 다릅니다.

실제 workflow_dispatch를 사용하려면 해당 workflow 파일이 기본 브랜치에 있어야 합니다. 현재 제공 파일은 .github/workflows 밖의 .yml.template이므로 버튼이 생기거나 실행이 활성화된 상태가 아닙니다. main과 course-staging은 수업 설계 이름이며 실제 기본/보호 브랜치·환경과 함께 맞춰야 합니다.

입력 문자열을 run 명령 안에 직접 조합하지 않고 env로 전달하는 부분도 확인하세요. 이후 검증기는 실제 신뢰한 CI run·registry·승인 대상을 대조해야 합니다. 이 교재의 로컬 check_plan은 선언 형식을 보는 도구이며 외부 증거를 조회하는 검증기가 아닙니다.

환경 보호 규칙과 승인 조건

GitHub environment는 staging이나 production처럼 배포 대상을 표현합니다. YAML에 environment: course-staging을 썼다고 검토자나 허용 브랜치가 자동으로 원하는 값이 되지는 않습니다. 실제 환경의 required reviewers, 배포 허용 브랜치, 자기 승인 제한, 비밀 접근 조건을 확인해야 합니다.

환경 보호 기능의 지원 여부는 플랜과 저장소 공개 범위에 따라 다릅니다. 공식 문서의 기능 설명과 실제 계정에서 설정이 켜졌다는 관측을 구분하세요. 필요한 검토를 설정할 수 없다면 승인 단계를 생략하지 않고 자동화를 보류한 채 검토한 수동 절차를 유지합니다.

승인은 무엇을 검토했는지가 남아야 합니다. 여기서는 source commit, image digest, 설정 manifest 해시, environment 네 항목이 대상입니다. 승인 후 후보나 설정이 바뀌면 같은 승인을 그대로 적용하지 않습니다.

검토할 때의 현재 이미지와 실제 적용 직전의 현재 이미지가 다를 수 있습니다. 다른 사람이 수동으로 변경했거나 앞선 배포가 먼저 끝났을 수 있기 때문입니다. 후보가 올바르더라도 기준 상태가 바뀌었다면 멈추고 새로 검토해야 합니다.

check_plan은 76일의 같은 commit 계보와 후보 형식을 읽고, simulate_rollout은 current_digest_before와 현재 설정이 예상값과 같은지 비교합니다. 이전 이미지는 단순히 오래된 태그가 아니라 되돌릴 대상으로 검토한 digest와 설정입니다. 현재 스키마가 이전 앱과 호환되는지도 적용 전에 판단합니다.

배포 동시성 제어

같은 환경에 두 배포가 겹치면 뒤 실행이 읽은 현재 상태가 앞 실행 때문에 바뀔 수 있습니다. concurrency는 같은 그룹의 workflow나 job 실행을 제한하는 기능입니다. 이 템플릿은 고정된 course-staging-deployment 그룹과 cancel-in-progress:false를 사용합니다.

cancel-in-progress:false는 새 요청 때문에 진행 중인 배포를 자동 취소하지 않도록 정한 값입니다. 기본 대기 설정에서는 새로운 요청이 기존 대기 요청을 바꿀 수 있으므로 모든 요청이 접수 순서대로 빠짐없이 배포된다고 설명하지 않습니다. 이 수업은 별도 큐 옵션을 추가하지 않습니다.

같은 환경을 다루는 다른 workflow가 다른 그룹을 쓰거나 사람이 서버를 직접 바꾸면 이 제한 밖의 변경이 생길 수 있습니다. 따라서 동시 실행 제어를 설정해도 적용 직전 현재 digest·설정을 다시 확인해야 합니다.

배포 대상과 앱 적용 경로

실제 적용 경로는 74–75일의 같은 앱·Compose·프록시·기존 데이터 조건을 이어받습니다. 단순히 새 이미지가 실행됐다는 사실보다 어느 설정과 실제 볼륨에 연결됐는지가 중요합니다. 이름이 같은 course-data라도 다른 호스트의 볼륨을 이전 데이터로 취급하지 않습니다.

현재 .yml.template에는 최종 원격 배포 진입과 검토한 액션 SHA가 아직 미확정으로 남아 있습니다. Python 상태 시뮬레이터에는 SSH·AWS·Docker를 실행하는 함수가 없으며 실제 배포 어댑터로 바뀌지 않습니다. 이 구분을 보고서에 그대로 남깁니다.

실제 자동화를 준비할 때는 같은 앱 입력과 설정 해시를 먼저 고정하고, 검토한 수동 접속 방식·최소 권한·호스트 검증·대상 상태 확인·실패 중지를 배포 절차로 구현해 검토해야 합니다. 현재 코드에 없는 기능을 placeholder 이름만으로 구현됐다고 가정하지 않습니다.

health와 기능 검증

health는 프로세스나 특정 준비 상태를 알리는 신호입니다. 실제 문서 질문이 같은 근거와 출처를 반환하는지, 다른 소유자가 거부되는지, 오류와 저장 결과가 보존되는지까지 자동으로 확인한 것은 아닙니다. 같은 H1 정상·빈 근거·입력/권한·실패와 전체 A1/출처를 사례별로 대조해야 합니다.

데이터 보존은 기존 owner·문서·대화·turn·상태와 연결된 실제 DB/볼륨을 기준으로 봅니다. 새 DB에 seed를 다시 넣어 비슷한 답이 나왔다고 이전 데이터가 보존됐다고 하지 않습니다. 검색 조건도 같은 원문·청크·벡터 설정을 유지해야 비교의 의미가 있습니다.

시뮬레이터의 h1_ok와 data_preserved는 그 상세 검사를 대표하는 합성 입력입니다. 실제 검사 결과를 대신하는 구현이 아닙니다. None을 True로 채워서 완료 상태를 만들지 마세요.

실패 단계별 복구 절차

적용 전 조건이 맞지 않으면 배포를 시작하지 않는 것이 결과입니다. 승인 대기·거절·현재 상태 변경·다른 배포 진행은 각각 다른 이유로 멈춥니다. 실제 효과가 없었던 차단을 배포 후 복구 성공으로 기록하지 않습니다.

적용 뒤에는 일부 변경이 이미 생겼을 수 있습니다. 새 digest나 설정이 기대와 다르거나 H1/데이터 검사에 실패하면 이전 이미지로 돌아갈 조건을 검토합니다. 관측이 없으면 확인 대기로 남기며, 적용 뒤 취소는 자동 rollback이 완료됐다는 뜻이 아닙니다.

실제 workflow의 실패·취소 처리와 복구 어댑터도 따로 구현·검토해야 합니다. 제공 템플릿에 rollback step이 없는데 GitHub가 자동으로 이전 앱을 복원할 것이라고 기대하지 않습니다. 모든 실패에 무조건 정리 명령을 붙여 기존 데이터를 삭제하지 않습니다.

합성 상태와 의미

이전 이미지로 롤백하는 조건

이미지 복구는 앱 코드를 이전 이미지로 바꾸는 작업입니다. 이를 위해 이전 digest와 그 이미지에 맞는 설정, 현재 DB 스키마와의 호환성, 복구 뒤 H1·데이터 재확인 조건이 필요합니다. 단순히 이전 태그를 적어둔 것만으로 충분하지 않습니다.

시뮬레이터는 후보 실패 뒤 이전 digest/config와 health/H1/데이터가 모두 맞다고 선언한 경우에만 simulated_rolled_back을 반환합니다. 이 결과도 실제 복구 검증은 False입니다. 복구 관측이 빠지거나 실패하면 simulated_recovery_required로 남습니다.

이미지 롤백과 DB 복구

이전 이미지를 실행해도 이미 기록된 DB 내용은 그대로 남을 수 있습니다. DB 복구는 신뢰한 백업을 별도 대상으로 되돌리고 owner·ID·관계·행 수·출처를 확인하는 다른 작업입니다. 75일의 백업·별도 대상 복원 계획과 현재 서비스 상태를 함께 검토해야 합니다.

스키마 변경이 이전 앱과 호환되지 않거나 데이터 손상이 의심되면 자동 이미지 교체로 해결됐다고 쓰지 않습니다. 실패 지점·현재 digest/config·DB 상태·백업 근거를 보존하고 수동 복구 판단으로 넘깁니다. 원본 볼륨 삭제나 새 빈 DB로의 전환은 기존 데이터 복구 증거가 아닙니다.

이 수업의 기본 경로는 자동 DB migration이나 파괴적인 되돌림을 구현하지 않습니다. 실제 배포 환경·백업·권한이 없는 상태에서는 비교 기준과 중지 조건을 작성하는 데 머물고 실제 목표는 HOLD로 표시합니다.

이미지 복구실행할 앱 버전과 설정이전 digest/config·호환성·H1/데이터
DB 복구특정 백업의 데이터별도 대상·owner/ID/관계·내용
동일 볼륨 재조회현재 볼륨의 기록실제 연결 대상과 기존 ID

배포 변경 및 관측 기록

최종 기록은 검토한 후보, 실제 적용 주체·시점, 현재/이전 digest와 설정, 상세 H1·데이터 관측, 실패·복구 근거를 연결합니다. 빈 칸을 메우는 것이 목표가 아니라 확인된 범위와 남은 미확인을 다른 사람이 재검토할 수 있게 쓰는 것이 목표입니다.

후속 웹·배포 작업은 이 절차를 참고할 수 있지만 새로운 투두 앱을 기존 RAG 서비스와 같은 기능이라고 가정하지 않습니다. 앱·자료·계약이 바뀌면 그 대상의 검사와 배포 근거를 별도로 연결해야 합니다.
