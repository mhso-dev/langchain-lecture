셀 01 · 승인 노드와 체크포인터 구성

05

LangGraph interrupt와 승인 후 재개 심화 읽기

읽기 서비스의 실행 기록

첫 15분에는 세 가지를 확인합니다. 5분 동안 29일의 thread 분리 기록을 읽고 대화 ID와 실행 ID의 차이를 설명합니다. 다음 5분에는 Q03의 안내 답변과 “이 내용으로 문의를 등록하라”의 효과 차이를 말합니다. 마지막 5분에는 승인 대기에서 result가 null이고 등록 수가 0이어야 하는 이유를 예측합니다.

읽기 응답과 쓰기 작업

읽기 요청은 이미 있는 정보를 조회해 답합니다. 쓰기 요청은 목록 추가·수정처럼 상태를 바꿉니다. Q03에 오류 대응 방법을 안내하는 것은 읽기이고, 그 설명과 별도로 문의 한 건을 목록에 남기는 것은 쓰기입니다. 오늘의 쓰기는 실제 발송이 아니라 메모리 안의 모의 등록 한 가지입니다.

ApprovalService.answer는 63일 읽기 서비스를 그대로 호출합니다. 읽기에는 승인 대기를 붙이지 않습니다. propose는 같은 읽기 결과를 먼저 확인한 뒤 별도 문의 제안을 만들고 멈춥니다. 모델이 문장을 생성했다고 자동 등록 권한을 갖는 것은 아닙니다.

승인 대상 객체

승인 대상에는 실행할 도구 이름, 검토할 인자, 효과 설명, 만료 시각이 들어갑니다. “계속할까요?”만 보여 주면 사용자가 무엇을 허용했는지 나중에 비교할 수 없습니다. 이 예제는 문의 문구 하나를 검토 가능한 arguments로 묶습니다.

request_id는 실행 요청, approval_id는 승인 대상의 식별자입니다. 둘 다 서비스가 발급합니다. arguments_hash는 정규화한 JSON 바이트의 SHA256입니다. 인자가 바뀌었는지를 비교하는 값이며 비밀번호나 암호화 토큰이 아닙니다. 소유자와 원래 요청에 연결된 대상인지도 별도로 확인해야 합니다.

시연은 재현할 수 있도록 시각을 100으로 고정하고 기본 TTL 300을 더합니다. 출력 만료 값 400은 현재 날짜의 운영 만료 시간이 아니라 고정 시계의 시험 값입니다. 실제 사용에서는 신뢰된 서버 시계와 저장 정책을 별도로 연결해야 합니다.

재개 시 소유자 검증

중단했다가 다시 실행하는 요청에도 신원이 필요합니다. 원래 요청에서 소유자를 확인했더라도 재개 시 대화의 소유권이 바뀌거나 다른 사용자가 요청 ID를 알게 될 수 있습니다. 따라서 원래 소유자와 현재 대화 소유 조건을 다시 검사합니다.

이 수업의 AppContext와 owners는 신뢰된 앱 fixture입니다. 실제 로그인이나 DB를 구현하지 않습니다. 승인 화면에서 user_id를 자유롭게 받아 AppContext로 만들면 이 계약을 지키지 못합니다. 요청 ID나 인자 해시를 아는 사실도 소유자를 대신하지 않습니다.

타인 요청은 등록 0이며 원래 사용자의 재개 예산도 소모하지 않습니다. 잘못된 신원 요청과 같은 소유자의 잘못된 승인 내용은 서로 다른 경계입니다. 후자는 요청 내용을 재시도한 것이므로 해당 요청의 누적 재개 횟수에 포함합니다.

interrupt()의 승인 대기

interrupt는 노드 실행 중 외부 결정을 기다리는 중단 지점입니다. LangGraph는 checkpointer에 현재 상태를 남기고 호출자에게 중단 정보를 돌려줍니다. InMemorySaver는 이 수업의 메모리 체크포인터입니다. 프로세스가 끝난 뒤 디스크에서 복구하는 저장소는 아닙니다.

thread_id는 어느 checkpoint를 다시 읽을지 정합니다. 이 예제는 서비스가 발급한 request_id를 내부 thread_id로 사용합니다. 대화 전체를 하나의 승인 요청으로 취급하지 않으며 두 요청을 같은 checkpoint에 섞지 않습니다.

Command로 승인·거절 전달

대기 중인 Graph는 새로운 일반 입력으로 이어 가지 않습니다. 같은 thread_id와 checkpointer에 Command(resume=payload)를 전달하면 중단 지점의 interrupt가 payload를 반환합니다. 공식 권장 입력 패턴에 맞춰 이 예제는 resume만 사용합니다. 노드 상태 변경용 update를 재개 입력에 섞지 않습니다.

resume 메서드는 외부 호출자가 사용할 서비스 경계입니다. 원래 요청·승인 ID와 해시를 검사한 다음 내부 Graph를 재개합니다. 사용자가 임의의 graph.invoke를 호출하도록 노출하면 이 검사를 건너뛰게 되므로 내부 Graph는 수업용 관찰 외에는 공개 경계로 쓰지 않습니다.

기본 Q03은 대기 전에 모델 2회와 근거 전달 도구 1회를 사용했습니다. 재개 시 답변 모델을 다시 부르지 않고 모의 등록 도구만 한 번 추가합니다. 승인 결과의 action_receipt는 쓰기 효과 기록이며 result는 앞의 A1 원형입니다. 등록을 했다고 출처를 새로 만들거나 generation_calls를 늘리지 않습니다.

거절·만료의 종료 상태

사람이 거절하면 등록 없이 declined로 끝납니다. 거절을 실행 오류 메시지로 바꿔 계속 승인을 요구하거나, 새 재개로 다시 쓰지 않습니다. 같은 요청의 종료 상태를 보존합니다.

만료는 now>=expires_at일 때입니다. 재개 시 한 번, 실제 쓰기 직전 다시 한 번 확인하므로 두 단계 사이에 만료되는 경우도 막습니다. 이 코드가 타이머를 돌려 오래된 요청을 자동 삭제하는 것은 아닙니다. 해당 요청을 다시 처리할 때 시각을 대조합니다.

인자 변경과 중복 재개

변경된 인자는 승인 대상이 달라졌다는 뜻입니다. 같은 소유자가 잘못된 해시나 허용되지 않은 결정을 보내면 pending을 유지하고 approval_target_mismatch를 돌려줍니다. 아직 쓰기를 실행하지 않았으며 이 시도는 재개 횟수에 포함합니다.

중복 재개는 이미 끝난 요청을 다시 보낸 경우입니다. 원래 소유자와 승인 ID를 확인한 뒤 보존된 결과를 돌려주고 duplicate_resume_ignored=true를 남깁니다. 모델·검색·쓰기를 다시 실행하지 않으므로 등록 수가 증가하지 않습니다.

이 관측의 한 번 실행은 같은 프로세스의 요청 원장·lock·모의 등록 사전에 의존합니다. 여러 서버나 실제 외부 시스템에서도 정확히 한 번 실행된다고 일반화하지 않습니다. 외부 쓰기는 요청 키·저장·트랜잭션·응답 유실의 경계를 별도로 다뤄야 합니다.

승인 전후의 호출 수

중단은 새 예산을 주는 신호가 아닙니다. 이미 모델과 도구를 사용했다면 그 수를 원장에 보존하고 재개 뒤의 실행을 더해야 합니다. 이 예제의 기본 전체 예산은 모델 3·도구 2·재개 2입니다. 63일의 읽기 제한이 이 전체 상한보다 크면 구성 시점에 거부합니다.

Q03 읽기는 모델 2·근거 전달 도구 1을 사용합니다. 전체 도구 상한을 1로 바꾸면 읽기에서 예산을 이미 사용했으므로 승인을 받아도 등록 도구를 실행할 수 없습니다. 승인 여부와 호출 예산은 별도의 조건입니다. 필수 검색은 retrieval_calls로 따로 기록합니다.

같은 소유자의 잘못된 재개를 두 번 보낸 뒤 세 번째 요청을 보내면 resume_limit으로 멈춥니다. 관측된 resume_attempts=3은 세 번째 시도를 거부하기 위해 센 값이며 승인 세 번이 허용됐다는 뜻이 아닙니다. 종료 뒤 중복 재개는 이미 끝난 결과를 돌려주므로 추가 예산을 쓰지 않습니다.

63일의 draft_generate_calls는 create_agent 모델 예산과 별도입니다. 실제 외부 generate를 주입하면 그 콜백의 비용·재시도를 이 장의 max_model_calls가 통제하지 않습니다. 현재 고정 대본의 호출 수를 외부 모델 비용으로 바꾸지 않습니다.

부분 실행 후 예외

쓰기 오류를 모두 “다시 실행하면 된다”로 처리하면 중복 등록이 생길 수 있습니다. 첫 사례는 등록 전에 예외가 나서 효과가 0인 경우입니다. 두 번째는 목록에 한 건을 넣었지만 성공 receipt를 돌려주기 전에 예외가 난 경우입니다. 호출자는 실패를 보지만 효과는 1일 수 있습니다.

LocalInquiryRegister의 before/after는 이 차이를 재현하는 로컬 실패 주입기입니다. 실제 외부 서비스의 상태를 관찰한 결과가 아닙니다. 쓰기 대상도 LocalInquiryRegister 타입으로 제한하므로 임의의 외부 쓰기 어댑터를 주입했다고 주장하지 않습니다.

효과 전 실패는 error/write_failed_no_effect, 효과 후 오류는 needs_review/write_effect_unknown입니다. 후자는 자동 재실행하지 않고 확인 필요로 남깁니다. result도 null이므로 미완료 작업을 정상 완료 답변 이력으로 저장하지 않습니다. 실제 서비스라면 외부 작업 상태를 조회할 방법과 운영 판단이 필요하지만 오늘은 그 통합을 하지 않습니다.

성공·실패 경로의 로그 비교

demo.py는 같은 Q03과 같은 문의 문구로 13개 관측을 남깁니다. 대기·승인·중복·거절·만료·타인·변경 해시·재개 상한·도구 상한·효과 전후 실패 및 그 뒤 중복을 포함합니다. 자신의 실행은 runs 아래에서 확인하고 provided는 작성자 기준으로 보존합니다.

모든 행을 성공률 하나로 줄이지 않습니다. 거절·만료·타인 거부는 등록 0이 올바른 동작이고, 확인 필요는 효과와 수신 상태가 갈라진 경우입니다. 상태, 공개 result, receipt, 등록 수, 누적 호출을 함께 읽어야 합니다.

승인 결과의 화면 상태

student_task.py에서 submit_decision은 원래 요청 ID·승인 ID·인자 해시와 결정을 서비스에 전달합니다. 새 도구 인자를 받아 기존 승인을 재사용하지 않습니다. visible_state는 상태, 완료 결과, 확인 필요 여부를 요약합니다. 실제 브라우저 UI를 만드는 과제는 아닙니다.

pending/declined/expired/error/needs_review는 완료 A1을 보여 주지 않습니다. completed에는 원래 result를 그대로 둡니다. 그 A1이 no_evidence나 invalid_citation이면 상태를 정답으로 바꾸지 않습니다. needs_review는 운영자가 효과를 확인할 수 있도록 별도 표시가 필요합니다.

조회·등록·분류의 책임 분리

다음 분류 학습에서 어떤 요청을 읽기·제안·추가 질문 후보로 보낼지 비교할 수 있습니다. 분류 결과는 후보 경로일 뿐 대화 소유권과 승인 완료를 만들지 않습니다. 오늘의 제안·재개 경계와 누적 예산은 그 뒤에도 유지해야 합니다.

66–67일의 서비스 평가는 정상 답변뿐 아니라 이 승인 경계의 실패도 받아야 합니다. 현재 계약은 로컬 수업용이며 최종 S1, HTTP 상태, B1 저장은 각각 후속 단계에서 검수합니다. 메모리 체크포인트를 영속 DB와 같다고 설명하지 않습니다.
