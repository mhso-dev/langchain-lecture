02

Runnable과 그래프 노드의 상태 전달 비교

같은 검색·답변 흐름도 LCEL에서는 함수 사이의 반환값으로, LangGraph에서는 상태 갱신으로 연결할 수 있습니다.

검색을 거치면 documents가 생기고 답 작성 단계는 거기서 첫 문장을 꺼냅니다. LCEL은 앞 함수의 반환값 전체를 다음 함수에 넘깁니다. Graph는 노드의 부분 반환값을 상태에 반영합니다. 두 코드가 공유하는 자료는 로컬 키워드 벡터로 찾으며 모델은 호출하지 않습니다.

05

LCEL과 LangGraph의 상태 전달 심화 읽기

공통 검색·답변 함수

make_steps가 만든 두 함수에 같은 search_function과 answer_function을 넘깁니다. 검색 단계는 R1 요청과 문서 형식을 검사하고 예상 연결 실패만 운영 상태로 바꿉니다. 답변 단계는 같은 문서 목록으로 A1을 호출합니다. 검색 실패에는 result=None을 유지합니다.

공통 자료는 contract-snapshot.json으로 식별합니다. 모드와 버전이 같아야 결과 차이를 해석할 수 있습니다. 교육용 벡터는 학습된 임베딩이 아니므로 실제 검색 엔진이나 모델을 교체한 측정과 별도 표에 둡니다.

LCEL의 명시적 입력 구성

LCEL의 다음 Runnable은 앞 Runnable의 반환값을 받습니다. search_full은 {**state, **search_step(state)}로 기존 키와 갱신을 합친 새 딕셔너리를 만듭니다. answer_full도 같은 방식으로 앞의 문서와 운영 상태를 보존합니다.

같은 키가 두 곳에 있으면 뒤 update의 값이 사용됩니다. 이 래퍼가 필요한 이유를 설명할 수 있어야 합니다. LCEL이 임의의 이전 상태를 자동으로 모아 준다고 가정하지 않습니다.

LangGraph의 상태 병합

Graph는 공통 함수가 반환한 키를 State에 반영합니다. search_step은 question과 documents 등을 바꾸고 answer_step은 result만 바꿉니다. 오늘은 고정 순차 경로라서 별도의 체크포인트나 반복을 추가하지 않습니다.

31장은 연결 실패를 notice 노드로 분기했고, 이번 비교는 공통 answer_step 안에서 result=None을 유지하도록 정리했습니다. 두 경우 모두 검색 오류에서 생성기는 호출하지 않습니다. 제어를 어느 위치에 둘지 바뀌어도 실패 의미를 유지해야 합니다.

단계별 입력과 소요 시간

observed는 원래 단계 함수를 한 번 실행하고 입력 요약, 반환 갱신, 경과 시간을 trace 목록에 추가합니다. trace는 State 밖에 있으므로 LCEL과 Graph의 결과 딕셔너리를 비교할 때 제외됩니다. 상태가 같아도 실행 시간은 매번 다를 수 있습니다.

search의 입력 document_ids는 빈 목록이고 갱신에는 검색한 문서가 있습니다. answer 입력의 document_ids는 그 목록입니다. 기록을 읽는 데 다시 invoke할 필요가 없습니다. trace를 확인하기 위해 stream이나 invoke를 한 번 더 실행하면 별도 호출과 비용이 생길 수 있습니다.
