02

공개 포트와 API의 내부 주소

외부에서 보낸 요청은 공개 포트와 프록시를 거쳐 내부 API에 도착합니다. 배포 선언에서 예상한 경로와 실제 응답을 구분해 확인합니다.

배포 예제에서는 HTTPS를 받는 프록시만 호스트의 443번에 연결합니다. 프록시는 Compose 네트워크 안의 api:8000으로 전달하고, API는 내부 db:5432를 사용합니다. DB 접속 정보를 브라우저에 건네지 않습니다.

셀 01 · 공개 포트 매핑 해석

기존 배포 설정에서 포트 관련 부분만 가져왔습니다. 어떤 서비스가 외부 요청의 첫 번째 목적지인가요?

EC2는 클라우드에서 빌려 쓰는 가상 컴퓨터입니다. 학생 브라우저에서 접속하는 주소와 그 컴퓨터 안에서 프록시가 API로 연결하는 주소는 서로 다른 접속점입니다. 연결표에서 브라우저가 출발점인 줄을 먼저 보세요.

05

EC2 배포 구성과 프록시 경로 심화 읽기

EC2 호스트에 서비스 배치

오늘의 질문은 “서버가 켜졌는가?”에 그치지 않습니다. 73일에 확인한 같은 문서·소유권·인용 결과가 EC2에서도 유지되는지 설명할 수 있어야 합니다. API를 새로 만들거나 도서관 검색 실험을 배포 앱으로 바꾸지 않습니다.

첫 15분에 73일 examples/service/provided/service-comparison.json과 같은 서비스의 소비 계약, 72일 앱/DB 구성, 70일 전체 A1 저장 규칙을 찾습니다. 자기 기록이 없으면 제공 예제를 읽은 상태로 적습니다. 이미지 digest와 실제 볼륨을 아직 측정하지 않았으면 빈칸으로 둡니다.

로컬·EC2·컨테이너의 경계

EC2는 AWS에서 실행하는 원격 컴퓨터입니다. AMI는 컴퓨터를 시작할 운영체제 이미지이고, 인스턴스 유형은 CPU·메모리 구성을 정합니다. Docker 이미지는 그 컴퓨터 안에서 앱을 실행하기 위한 묶음입니다. AMI와 앱 이미지는 서로 다른 계층입니다.

리전은 자원이 놓이는 지역, 가용 영역은 리전 안의 구분입니다. 강사가 정한 리전·서브넷·접속 경로를 사용합니다. 지금 자원 값이나 무료 사용 조건은 확인하지 않았으므로 예시 이름을 실제 선택값으로 채우지 않습니다.

클라우드 자원과 비용 책임

비용 계획은 인스턴스 유형 하나만 적는 표가 아닙니다. 실행 시간 외에 디스크·스냅샷·주소·전송·도메인 등 선택한 자원을 함께 봅니다. 강사가 실제 견적의 확인 시각과 근거를 기록하고 종료 시각·정리 담당자를 정합니다. 이 책에는 현재 가격이나 무료 사용을 보장하는 숫자가 없습니다.

예산 알림은 사용량을 살펴보는 신호입니다. 알림을 만들었다고 모든 지출이 즉시 멈추는 것은 아닙니다. 합성 계획의 예산 1은 코드가 양의 유한 숫자를 구별하는지 확인하기 위한 허구 값이며 견적이 아닙니다.

IAM은 AWS에서 어떤 작업을 할 수 있는지 정합니다. 앱의 Alice/Bob 사용자나 대화 소유권은 별도의 H1/B1 경계입니다. IAM 역할이 있다고 다른 사용자의 문서를 읽을 수 있게 만드는 것은 아닙니다.

공개 포트와 접속원

IP 주소는 접속 위치를, 포트는 그 위치에서 사용할 프로그램 경로를 구분합니다. SSH의 22번, HTTPS의 443번, PostgreSQL 내부의 5432번을 각각 어느 구간에서 쓰는지 표시합니다. 보안그룹이 허용해도 프로세스·라우팅·DNS가 준비되지 않으면 접속이 되지 않을 수 있습니다.

기본 경로는 강사가 준비한 Session Manager 또는 한 승인 접속원의 SSH입니다. Session Manager에는 에이전트·역할·연결 준비가 필요합니다. SSH를 쓰면 승인한 /32 또는 /128만 계획합니다. 연결된 보안그룹 전체의 허용 규칙을 확인해야 하며 좁은 규칙 하나가 넓은 규칙을 취소하지는 않습니다.

배포 선언 정적 검사의 범위

examples/cloud/check_inputs.py는 JSON 선언을 읽는 표준 라이브러리 도구입니다. 참조 문자열이 가리키는 AWS·파일·이미지·예산을 열지 않습니다. 필드와 위험한 조합을 거부할 수 있지만 실제 환경이 안전하거나 배포 가능하다는 증거는 만들지 않습니다.

이 장 폴더에서 다음 명령을 시작합니다. 이미 examples/cloud에 있다면 cd를 반복하지 않습니다. 빈 학생 입력은 아직 강사 값이 없으므로 exit 2가 예상됩니다. 합성 계획의 exit 0도 live_deployment_ready=false입니다.

OS와 이미지 플랫폼 호환성

Docker 설치 방법은 운영체제와 버전에 따라 다릅니다. 강사는 선택한 OS·아키텍처의 공식 설치 경로를 확인해 설치표를 제공합니다. 학생은 설치 명령을 어느 컴퓨터에서 실행하는지 표시하고 정상/실패 근거를 남깁니다. 운영체제를 정하지 않은 상태에서 임의의 설치 스크립트를 실행하지 않습니다.

linux/amd64와 linux/arm64는 다른 CPU 플랫폼입니다. 파일 이름이나 태그가 같아도 플랫폼이 맞지 않으면 실행되지 않을 수 있습니다. 앱/DB 이미지의 확인된 digest와 플랫폼을 함께 기록합니다. 실제 이미지가 만들어지지 않았으면 해시 모양의 문자열을 지어내지 않습니다.

배포 입력의 판본 고정

앱 내용은 73일 최종 서비스 소비 사본을 그대로 사용합니다. 70일의 업로드·소유 대화·이력·스트림·전체 A1 저장에 73일의 검색 저장소 변경이 더해진 경로입니다. 별도 도서관 비교 실험을 이 배포 앱의 자료로 복사하지 않습니다.

배포 구성은 같은 B1 프로젝트와 데이터 관계를 유지하면서 외부 게시 포트를 제한합니다. 72일 로컬 포트가 override에 빈 배열을 적는 것만으로 사라진다고 가정하지 않습니다. 제공 클라우드 구성은 독립된 전체 파일이며 이전 로컬 포트 구성을 함께 합성하지 않습니다. 최종 Compose 해석과 실제 네트워크는 강사가 후속 확인합니다.

새 호스트의 볼륨 데이터

course-b1이라는 프로젝트와 course-data라는 키는 구성의 이름입니다. 새 EC2에 같은 이름을 적어도 로컬 Docker 볼륨이 옮겨지지는 않습니다. 새 빈 DB가 정상 시작된 것을 이전 문서·이력 보존으로 기록하면 안 됩니다.

원본 자료를 보존한 채 강사가 검증한 백업/전송/별도 대상 복구를 준비합니다. 문서·대화·turn·owner, 전체 A1 출처와 73의 원문/청크/벡터 매핑을 대조해야 합니다. 74일에는 그 인계 근거를 읽고 75일에 별도 복구 계획을 자세히 확인합니다.

동일 요청의 배포 전후 검사

배포 전후에는 같은 질문·k·문서 범위·신뢰 문맥·자료 버전을 사용합니다. HTTP 상태만 비교하지 말고 run_status, 전체 result.sources, metadata와 persistence도 확인합니다. 정상 빈 근거를 실행 실패로 합치거나 저장 실패 행을 빼면 비교 조건이 달라집니다.

/health는 프로그램이 응답하는지 살펴보는 작은 확인입니다. 그 결과만으로 DB, 소유권, 문서 준비, 검색과 저장이 모두 동작했다고 말할 수 없습니다. 강사가 실제 환경을 준비한 뒤 같은 API 사례를 수행하고 원문 결과는 승인된 증거 폴더에 남깁니다.

접속 실패에는 주소/DNS, 라우팅·보안그룹, 호스트, 컨테이너, 앱, DB처럼 여러 위치가 있습니다. 오류를 없애려고 모든 포트를 공개하거나 자료 볼륨을 지우지 않습니다. 마지막으로 확인된 단계와 다음에 확인할 근거를 한 칸씩 적습니다.

실패 기록의 형식
상황먼저 분리할 것
주소에 연결되지 않음DNS/경로/포트/프로세스
앱 503 저장 오류이미 생성한 답과 DB 저장 효과
컨테이너 반복 종료이미지/환경/시작 명령
DB에는 새 빈 자료만 있음원본 전송·볼륨 식별·복구 근거
자원 중지·종료·데이터 보존

EC2 중지는 다시 시작할 수 있는 상태이고 종료는 인스턴스를 제거하는 동작입니다. 어느 경우에도 디스크·스냅샷·주소 등 다른 자원의 보존과 비용을 따로 확인해야 합니다. EBS의 DeleteOnTermination과 실제 저장 위치가 중요하며, 명명 볼륨이 있다는 사실만으로 그 아래 디스크가 보존되지는 않습니다.
