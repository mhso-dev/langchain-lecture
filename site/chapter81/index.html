CRUD를 요청과 응답으로 나누기

CRUD는 만들기(Create), 읽기(Read), 수정하기(Update), 삭제하기(Delete)를 묶어 부르는 말입니다. HTTP 메서드는 서버에 어떤 작업을 요청하는지, 경로는 어떤 자원을 대상으로 하는지 나타냅니다. POST /todos는 새 항목을 만들고 PATCH /todos/1은 ID 1의 일부 필드를 바꿉니다.

클라이언트는 새 ID를 정하지 않습니다. title만 보내면 서버가 ID와 completed=false를 정해 반환합니다. JSON은 전송할 값의 표현이고, Python dict나 JavaScript 객체는 프로그램 안의 값입니다. JSON의 true는 Python에서 True가 되지만 문자열 "true"는 문자열로 남습니다.

응답에는 data, error, storage가 있습니다. 정상 목록 []는 항목이 없다는 성공 결과이고, data=null과 오류 코드는 실패입니다. 상태 코드만 보고 빈 목록으로 바꾸면 서버 고장을 할 일 0개로 보여 주게 됩니다.

언어가 값을 편하게 바꿔 주는 기능은 API 경계에서 뜻을 바꿀 수 있습니다. Python의 bool은 int와 관련된 타입이므로 단순 isinstance(True, int)만으로 ID를 검사하면 True가 통과할 수 있습니다. 제공 코드는 type(value) is int로 검사하고 1부터 2147483647까지 허용합니다. completed에는 실제 bool만 허용합니다.

제목은 문자열인지 확인한 뒤 T1에 고정한 공백 문자 25개를 양끝에서 제거합니다. 중간 공백·대소문자는 그대로 두며 제거 후 빈 제목은 거부합니다. Python의 기본 strip과 JavaScript trim이 항상 같은 문자 집합이라는 가정을 하지 않습니다. 문자 표를 외우는 대신 같은 입력에서 결과가 같은지 확인합니다.

PATCH에 title과 completed를 함께 보냈다면 두 필드가 모두 유효해야 합니다. 제목부터 저장하고 나중에 잘못된 completed를 발견하면 실패 응답인데 제목은 바뀐 상태가 됩니다. 먼저 전체 patch를 검증한 다음 저장소를 바꾸는 순서를 읽어 보세요.

오류를 숨기지 않는 API 경계

경계 함수 dispatch는 요청한 작업을 저장소 메서드에 연결하고 외피를 만듭니다. 저장소 결과도 다시 검증하므로 반환값에 completed="false"가 섞이면 성공으로 포장하지 않습니다. 형식 검사와 업무 처리를 분리해 두면 HTTP 서버가 없어도 같은 입력을 함수로 점검할 수 있습니다.

오류 코드는 원인을 구분하는 이름입니다. MALFORMED_JSON은 JSON을 읽는 단계, REQUEST_SHAPE는 본문 키의 모양, NOT_FOUND는 요청한 ID의 부재를 나타냅니다. JSON 문법 오류와 유효한 JSON 안의 빈 제목은 다른 문제입니다. 중복 키도 어느 값을 믿을지 모호하므로 거부합니다.

서버의 원시 예외 메시지를 응답에 그대로 넣지 않습니다. 내부 경로나 설정이 포함될 수 있고 클라이언트가 그 문장을 계약으로 삼기 어렵습니다. 예상 밖 오류는 INTERNAL_ERROR로 구분하고 정상 []로 바꾸지 않습니다. 상세 원인 분석과 사용자에게 보일 상태는 별도로 기록합니다.

Codex에 작은 API 변경을 요청하기

요청은 “투두 앱을 완성해 줘”보다 입력·기대·바꾸지 않을 규칙을 포함할 때 검토하기 쉽습니다. 오늘의 첫 변경은 서버 메모리 CRUD와 제목 수정입니다. 80일차의 ID·완료·공백 규칙을 적고, 파일 역할과 검증 계획을 먼저 설명하게 합니다. 제공 참조 앱은 비교 자료이며 실제 Codex가 만든 결과로 부르지 않습니다.

학생 작업 사본에는 기존 파일과 현재 동작을 남깁니다. 한 번에 인증·DB·배포까지 넣지 않습니다. 먼저 요청 검증과 메모리 동작을 확인하고 다음 단계에서 화면을 연결하면, 어느 변경 때문에 실패했는지 좁히기 쉽습니다.

Codex를 사용할 수 없으면 같은 요구를 문서로 작성하고 제공 코드에서 해당 조건을 구현한 줄을 찾습니다. 이 분석은 유용한 대체 활동이지만 실제 도구로 구현하고 확인한 수행과 같지는 않습니다. 실제 응답·수정 파일·명령은 자신이 확인했을 때만 양식에 적습니다.

메모리 앱과 실제 HTTP 진입점 읽기

MemoryRepository는 한 앱 인스턴스 안에서 항목과 다음 ID를 보관합니다. 같은 제목 두 항목도 ID로 구분하고, 삭제한 번호를 당장 재사용하지 않습니다. 새 저장소 객체를 만들면 빈 상태가 됩니다. 아래 시연은 Python 객체 생성 결과이며 운영체제에서 서버를 재시작한 기록이 아닙니다.

app.py의 create_app은 저장소를 한 번 만들고 HTTP 경로에 연결합니다. request의 bytes를 읽어 JSON으로 해석한 뒤 dispatch를 호출합니다. JSONResponse를 직접 반환하므로 자동 응답 모델이 모든 값을 검사한다고 가정하지 말고 저장소·dispatch의 검증을 따라갑니다.

수업 환경에 FastAPI와 Uvicorn이 준비돼 있다면 examples에서 아래 진입 명령을 사용합니다. 브라우저는 같은 서버의 루트 주소를 열어야 합니다. web/index.html을 파일로 직접 열면 /static과 /todos는 같은 서버를 가리키지 않습니다. 환경이 없으면 함수 시연과 진입점 읽기를 수행하고 실제 HTTP는 미확인으로 남깁니다.

화면의 상태는 언제 확정되는가

화면은 입력하자마자 저장이 끝났다고 가정하지 않습니다. controller는 쓰기 요청을 보낸 뒤 목록을 다시 읽고, 유효한 목록 응답을 받았을 때만 rows를 바꿉니다. busy는 요청 진행 중, stale은 현재 목록을 최신이라고 확정할 수 없다는 뜻입니다.

버튼을 누를 수 없게 만드는 UI와 서버의 동시성 보장은 다릅니다. 이 제어기는 같은 화면 안의 중복 조작을 줄이지만 다른 탭·다른 프로세스·끊어진 네트워크 전체에서 정확히 한 번만 쓰게 하는 장치는 아닙니다. 한 앱 인스턴스의 수업 범위를 지킵니다.

클라이언트도 요청별 응답 형태를 검사합니다. GET 목록에 단일 객체가 오면 for...of로 목록을 그릴 수 없습니다. 배열인지 먼저 확인하고 오류면 이전 목록을 보존합니다. 아래 fetch는 작성한 대역이며 실제 서버를 호출하지 않습니다.

제목·완료·삭제를 같은 ID에 연결하기

제목 수정은 레코드를 새로 만드는 동작이 아닙니다. 관찰한 ID를 경로로 보내고 title만 바꾸면 completed는 유지됩니다. 완료 체크는 현재 값을 뒤집으라는 명령 대신 원하는 true 또는 false를 보냅니다. 이미 true인 항목에 true를 다시 보내도 true입니다.

browser.mjs는 목록의 item.id를 저장·삭제 이벤트에 연결합니다. 화면의 순번이나 제목을 ID로 대신하면 정렬이나 중복 제목에서 다른 항목을 바꿀 수 있습니다. textContent로 제목을 표시하는 줄은 입력 문자열을 HTML 구조로 해석하지 않게 합니다. 이 코드 읽기와 실제 화면의 키보드 동작 관찰은 구분합니다.

학생은 자신의 작업 사본에서 제목 편집 입력과 저장 버튼을 연결합니다. 저장 성공 뒤 목록을 다시 읽고 ID·제목·완료가 기대대로인지 대조합니다. 이미 제공 참조를 분석하는 경로라면 동작을 새로 구현했다고 적지 말고 연결한 함수와 확인 질문을 기록합니다.

네트워크 오류는 서버가 요청을 받지 않았다는 증거가 아닙니다. 삭제가 처리된 뒤 응답만 끊겼을 수도 있습니다. 같은 작업을 자동으로 다시 보내면 추가가 두 번 일어나거나 이미 삭제된 항목을 재삭제할 수 있습니다. 먼저 재조회로 현재 상태를 확인합니다.

쓰기 성공 뒤 이어지는 목록 조회만 실패해도 화면에는 이전 목록이 남습니다. 이때 stale=true로 표시하고 변경을 막습니다. 마지막 확인 목록은 문제를 살피는 자료이며 현재 서버 상태의 확정값이 아닙니다. 오류를 지우고 빈 목록으로 대체하면 이 구분이 사라집니다.

아래 대역은 remove 호출을 한 번 실패시키고 두 번째 변경을 막는 흐름만 보여 줍니다. 실제 서버에서 삭제가 되었는지는 알 수 없습니다. 재조회 후 같은 ID의 존재 여부와 원래 요청을 함께 대조하는 절차를 학생 기록에 남깁니다.

같은 사례로 회귀를 확인하기

회귀는 새 기능을 붙이면서 기존 약속이 깨지는 일입니다. 제목 수정이 생겼다고 공백 제목을 허용하거나 완료 타입을 문자열로 바꾸면 안 됩니다. TC80의 사례를 A81 API 사례로 이어서 비교하고 새 제목 수정·응답 형태 사례를 추가합니다.

로컬 검사는 함수와 대역의 동작을 빠르게 확인합니다. 19개 Python 검사와 11개 Node 제어기 검사는 실제 HTTP 경로·브라우저 DOM 검사가 아닙니다. 검사 수를 학생 점수로 삼지 말고 각 목표에 필요한 입력·관찰·설명 근거를 확인합니다.

테스트 명령이 통과하더라도 현재 작업 파일을 실행했는지 먼저 확인합니다. 다른 폴더의 옛 파일을 실행했다면 현재 diff를 검증한 것이 아닙니다. 실패한 행과 미실행한 행도 남겨 다음 검토자가 같은 조건을 재현할 수 있게 합니다.

diff를 읽고 수정 요청·커밋 기록 남기기

diff는 변경 전후 줄을 보여 줍니다. 파일 이름만 확인하지 말고 입력 검증, 상태 갱신, 오류 반환 중 어느 책임이 달라졌는지 설명합니다. 도구가 많은 파일을 바꿨다면 이번 요구와 관계없는 변경을 따로 표시하고 이유를 물어봅니다.

수정 요청에는 재현 순서·실제 결과·기대·관련 파일을 넣습니다. “안 돼요”만 쓰면 어떤 상태인지 알 수 없습니다. 예를 들어 목록에 단일 객체가 왔을 때 stale이 false가 된다는 관찰과, 기존 목록을 보존하고 오류로 표시해야 한다는 기대를 나눕니다. 제공 참조가 이미 그 경계를 처리하면 결함을 고쳤다고 기록하지 않습니다.

커밋은 자기 저장소에서 변경을 검토한 후 관련 파일만 기록한 경우에 남깁니다. 제공 예제의 해시는 파일 식별자이지 자신의 커밋 ID가 아닙니다. 실제 Codex 응답과 커밋이 없다면 빈 칸 또는 미실행을 유지합니다.

82일차에 무엇을 넘길까

다음 장은 같은 API와 화면 규칙을 유지하면서 저장소를 PostgreSQL로 바꿉니다. 오늘의 서버 메모리 상태를 DB에 자동 이전하는 기능은 만들지 않았습니다. 같은 T1 계약·사례·현재 코드·실제 미확인 목록을 넘깁니다.

O81-1은 요청·정상/오류를 설명하는 표, O81-2는 CRUD·제목 수정의 코드와 실제 관찰 또는 미확인, O81-3은 diff·회귀·인계 기록으로 확인합니다. 목표별로 근거충족·수정필요·미확인을 판정하며 임의의 합격 점수를 두지 않습니다.
