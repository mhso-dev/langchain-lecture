05

관련 개념 더 읽기

모델이 도구를 요청한 뒤 어디로 갈까요?

조건 함수 after_model은 다음 노드 이름만 반환합니다. 먼저 오류가 있으면 끝냅니다. 요청이 없으면 answer로 갑니다. 요청이 있고 이미 허용한 도구 회차를 채웠으면 limit로 갑니다. 나머지는 tool입니다. 조건 함수에서 검색을 실행하면 실제 도구 노드와 겹쳐 호출 수가 늘 수 있습니다.

조건 순서는 의미가 있습니다. 이미 두 번 검색했어도 모델이 더 요청하지 않고 마치면 답변으로 갈 수 있습니다. 상한은 새로운 도구 요청을 막는 규칙이므로 요청 유무를 먼저 봅니다.

조건 함수가 반환한 문자열은 오른쪽 연결 표의 키여야 합니다. tool을 반환하면 tool 노드로 가고, 오류 뒤 end를 반환하면 END로 갑니다. 도구가 정상 실행되면 model로 돌아가므로 같은 판단→도구 구조를 반복할 수 있습니다.

확장 예제에서는 답을 어느 노드에서 쓸까요?

‘대출 기간은?’을 keywords 정책으로 실행하면 첫 판단이 검색을 요청합니다. 도구가 library-1을 돌려주면 두 번째 판단은 요청을 비워 마칩니다. answer가 A1을 실행해 인용 답변을 만듭니다. 같은 그래프라도 주차 질문처럼 요청이 없으면 tool 노드를 거치지 않습니다.

참고 구현의 정상 왕복과 마지막 answer 노드

학생 셀의 기본 경로는 모델 → 도구 → 모델에서 끝납니다. 이 참고 구현에서는 도구 요청이 끝나면 answer 노드로 가서 인용까지 확인합니다.

상태에 질문·근거·메시지·횟수 보관하기

State는 노드 사이에 전달하는 값의 이름과 구조를 모읍니다. question과 k는 비교할 입력입니다. documents는 가장 최근 검색 결과이고 result는 A1의 최종 응답입니다. messages는 질문·요청·결과 메시지의 순서입니다. trace는 어떤 노드가 실행됐는지 읽기 위한 기록입니다.

이 예제는 messages와 trace에 별도 reducer를 두지 않습니다. 각 노드가 이전 목록에 새 항목을 붙인 전체 목록을 반환합니다. messages=[새 메시지]만 반환하면 기존 질문과 도구 결과가 없어집니다. 27–28일의 ‘어떤 상태 키를 갱신하는가’를 다시 적용해 보세요.

모델·도구·응답 노드의 일 나누기

model 노드는 messages를 판단 함수에 보내고 AIMessage를 붙입니다. tool 노드는 그 요청의 인자를 검사하고 검색한 뒤 ToolMessage를 붙입니다. answer 노드는 추가 요청이 없을 때 A1로 최종 답변을 만듭니다. 판단과 답변을 분리했기 때문에 32일의 생성기와 인용 검사를 그대로 비교할 수 있습니다.

이 장의 모델 노드는 실제 모델 객체를 넣을 수 있는 위치를 보여 주지만 기본 구현은 모의 판단입니다. Tool을 요청하지 않은 AIMessage의 content도 최종 답변으로 쓰지 않습니다. 모든 답변이 같은 A1 규칙을 지나도록 answer 노드가 별도로 있습니다.

Tool은 검색 기능을 모델에 제시하는 인터페이스이고 Node는 그래프에서 실행할 처리 단계입니다. 도구를 실제로 실행하는 tool 노드도 노드입니다. 따라서 Node와 Tool을 서로 대체하는 같은 종류의 객체로 외우기보다, 검색이 언제 실행되도록 연결했는지 비교합니다.

반복 요청을 상한에서 멈추기

repeat 정책은 ToolMessage를 받은 뒤에도 같은 검색을 요청합니다. 검색 결과가 있어도 무조건 반복하는 실패를 재현합니다. 기본 max_tool_rounds=2는 도구 노드를 두 번까지 허용하고, 세 번째 요청은 검색 전에 limit로 보냅니다.

상한을 확인하려면 요청이 도착해야 하므로 판단은 세 번입니다. 실제 검색은 두 번이고, 상한에 걸린 흐름은 최종 답변을 만들지 않아 생성은 0회입니다. 마지막 ToolMessage는 step_limit 오류를 담은 프로그램의 메시지이며 모델이 생성한 답변이 아닙니다.

LangGraph의 recursion_limit도 실행에 넘기지만 이것은 그래프의 진행 단계를 제한하는 별도 장치입니다. 도구 호출 수와 같은 숫자로 읽지 않습니다. 예제는 명시적인 tool_rounds 정책으로 먼저 종료하고, 프레임워크 제한은 실수로 루프가 이어질 때를 위한 추가 방어로 둡니다.

상한 종료 뒤 documents에 이전 검색 결과가 남아 있어도 result=None입니다. 그 문서는 진단용 기록이며 최종 출처로 표시하지 않습니다. 더 많이 반복했다고 답변 품질이 높아진다고 가정하지 않습니다.

빈 결과·오류·인용 실패를 다른 경로로 끝내기

정상 빈 검색 뒤 판단이 마무리하면 answer가 A1을 실행합니다. A1은 근거가 없으므로 생성하지 않고 no_evidence를 돌려줍니다. 검색이 TimeoutError로 실패하면 tool_error로 바로 종료합니다. 오류를 받은 뒤 다시 판단하거나 생성하는 비용은 이 예제에서 발생하지 않습니다.

생성기가 출처 없는 문장을 만들었다면 검색·생성은 이미 실행된 상태입니다. A1이 invalid_citation으로 막습니다. 생성 도중 TimeoutError가 나면 생성 시도는 1이고 result=None입니다. 원인이 다른 실패를 하나의 자료 없음으로 합치지 않습니다.

필수 검색 Node와 선택 검색 Tool의 차이

필수 검색 흐름은 START에서 search로 들어가고 검색 후 answer로 이어집니다. 정상 입력이면 질문 종류와 관계없이 검색을 한 번 시도합니다. 선택 검색 흐름은 model이 요청한 경우에만 tool을 실행합니다. 두 흐름 모두 같은 R1과 A1을 사용합니다.

compare.py의 run_node는 30–32일 구조를 다시 연결하고 호출 수와 오류 기록을 추가한 제공 기준입니다. 원래 검색을 다른 검색 알고리즘으로 바꾸지 않습니다. 비교 중 검색 함수나 생성기를 한쪽만 바꾸면 흐름 차이를 설명하는 실험이 되지 않습니다.

Tool 실행도 그래프의 노드 안에서 일어납니다. 이 비교의 Node/Tool이라는 줄임말은 ‘필수 검색 노드로 둔 흐름’과 ‘선택 가능한 검색 도구로 둔 흐름’을 뜻합니다. 어느 API가 무조건 더 낫다는 분류가 아닙니다.

같은 질문으로 호출 수와 최종 결과 비교하기

개발 질문 세 개는 data/questions.json의 development에서 읽습니다. question_id를 보존하고 case_id에 정책을 붙여 같은 질문의 여러 실험을 구분합니다. dev-01의 질문은 ‘대출 기간은 며칠인가요?’이며 다른 표현으로 바꾸지 않습니다.

각 질문에서 Node와 Tool의 판단·검색·생성 횟수를 따로 기록합니다. 주차 질문은 Tool이 검색을 생략해도 Node와 같은 no_evidence를 냅니다. 그러나 검색 한 번을 줄이기 위해 판단 한 번이 추가됐습니다. 실제 모델이라면 그 판단의 시간·비용도 측정해야 하지만 여기서는 API를 실행하지 않았습니다.

expected_document_ids는 원문 문서 ID이고 documents의 id는 검색 청크 ID입니다. 지금은 페이지당 청크가 하나라 같은 값이지만 source-map.json으로 대응을 확인합니다. 근거 없는 질문의 예상 문서 ID는 빈 목록입니다. 이 작은 공개 질문 묶음을 실모델의 일반 성능 평가로 설명하지 않습니다.

comparison-results.json의 result.sources는 실제 인용이고 documents는 검색 결과입니다. same_result는 A1 result만 비교합니다. 오류인 두 결과가 모두 None일 수도 있으므로 error_type·stop_reason도 함께 봐야 합니다. CSV는 이 필드를 보존하는 요약이며 원문 근거와 메시지는 JSON에서 확인합니다.

검색을 줄여도 답을 놓칠 수 있다

skip 정책은 어떤 질문에서도 도구를 요청하지 않게 만든 실패 비교입니다. 같은 dev-01 대출 질문을 넣으면 Node는 답하지만 Tool은 no_evidence가 됩니다. 검색 1회를 아꼈다는 사실만 보고 개선이라고 말하면 답할 수 있는 질문을 놓친 결과를 숨기게 됩니다.

repeat 정책은 같은 질문을 다시 검색하다 상한에 걸립니다. 검색 횟수는 Node의 1회보다 많은 2회이고 최종 답변도 없습니다. 이 두 예시는 선택 기능을 만들었을 때 검증할 실패를 드러내기 위한 고정 사례입니다. 실제 모델의 선택 정확도를 측정한 결과가 아닙니다.

원인이 불분명할 때 상한을 크게 올리거나 오류를 모두 []로 바꾸지 않습니다. trace의 마지막 노드와 상태를 보고, 정해 둔 조건과 실제 값의 차이를 찾습니다. 의도적으로 바꾼 코드와 관찰 결과를 같이 남겨야 다른 사람이 같은 문제를 재현할 수 있습니다.

다음 비교 학습에 넘길 원본과 요약

comparison-results.json은 실행 근거의 원본입니다. 각 case_id의 질문·정책·mode·공통 스냅샷과 두 경로의 문서·응답·호출 수를 담습니다. node-tool-comparison.csv는 질문과 경로별 상태를 빠르게 비교하는 요약입니다. 두 파일과 학생 분기 함수, observation.md를 함께 보관합니다.

다음 장에서는 같은 입력을 유지한 채 검색 결과와 답변을 더 체계적으로 점검합니다. 오늘의 small fixture 성공을 일반 품질 점수로 바꾸지 않고, 원문 문서와 청크 관계, 근거 없는 질문, 공개된 확인 문항의 범위를 계속 구분합니다. 실제 LLM·Chroma를 아직 실행하지 않았다면 인계 기록에도 그대로 표시합니다.

공식 자료와 다음 학습

이 원고는 설치된 LangChain·LangGraph와 가상 자료로 실행했습니다. 검색 선택은 코드로 정한 모의 판단이고 답변은 고정 생성기입니다. 실제 LLM의 도구 선택·Chroma 통합·Windows/WSL·최종 화면은 별도 확인 대상입니다. 생성한 결과가 실제 모델 성능이나 검색 품질을 증명하지 않습니다.
