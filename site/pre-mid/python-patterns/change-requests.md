# 야간 분실물 센터 · 인수인계 변경 요청

이전 센터의 예제는 두고, 새 노트북에서 아래 접수표와 다섯 요구를 재현합니다. 매번 예제에 있는 이름이나 접수 순서가 바뀌어도 약속을 지키는지 확인하세요. 담당자가 기대값을 먼저 적고 구현자가 작업한 뒤 다음 요청에서는 역할을 바꿉니다.

| 접수 순서 | 물건 | 구역 |
| --- | --- | --- |
| 1 | 지갑 | 동문 |
| 2 | 카드 | 서문 |
| 3 | 키 | 동문 |
| 4 | 우산 | 서문 |
| 5 | 장갑 | 동문 |

## 1장 · 정렬 기준을 담당자가 바꾸는 요청

직원은 접수순 원장을 보며 전화를 받습니다. 야간 게시판에는 짧은 이름이 먼저 보이고, 다른 화면은 구역별로 묶습니다. 이름 길이와 구역을 읽는 두 함수를 각각 써서 같은 조회 함수로 넘기세요. 결과 목록을 비교하는 테스트에 ‘원본 순서 유지’ 조건도 넣으세요. 추가 접수로 ‘표’ 한 건이 마지막에 들어오면 ‘키’와의 순서를 새로 예측합니다.

<details><summary>야간 근무자의 확인 결과</summary><p>길이순의 첫 이름은 키입니다. 표가 추가된 뒤에는 키 다음이 표입니다. 구역순 조회에서 동문 세 건은 지갑, 키, 장갑 순서입니다. 한 화면의 조회가 원장을 제자리에서 정렬했다면 두 번째 화면에 영향을 줄 수 있습니다.</p></details>

## 2장 · 당일 화면과 오전 마감표

오전에는 ‘카드’가 우선 물건이었고, 오후에 ‘지갑’을 추가합니다. 실시간 화면과 오전 마감표 모두 같은 원장을 쓰되, 직원이 오후 목록을 바꿔도 오전 마감표의 첫 물건은 카드로 유지되어야 합니다. 우선 물건끼리는 원장 접수순을 유지합니다. 오후 목록을 비운 뒤 실시간 화면과 오전 마감표도 다시 읽으세요.

<details><summary>현장 인계 결과</summary><p>오전은 추가 전후 모두 카드가 먼저입니다. 현재 화면은 추가 뒤 지갑, 카드 순서로 시작하고 목록을 비우면 원래 접수 순서가 됩니다. 현재 화면까지 복사본을 쓰면 오후 직원이 원래 목록에 추가한 내용이 반영되지 않습니다. 반대로 오전까지 같은 목록을 공유하면 마감표가 달라집니다.</p></details>

## 3장 · 형식을 고르는 코드와 출력하는 코드

새 형식 locker는 ‘보관 / 카드’를 출력합니다. 나머지 형식과 공개 함수의 호출 방법은 유지하세요. 기존 콜센터는 plain으로 ‘키’를 쓰고, 팀원이 실수로 lockre를 입력합니다. 새 형식, 기존 형식, 오타 입력을 같은 게시 함수로 검수하세요. 팀원은 형식을 고르는 곳과 문자열을 완성하는 곳을 각각 한 줄씩 짚습니다.

<details><summary>승인할 세 동작</summary><p>locker의 카드는 ‘보관 / 카드’, plain의 키는 ‘키’입니다. lockre는 미지원 형식이어서 수정 요청을 받아야 합니다. 새 객체의 render에 다른 형식의 분기를 다시 넣으면 형식 선택 책임이 두 곳으로 늘어납니다.</p></details>

## 4장 · 성공 기록만 남기는 두 종류의 데스크

동문 데스크는 접수 원문을, 서문 데스크는 화면에 사용한 이름을 성공 기록으로 보관합니다. 공백만 받은 요청은 두 곳 모두 거절합니다. 두 데스크에 차례로 ‘ 카드 ’와 공백 한 칸을 보내고 동문에만 ‘키’를 추가하세요. 두 화면의 성공 응답과 기록을 비교합니다. 실패 입력이 기록에 남았다면 렌더링 호출 앞뒤 중 어느 곳에서 기록하는지 추적하세요.

<details><summary>동문·서문 대조 메모</summary><p>양쪽의 첫 화면은 [카드]입니다. 동문 기록은 원래 공백이 있는 ‘ 카드 ’와 ‘키’, 서문 기록은 ‘카드’ 한 건입니다. 공백 한 칸은 두 성공 기록에 모두 없어야 합니다. 두 화면만 확인하면 기록 순서의 오류를 놓칠 수 있습니다.</p></details>

## 5장 · 다음 변경을 누가 유지할지 결정하기

센터장이 다음 달부터 “구역별로 접두 문구를 바꾸되 근무 교대 때 복원”해 달라고 했습니다. 동문과 서문이 연속으로 서로 다른 문구를 설정한 뒤 동문의 문구가 보존되는 예를 작성하세요. 하나의 전역 문자열을 바꿨을 때 생기는 문제를 두 번째 호출로 재현합니다. 해결안은 함수 인자로 설정을 전달하거나 설정을 가진 객체를 둘 만들 수 있습니다. 두 방식에 같은 입력 세 건을 넣고 팀이 유지할 구현 하나를 고르세요. 리뷰에는 수정할 때 찾아갈 함수, 학교 예제와 다른 실제 입력, 다음 사람이 한 번에 실행할 노트북 경로를 남깁니다.

<details><summary>두 구현의 모범 판단</summary><p>동문이 ‘동문 안내’, 서문이 ‘서문 안내’일 때 카드·키·우산을 동문, 서문, 동문 순서로 게시하면 마지막에도 ‘동문 안내’가 나와야 합니다. 호출자가 항상 문구를 알고 있고 작업이 한 번뿐이면 인자가 간결합니다. 같은 데스크 설정으로 여러 번 게시하고 교대 시 복원한다면 설정을 담은 객체를 보관하는 쪽이 호출에서 빠뜨릴 값이 적어집니다. 두 구조에 같은 성공·거절 입력을 걸고 결정하세요.</p></details>
