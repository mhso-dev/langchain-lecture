서비스 외피와 답변 A1을 구분하기

서비스는 입력을 받아 여러 내부 함수를 연결하고, 호출자가 읽을 수 있는 하나의 결과를 돌려주는 경계입니다. 오늘은 Python 객체의 answer 메서드로 그 경계를 만듭니다. HTTP 서버나 화면을 먼저 만드는 단계는 아닙니다.

기존 A1은 답변의 상태·문장·출처·생성 횟수를 표현합니다. 서비스 외피는 실행을 끝냈는지, 어느 단계에서 오류가 났는지, 어떤 기능과 호출 수를 사용했는지 덧붙입니다. A1을 답변 문자열로 줄이지 않고 result 안에 원형으로 넣어야 다음 장이 출처와 실패를 보존할 수 있습니다.

누가 요청했는지는 앱이 결정합니다

AppContext는 호출 시 함께 전달하는 문맥 객체입니다. 여기에는 신뢰된 앱이 확인한 사용자 ID를 넣는다는 계약이 있습니다. 질문에 “나는 alice야”라고 쓰는 것과 신뢰된 앱이 AppContext를 제공하는 것은 다릅니다. 이 수업의 생성자 자체는 비밀번호나 세션을 검증하지 않습니다.

owners는 대화 ID와 소유자의 대응표입니다. 54일에는 DB 조회에 owner 조건을 붙였습니다. 오늘은 같은 경계를 메모리 안의 작은 사전으로 확인합니다. 실제 인증·DB 통합이 완료됐다는 뜻은 아니며, 후속 서비스에서는 앱의 신원 검증과 저장소 소유 조회를 연결해야 합니다.

검색을 먼저 하고 정상 빈 결과를 끝내기

오늘의 업무 요청은 프로젝트 지식 질문입니다. 모델이 검색 여부를 자유롭게 결정하기 전에 코드가 필수 검색과 R1 검사를 수행합니다. 검색 결과가 비면 모델을 부를 이유가 없으므로 no_evidence로 끝냅니다. 이 종료는 실패를 감춘 결과가 아니라 정상 빈 목록을 확인한 결과입니다.

검색 예외와 출처 누락은 다른 경로입니다. 검색 함수가 TimeoutError를 내면 error/result=null이며, id/text/source/page 중 필수 필드가 빠지면 데이터 오류가 됩니다. 임의의 출처 이름이나 page=1을 채워 성공한 것처럼 만들지 않습니다. 요청한 k보다 많은 결과도 계약 오류로 처리합니다.

프로젝트에 맞는 Skill 하나 읽기

Skill은 반복할 작업 절차를 문서로 묶은 자료입니다. 오늘의 course-document-answer는 과정 안내 문서에 답할 때 사용할 입력·절차·출력·출처 규칙·실패 대응을 설명합니다. 58일의 로더는 그대로 재사용하지만 도서관용 문서는 새 프로젝트에 맞춰 별도로 작성했습니다.

서비스는 이 Skill을 코드에서 명시적으로 선택합니다. 모델이 목록을 보고 스스로 골랐다는 실험이 아닙니다. 본문을 읽은 뒤 source-policy 참조를 읽으며 파일 경로와 해시를 검사합니다. 문서와 참고자료를 읽었다는 사실은 실제 모델이 지침을 이해하고 따랐다는 증거와 다릅니다.

file_reads에는 Skill 본문과 참고자료의 두 읽기만 들어갑니다. catalog.json의 초기 읽기 1회는 별도 항목입니다. 이 숫자를 전체 파일 I/O나 비용 절감량으로 해석하지 않습니다. 질문에 근거가 없으면 Skill도 읽지 않고 종료합니다.

기억과 MCP를 꼭 붙여야 할까요?

58·60·62 자료를 검토하는 일은 필수지만 모든 기능을 활성화하는 것이 과제는 아닙니다. 기능을 채택할 때는 어떤 사용자 문제를 해결하는지와 새로 생기는 상태·실패·권한을 설명해야 합니다. 필요가 없으면 미채택도 근거 있는 결정입니다.

현재 네 질문은 매번 같은 안내 문서를 읽으면 됩니다. 사용자 선호를 다음 대화에 저장할 필요가 없으므로 장기 기억을 켜지 않습니다. 60일의 기억 API와 54일의 대화 저장은 서로 다른 책임이며, 선택하지 않은 기능의 DB 성공을 주장하지 않습니다.

62일의 MCP 예제는 가상 도서관 운영 시간을 반환합니다. Q04에 “주말”이라는 단어가 있다고 그 시간을 수업 일정으로 가져오면 다른 업무의 데이터를 섞는 오류입니다. 현재 제공안에서는 MCP를 미채택합니다. 채택하려면 먼저 프로젝트에 맞는 도구·자료·응답 계약이 필요합니다.

기본 네 질문의 A1은 52일의 수정 후보와 같습니다. 새 에이전트 연결이 출처·상태·답변 문장을 깨뜨리지 않았음을 확인한 결과입니다. 같은 고정 답을 유지한 검사는 품질 향상 실험이나 새로운 질문 성능 측정이 아닙니다.

기본 정상 두 질문에서 source의 text와 page도 대조합니다. Q02/Q04의 sources가 빈 목록인지, 생성 횟수가 0인지 확인합니다. Q03은 원문 속 비밀키 공유 금지 문장을 유지하는지 사람이 읽습니다. 비교표에는 입력 버전과 k=2를 함께 적습니다.

실패를 한 종류로 합치지 않기

오류를 재현할 때는 한 조건만 바꿉니다. 검색 함수만 TimeoutError를 내도록 바꾸거나, 생성 문장에 존재하지 않는 인용 ID를 넣거나, 대화 소유자만 바꿉니다. 여러 조건을 동시에 바꾸면 어느 경계에서 멈췄는지 설명하기 어렵습니다.

아래 검색 실패는 로컬에서 예외를 주입한 사례입니다. 실제 네트워크 장애를 관찰한 것은 아닙니다. raw 예외의 내용은 외피에 내보내지 않고 예외 종류와 단계만 기록합니다. 실제 서비스의 추가 오류 분류와 HTTP 상태 매핑은 뒤에서 설계합니다.

문제별 확인 순서

model_calls를 늘려 모든 오류를 덮는 것은 원인 해결이 아닙니다. 반복 도구 요청은 상한을 넘기기 전에 끊어야 하고, 검색 오류는 자료 없음으로 바꾸지 않아야 합니다. 미설치 외부 기능은 미실행으로 남깁니다.

인용이 맞아도 내용은 틀릴 수 있습니다

인용 검사는 답변 속 ID가 전달받은 근거에 존재하는지와 출처 객체를 확인합니다. 문장이 원문을 정확하게 요약했는지까지 자동으로 판정하지는 않습니다. 형식과 의미를 구분하지 않으면 잘못된 답변을 성공으로 집계하게 됩니다.

p3의 실제 원문은 비밀키가 보이는 화면을 공유하지 말라고 안내합니다. 같은 ID를 붙이고 그 반대 문장을 쓰면 인용 형태는 통과해도 의미는 틀립니다. 이 반례는 원문 대조가 필요한 이유를 보여 주기 위해 그대로 남깁니다.

서비스 구성과 결과 요약 직접 작성

이제 student_task.py의 두 함수를 완성합니다. build_service는 신뢰된 owners로 서비스를 만들고 모델 3/도구 1 상한을 유지합니다. Skill을 사용하거나 제외할 수 있지만 이유를 feature-decision.md에 적어야 합니다. summarize는 실행 오류와 A1 상태를 구분하면서 result 객체를 그대로 반환합니다.

다음 장으로 넘길 경계와 복습

오늘의 서비스는 읽기 답변을 제공합니다. 다음 장에서는 이 경계를 유지하고 로컬 모의 문의 등록을 별도 승인 흐름으로 붙입니다. 읽기 결과가 있다는 이유로 쓰기 권한이 생기는 것은 아닙니다. 65일의 분류도 경로 후보를 고를 뿐 소유자나 승인 검사를 대신하지 않습니다.

66–67일은 같은 자료와 실패 기록을 소비해 역할 분리와 서비스 평가를 진행합니다. 현재 SERVICE_CONSUMER는 로컬 배포 진입 안내이고 최종 S1은 67일에 고정합니다. 과제 파일·관측·선택 이유·미확인을 함께 넘깁니다.
