05

후보 수와 최종 k는 어디에서 쓰일까요?

후보는 첫 검색이 돌려준 검토 대상입니다. candidate_k=2이면 질의 하나에서 최대 두 청크를 받습니다. final_k=1이면 그중 한 청크만 A1으로 넘깁니다. 후보 상한을 늘리면 점수 계산에 쓸 자료가 늘고, 최종 k를 늘리면 답변 생성기에 전달할 문맥이 늘어납니다. 두 값의 역할이 다릅니다.

오늘의 기준선도 두 후보를 받은 뒤 첫 문서 한 개를 사용합니다. 같은 정렬의 앞부분이므로 37일 k=1 결과와 같습니다. 재순위만 비교하려고 후보 수를 모든 방법에서 고정했으며 실제 결과도 대조했습니다. 후보 수와 재순위 방법을 동시에 바꾸지 않습니다.

기본 검색에서 14일 청크는 처음부터 1위입니다. 셀 01은 순위 변화를 보려고 후보 순서만 뒤집은 별도 입력입니다.

Reranking: 후보 안에서 다시 순서를 정하기

재순위는 질문과 각 후보가 얼마나 관련되는지 추가로 비교한 뒤 순서를 정합니다. 학습된 CrossEncoder는 질문과 문서를 함께 입력받아 점수를 계산하는 방식으로 사용할 수 있습니다. 점수의 척도와 비용은 모델마다 다르므로 오늘의 정수 점수와 같은 값으로 해석하지 않습니다.

이 예제의 rule_rerank는 질문과 청크에 함께 있는 대출·휴관·반납 키워드 수를 셉니다. 학습된 모델도, 일반적인 의미 유사도도 아닙니다. 같은 점수에서는 이전 순서를 유지합니다. 간단한 규칙 덕분에 어떤 후보가 왜 앞에 왔는지 손으로 재계산할 수 있습니다.

검증할 원본도 같은 객체를 가리키면 정렬 함수의 제자리 변경을 놓칠 수 있습니다. checked_rerank는 deepcopy로 비교용 원본과 작업 사본을 따로 만들고 작업 사본만 콜백에 전달합니다. deepcopy는 이 파일 맨 위에서 copy 모듈로부터 가져옵니다. 제자리 reverse처럼 순서만 바꾸는 함수도 사용할 수 있고 호출자 입력은 보존됩니다.

MultiQuery: 질문 표현을 여러 개로 만들어 검색하기

같은 의도를 다른 표현으로 말하면 첫 검색에서 놓친 근거가 후보에 들어올 수 있습니다. MultiQuery는 원질의에서 여러 검색 질의를 만들고 각각 검색한 결과를 모읍니다. 실제 LLM을 쓰는 구성에서는 질의 생성 자체에도 시간·토큰·실패 가능성이 있습니다.

오늘의 fixed_expansion은 사전에 적은 짧은 문구를 반환합니다. 대출 질문에는 대출 기간을 더하고, 휴관 질문에는 휴관 요일을 더합니다. 원질의도 보존합니다. 생성된 질의가 항상 원래 의도를 유지한다고 가정하지 말고 사람이 읽어 확인해야 합니다.

검색 결과는 문장 내용이 같다는 이유로 합치지 않습니다. 서로 다른 원문 페이지가 같은 문장을 포함할 수 있기 때문입니다. 청크 ID를 기준으로 합치되 같은 ID의 본문·출처·페이지가 다르면 자료 충돌로 처리합니다. 원문 ID가 같은 서로 다른 청크를 하나로 합치면 필요한 문장을 잃을 수 있습니다.

후보가 늘어도 최종 답변은 같을 수 있다

여러 질의가 같은 문서를 찾으면 합집합의 크기는 검색 횟수만큼 늘지 않습니다. 새 문서가 뒤에 추가되더라도 최종 k=1에서 잘리면 A1이 읽는 근거는 바뀌지 않습니다. 후보 확대와 최종 선택은 따로 관찰해야 합니다.

이 실습은 원질의에서 먼저 나온 청크의 순서를 유지하는 단순 병합을 씁니다. 서로 다른 질의의 점수를 바로 더하지 않고, 재순위를 함께 적용하지도 않습니다. 두 기술을 묶으면 어떤 변경이 결과를 바꿨는지 오늘의 비교로는 설명하기 어렵습니다.

확장·검색·재순위 실패를 기록하기

확장 호출이 실패하면 검색은 아직 시작하지 않았습니다. 두 번째 검색이 실패하면 첫 번째 검색 결과가 기록에 남아 있을 수 있지만 전체 정책의 성공으로 내보내지는 않습니다. 이 예제는 해당 질문의 result를 None으로 남기고 시도 횟수를 기록합니다. 실제 서비스에서 부분 결과를 허용한다면 별도 정책과 화면 표시가 필요합니다.

failure_stage는 앞선 metrics.py의 공통 분류이고 optimization_failure_stage는 확장/검색/재순위 중 어디서 실패했는지를 덧붙입니다. 같은 검색 파이프라인 한 번 안에서 여러 검색이 일어나므로 pipeline_calls와 retrieval_calls도 구분합니다.
