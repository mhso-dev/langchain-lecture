에이전트의 도구 실행 정책

55일에는 create_agent가 도구 요청과 응답을 이어 주는 것을 확인했습니다. 오늘은 그 경로에 입력 검사·허용 목록·호출 상한·오류 기록을 붙입니다. 이런 실행을 돕는 코드를 하네스라고 부르지만, 이 장에서는 한 번의 실행과 한 턴 한 도구에 필요한 최소 정책만 다룹니다.

구조화된 답변을 받았다는 사실과 근거가 맞다는 사실도 나눠 봅니다. 형태가 맞는 999일 답변이 원문 14일과 다를 수 있습니다. 초안을 곧바로 최종 답변으로 쓰지 않고 공통 A1을 통과시키며, 의미 대조는 별도로 남깁니다.

12일 structured-output/cases.json에서 JSON의 필드와 타입을 검사했던 사례를 읽습니다. 39일 evaluation/adoption-decision.md에서는 개선을 채택하거나 보류한 근거를 확인합니다. 제공 채택 기록을 읽은 것과 본인이 같은 평가를 수행한 것은 다릅니다.

55일 agent/framework-comparison.md에서 정상 왕복의 모델/검색 횟수, ToolMessage의 요청 ID, 마지막 모델 예산 뒤 검색이 실행되었던 한계를 찾아봅니다. 첫 15분에 ‘999일 답변의 형태가 맞으면 정답인가’, ‘허용 목록은 누가 정하는가’, ‘검색 예외와 빈 목록은 같은가’를 설명합니다.

메시지·도구별 실행 기록

examples 폴더에는 실행 코드와 31개 고정 입력 사본을 담았습니다. 다른 장이나 prototype 폴더를 가져오지 않아도 실행됩니다. Python 3.12.15, langchain 1.5.0, langchain-core 1.8.0, langgraph 1.2.22, pydantic 2.14.2, langsmith 0.14.17에서 확인했습니다. 새 설치나 학생 운영체제 재현은 별도 확인이 필요합니다.

실제 create_agent·ToolStrategy·middleware를 실행합니다. 모델은 ScriptedChatModel 대본이고 검색은 가상 도서관 원문 3개의 로컬 교육 벡터입니다. 실제 LLM·Chroma·DB·인증은 이번 예제에서 실행하지 않습니다. API 키를 입력할 필요가 없습니다.

run_status는 실행 정책/운영 오류가 있었는지, result.status는 A1이 답변·자료 없음·인용 오류 중 무엇을 반환했는지 나타냅니다. completed여도 invalid_citation일 수 있으므로 둘을 모두 읽습니다. 예외가 난 실행의 result는 null입니다.

입력과 반환값의 별도 검증

StrictStr·StrictInt는 다른 타입을 편의상 바꾸어 받지 않게 합니다. k=True나 문자열‘2’를 정수 2처럼 처리하지 않습니다. extra='forbid'는 약속하지 않은 필드도 거부합니다. question이 공백이 아닌지와 k가 양수인지는 validate_request에서 다시 확인합니다.

content는 모델에게 전달할 JSON 문자열이고 artifact는 애플리케이션이 사용할 원문 객체 목록입니다. 검색 도구가 성공해도 id·text·source·page가 빠졌거나 실제 요청 k보다 많은 결과를 돌려주면 data_contract_error입니다. 정상 빈 검색과 구분해 result=null로 기록합니다.

요청의 ID는 응답의 tool_call_id에 이어져야 합니다. 한 턴의 여러 도구 요청과 빈/중복 ID는 실행 전에 거부합니다. 팀 문서 ID에 콜론이 들어 있어도 보존합니다. 검사는 ID를 줄이거나 임의로 새 이름으로 바꾸지 않습니다.

구조화 초안과 최종 응답

AnswerDraft는 answer 문자열과 cited_ids 목록이 있는 형태입니다. 실제 출처 객체를 모델이 새로 쓰게 하지 않습니다. 검색한 R1 객체와 본문의 [id]를 코드로 대조한 뒤 실제 인용 객체만 A1.sources에 넣습니다.

create_agent에 response_format=ToolStrategy(AnswerDraft, handle_errors=False)를 지정합니다. ToolStrategy는 도구 호출 형식으로 구조화 응답을 받아 state의 structured_response에 담습니다. AnswerDraft는 응답을 받기 위한 스키마이므로 검색 도구의 허용 목록이나 실제 검색 실행 횟수에 넣지 않습니다.

handle_errors=False라 형태 오류를 자동으로 다시 요청하지 않습니다. 빈 answer는 스키마에서, 공백 answer는 후속 검사에서 실패합니다. structured_response가 없어도 성공으로 처리하지 않습니다. 여기서 사용한 대본 모델은 공급자의 native structured output을 검증하는 ProviderStrategy와 다릅니다.

미들웨어의 실행 전후 처리

middleware는 모델이나 도구 호출 전후에 코드를 끼워 넣는 장치입니다. wrap_model_call의 handler를 부를 때 실제 모델에 진입하고, wrap_tool_call의 handler를 부를 때 실제 도구 실행에 진입합니다. handler를 부르기 전에 거부하면 요청은 있어도 실제 실행은 0회입니다.

제공 코드의 순서를 읽습니다. 먼저 허용 목록, 이미 실행한 도구 수, 남은 모델 예산을 확인합니다. 인자가 맞으면 도구를 실행한 뒤 artifact를 검증합니다. 학생은 이 코드를 처음부터 만들지 않고, RunContext의 한 조건을 바꾸어 어느 검사에서 멈췄는지 trace로 설명합니다.

빈 결과·빈 응답·예외의 분기

주차처럼 정상 검색 결과가[]이면 search_status=empty입니다. middleware가 로컬 종료 메시지를 만들고 다음 실제 모델 handler를 생략합니다. A1은 no_evidence와 생성 0을 반환합니다. 모델이 빈 문자열·공백을 반환한 것은 이 정상 빈 근거와 다르며 empty_model_response 오류입니다.

55는 주차에서 검색을 생략해 모델 1/검색 0이었습니다. 56은 빈 검색 정책을 관찰하려고 대본이 항상 검색을 요청하여 모델 1/검색 1입니다. 이 차이는 대본 정책의 변경이며 ToolStrategy나 create_agent 자체의 비용 효과가 아닙니다.

TimeoutError와 자료 메타데이터 오류도[]로 바꾸지 않습니다. 예외 종류만 기록해 실패 원인을 남기고 원문 예외 메시지는 내보내지 않습니다. 명시적 거절은 제공한 additional_kwargs.refusal과 type=refusal 블록 두 형식만 확인했습니다. 모든 공급자 메시지 형식을 처리했다고 볼 수는 없습니다.

후속 기능의 도구 계약

57–62일은 이 메시지·도구·오류 경계를 유지하면서 필요한 Skill·기억·외부 도구 연결을 추가합니다. 55–56에서는 그 기능이나 웹 서비스·인증을 선수 구현으로 끌어오지 않습니다. 도구가 늘면 등록 목록과 허용 정책을 함께 바꾸고 새 계약 검사로 인계합니다.

후속 소비자는 examples/API_CONTRACT.md의 run_agent_case·RunContext·반환 의미를 읽습니다. contract_version의 agent-foundation-prototype-v1은 설계 때 고정한 식별자를 유지한 것입니다. 학생 실행 코드는 examples 안에 완결되어 있습니다. S1 서비스 함수의 최종 서명이나 user_id·thread_id·HTTP 상태를 여기서 임의로 추가하지 않습니다.
