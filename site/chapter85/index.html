05

FastAPI 앱 재시작과 DB 호환성 심화 읽기

배포 대상과 인수 기준

84일차의 v2 앱·화면·082/084 SQL·회귀 근거를 인수합니다. 첫 15분에는 소비 목록의 파일과 실제 복사된 파일이 같은지, 날짜·우선순위·기존 T1 의미가 유지되는지 설명합니다. 다른 앱으로 바꾸어 배포 성공만 만드는 과제가 아닙니다.

72일차 Compose의 DB 연결·영속성 절차와 77일차 CI/CD의 같은 소스·이미지·검토 기준을 읽습니다. 이전 S1/B1 서비스의 데이터나 H1 응답을 Todo에 섞지 않습니다. Todo는 별도 DB와 볼륨의 단일 사용자 수업 앱입니다.

실제 Docker·AWS·HTTP·PG·Actions·동료 수행은 준비 파일과 다릅니다. 환경이 없으면 로컬 회귀·정적 설정·실행 계획을 분석하고 실제 배포 목표는 미확인으로 남깁니다.

환경 설정과 비밀값 주입

Compose 프로젝트 이름은 course-todo이고 논리 볼륨은 todo-data입니다. 이전 course-b1의 데이터 볼륨과 구분합니다. DB 서비스 이름 db는 컨테이너 내부 호스트이며 API는 내부 5432로 연결합니다.

DB의 호스트 포트는 기본 공개하지 않고 API는 호스트의 127.0.0.1:8000에만 묶습니다. 컨테이너 안의 0.0.0.0과 호스트 공개 주소는 다른 설정입니다. 인증 없는 단일 사용자 앱을 공개 운영 인증이 끝난 서비스로 설명하지 않습니다.

이미지와 정적 자산

Docker build context는 배포 폴더입니다. Dockerfile은 같은 v2 앱의 필요한 Python·SQL·web 파일만 COPY합니다. 정적 제공 범위는 web 디렉토리이며 앱 소스나 비밀 파일을 웹 경로로 내보내지 않습니다.

로컬 정적 검사는 COPY 대상 파일이 있는지와 제외 범위를 확인합니다. 이것이 Docker 빌드나 컨테이너 부팅 성공을 뜻하지는 않습니다. 준비된 수업 환경에서 빌드·버전·오류를 직접 기록해야 합니다.

Compose 서비스와 DB 초기화

실행 순서는 DB 시작과 준비 확인, 마이그레이션 성공, API 시작으로 나눕니다. pg_isready의 응답은 DB 프로세스가 연결을 받을 수 있는지 보는 신호이며 원하는 데이터와 스키마까지 검증하지 않습니다.

migrate 서비스는 같은 앱의 apply_v2_schema.py를 실행합니다. API 진입 전 require_schema는 082/084 기록의 해시를 파일과 대조하고 맞지 않으면 시작을 멈춥니다. 이 읽기 검사는 임의로 스키마를 초기화하거나 손실된 데이터를 만들어 주지 않습니다.

실제 DB에서 DDL을 실행하지 않았다면 아래 명령은 수행 순서의 준비입니다. 실패 시 대상 DB·권한·마이그레이션 기록을 보존하고 확인합니다. 기존 데이터를 삭제해 충돌을 없애는 것을 해결로 삼지 않습니다.

기존 호스트의 배포 절차

기존 AWS 실습 환경을 사용하더라도 접속 대상·허용 범위·같은 DB/볼륨을 다시 확인합니다. 새 계정·자원·보안 그룹을 이 교재가 만들었다고 가정하지 않습니다. 강사가 확인한 수동 배포 경로를 먼저 사용합니다.

기본 API 바인딩은 loopback입니다. 원격 수업 서버에서는 강사가 제공한 제한된 접근 방식으로 같은 서버 루트에 연결합니다. 임의로 0.0.0.0 호스트 포트를 열어 공개하는 것을 기본 해결로 삼지 않습니다.

학생의 실제 이미지 식별자·환경·명령·오류를 기록합니다. 실행 환경이 없으면 설정과 명령의 조건을 읽고 미확인을 남깁니다. 제공 파일이 있다는 사실만으로 AWS 배포가 완료된 것은 아닙니다.

API 접속 확인

첫 연결에서는 정적 화면, API 요청·응답, DB 읽기를 각각 확인합니다. 루트 페이지가 열린다고 /todos가 정상이고 기존 행이 보존됐다는 뜻은 아닙니다. 오류 응답을 정상 빈 목록으로 바꾸지 않습니다.

실제 API 관찰에서는 T1-api-v2와 다섯 필드, 날짜 문자열, 우선순위를 확인합니다. v1 UI나 오래된 캐시가 섞이면 응답 형식 오류가 날 수 있으므로 소스·이미지·브라우저가 같은 버전인지 대조합니다.

기능·영속성 검사

자기가 만든 시험 행의 ID를 기록한 뒤 추가·제목 수정·명시 완료·삭제·검색·마감일·우선순위를 대조합니다. 같은 제목이 있는 다른 사람의 행을 정리하지 않습니다. 공개 검색 기대를 적용할 때도 같은 자료인지 먼저 확인합니다.

앱 재시작 후 같은 ID·값이 보이는지, DB를 같은 볼륨으로 재시작했는지 따로 기록합니다. 새 볼륨을 연결한 빈 DB와 같은 실험이라고 쓰지 않습니다. 실제 복구는 별도 격리 대상에서 백업 시점·행을 대조해야 합니다.

저장 결과가 불명확하면 자동으로 쓰기를 다시 보내지 않습니다. 원래 요청과 재조회 근거를 연결하고 stale 화면을 최신 성공처럼 표시하지 않습니다. 제공 대역의 호출 횟수는 실제 서버 효과의 횟수가 아닙니다.

기존 CI/CD 경로 연결

77일차의 핵심은 같은 소스가 검사·빌드·배포로 이어지는지 확인하는 것입니다. Todo용 템플릿은 v2 로컬 검사를 실행하고 같은 build context를 빌드하는 경로를 적습니다. 로컬 테스트 통과와 실제 HTTP/PG 검증은 다른 근거입니다.

CI/CD 파일은 .yml.template이고 첫 단계가 HOLD로 끝나도록 되어 있습니다. action의 전체 commit SHA, 이미지 digest, 실제 환경 검토와 수동 적용 경로가 확정되기 전에는 활성 워크플로로 바꾸지 않습니다. Secrets·registry·Actions 실행은 이 제작에서 만들거나 수행하지 않았습니다.

동시 배포 제한과 main·todo-classroom 이름은 수업 설계입니다. 실제 브랜치·환경 정책과 적용 직전 현재 이미지·설정을 확인해야 합니다. 실패한 job이나 중간 취소가 자동으로 이전 이미지 또는 DB 복원을 수행했다고 해석하지 않습니다.

롤백과 데이터 호환성

이미지 롤백은 이전 앱 버전으로 되돌리는 작업이고 DB 복원은 데이터의 시점을 바꾸는 작업입니다. 둘을 같은 명령으로 묶으면 문제의 범위와 손실 가능성을 살피기 어렵습니다. 현재·이전 이미지와 설정, DB 상태를 먼저 보존합니다.

v1 이미지는 v2 필드를 표시하지 못할 수 있고 API 파서도 다릅니다. 가산 열이 남아 있다는 사실만으로 모든 조합이 호환된다고 가정하지 않습니다. 이전 이미지·UI·API와 현재 스키마의 동작을 확인한 뒤 제한된 수업 경로에서만 적용합니다.

DB 복구 연습은 새 격리 대상에서 수행하고 원본에 백업을 덮어쓰지 않습니다. 실패 후 자료를 모으는 동안 다른 배포가 덮어쓰지 않게 범위를 정합니다. 실제로 복구하지 않았다면 계획과 미확인만 남깁니다.

동료 테스트와 결함 수정

동료는 실행 안내만 보고 같은 앱과 사례를 찾을 수 있어야 합니다. 실제 동료가 사용한 명령과 환경, 설명이 더 필요했던 지점, 정상·실패 결과를 그대로 적습니다. 참여하지 않은 사람의 반응을 만들어 채우지 않습니다.

동료가 다른 DB를 보았다면 앱 결함과 환경 혼동을 나누어 확인합니다. 모든 실패를 코드 문제로 단정하지 말고 이미지·설정·주소·볼륨·같은 ID를 대조합니다. 수정 요청에도 이 근거를 넣습니다.

실제 동료나 배포 환경이 없으면 실행 안내를 역할별로 읽고 빠진 전제·입력·오류 대응을 찾습니다. 문서 검토를 실제 새 OS 재현이나 사용자 만족으로 표시하지 않습니다.

실행 코드와 시연 근거

한 요청을 UI→클라이언트→API→저장소→SQL→응답으로 설명합니다. 예를 들어 날짜 해제는 빈 입력을 null로 바꾸고, PATCH에서 해제 의미를 검증한 뒤 date NULL로 저장할 준비를 하며 v2 응답에 null로 돌아옵니다.

대표 실패도 포함합니다. 잘못된 날짜는 입력 오류이고, commit 결과가 불명확하면 data=null과 failed_or_unknown을 보존합니다. 화면은 이전 확인 목록을 유지하며 재조회 전 변경을 막습니다.

시연은 실제로 실행한 범위만 말합니다. 로컬 대역으로 코드 흐름을 설명했다면 Docker·HTTP·PG·브라우저 시연을 완료했다고 부르지 않습니다. 모르는 부분과 다음 확인할 조건을 함께 남깁니다.

앱·DB 최종 인계

인계에는 앱·SQL·화면·배포 설정의 버전, 실제 이미지 식별자 또는 미확인, 실행 안내, 정상·실패·복구 기준을 묶습니다. 교재의 고정 파일 해시는 학생이 만든 실제 이미지 digest나 운영 기록을 대신하지 않습니다.

O85-1은 같은 앱과 구성, O85-2는 핵심 동작·저장·오류의 직접 근거와 미확인, O85-3은 자동화·복구·동료 재현·설명 기록으로 판단합니다. 임의 합격선 대신 목표별 근거충족·수정필요·미확인을 사용합니다.

86일차는 새 프로젝트의 문제·사용자를 정하는 단계입니다. 이번 Todo의 모든 기능이나 기술을 새 프로젝트에 강제하지 않습니다. 요구에 맞는 선택과 실제 검증 근거를 가져갑니다.
