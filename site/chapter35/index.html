개발용과 공개 확인용을 나누는 이유

개발 문항은 코드를 바꾸고 오류를 고치는 동안 계속 볼 수 있는 질문입니다. 확인 문항은 설정을 정한 뒤 같은 기준이 다른 질문에도 적용되는지 읽는 데 씁니다. 두 용도를 나누면 무엇을 보고 고쳤는지 설명하기 쉬워집니다.

이 교재의 확인 2문항은 파일과 교재에 공개돼 있습니다. 비공개 시험이나 모델이 보지 못한 질문이라고 부르지 않습니다. 확인 결과를 보고 다시 설정을 골랐다면 그 문항도 개발에 사용한 것입니다. 새 확인 문항을 만들고 버전과 변경 이유를 남기는 것이 다음 단계입니다.

질문의 공백만 바꿔 다른 분리에 넣는 것은 새 질문을 만든 것이 아닙니다. 제공 검사는 유니코드 표기와 연속 공백을 정리한 뒤 같은 질문인지 검사합니다. 다만 뜻이 같은 모든 바꿔쓰기를 자동으로 알아내지는 못하므로 사람이 문장을 함께 읽어야 합니다.

같은 답변을 두 사람이 다르게 채점했다면 먼저 질문과 원문, 판정 기준을 함께 봅니다. “좋은 답”처럼 넓은 말 대신 확인 가능한 조건을 나누면 차이를 설명할 수 있습니다. 검색 근거가 맞는지, 답변에 인용했는지, 숫자와 조건이 보존됐는지를 따로 기록합니다.

“대출은 30일입니다. [library-1]”은 인용 ID가 존재하더라도 원문의 14일과 다릅니다. 반대로 “대출은 2주입니다. [library-1]”은 이 가상 규칙에서 같은 기간을 다른 말로 표현한 것입니다. 정답 문자열의 완전 일치만으로 모든 답변 내용을 판단하지 않습니다.

rubric.json은 기준표입니다. 학생 점수나 실제 사람 평가 결과가 들어 있는 파일이 아닙니다. 사람 평가를 했다면 검토자와 검토일, 대상 답변, 판단과 근거를 별도 기록해야 합니다.

질문을 JSONL로 저장하기

JSONL은 한 줄마다 JSON 객체 하나를 적는 형식입니다. 파일 전체를 하나의 JSON 배열로 읽는 대신 각 줄을 json.loads로 읽습니다. 질문 안의 줄바꿈은 JSON 문자열 안에서 이스케이프되므로 하나의 문항을 여러 줄로 예쁘게 들여쓰기해서 저장하지 않습니다.

잘못된 질문을 먼저 거르기

validate_rows는 질문 ID·질문의 빈값과 중복을 확인하고 기대 원문이 실제 원문 목록에 있는지 검사합니다. answerable이 참이면 기대 목록이 있어야 하고 거짓이면 비어야 합니다. bool 값 대신 숫자 1을 넣는 경우도 명시적으로 거부합니다.

구조 검사를 통과해도 질문의 뜻과 기대 원문이 맞는지는 사람이 확인합니다. 예를 들어 반납함 질문의 기대 원문을 대출 안내로 적어도 그 ID가 존재하기 때문에 단순 형식 검사는 통과할 수 있습니다. 코드는 존재 여부를, 판정자는 의미를 확인합니다.
