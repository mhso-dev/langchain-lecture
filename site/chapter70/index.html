05

SQLite 문서 상태와 대화 턴 저장 심화 읽기

문서 접수·준비·실패 상태

received는 본문을 처리하기 전 접수 상태입니다. ready는 본문과 새 업로드의 출처 매핑을 준비한 상태이고, failed는 파싱 실패의 제한된 오류 코드가 남은 상태입니다. “파일 이름이 있다”는 사실만으로 검색 가능한 자료가 아닙니다.

POST /documents는 title과 text를 JSON으로 받습니다. UTF-8 TXT 내용을 읽어 보내는 수업용 인터페이스이며 multipart 파일 전송이나 PDF 파서를 구현한 것은 아닙니다. 성공적으로 접수했어도 파싱 결과가 failed일 수 있으므로 status를 봅니다. SQL 오류는 정상 failed 응답으로 숨기지 않고 상태 재조회가 필요한 오류로 남깁니다.

파일 크기와 UTF-8 검증

제공 sample.txt를 read_bytes().decode("utf-8")로 읽으면 파일의 CRLF를 텍스트 모드가 임의로 바꾸지 않습니다. JSON text를 다시 UTF-8로 인코딩한 바이트를 parser에 넘깁니다. 이 경로의 해시는 그 전달 바이트를 대상으로 합니다.

최대 65536바이트를 허용합니다. len(text)는 글자 수이고 len(text.encode("utf-8"))는 바이트 수입니다. 한글 30000자는 글자 제한 안이어도 바이트 제한을 넘을 수 있습니다. 공백만 있는 본문과 NUL, 잘못된 UTF-8도 거부합니다. 이 제한을 HTTP 요청 전체의 네트워크 용량 제한이라고 주장하지 않습니다.

UUID·청크·원문 쪽 번호

parse_txt는 빈 줄을 기준으로 문단을 나눕니다. 원문 ID는 upload:<문서UUID>, 청크 ID는 뒤에 :c001처럼 번호를 붙입니다. 페이지 1은 TXT의 수업용 논리 페이지이며 실제 PDF 페이지를 추정한 값이 아닙니다. 원문 바이트 해시와 정리한 각 청크 문자열 해시의 대상을 구분하세요.

이전 B1 ready 문서는 새 매핑 표가 비어 있을 수 있습니다. 이때 정상 검색 결과 []로 진행하면 자료 준비 실패를 no_evidence로 잘못 해석하게 됩니다. prepare_existing_mapping을 신뢰된 운영 준비 코드에서 명시적으로 호출해 현재 DB 본문을 UTF-8로 내보내고 매핑을 만듭니다. source_sha256을 과거 업로드 파일의 해시라고 쓰지 않습니다. 이미 매핑이 있으면 자동으로 덮어쓰지 않습니다.

문서 소유 범위 확인

질문 경로는 /conversations/{cid}/documents/{did}/ask입니다. 본문은 68일과 같은 question/k이고, 문서는 명시적인 자원 경로로 선택합니다. 요청자가 지정한 ID는 권한을 증명하지 않습니다. 서버는 대화와 문서의 owner, 문서의 ready 상태, 범위 전체의 매핑을 확인합니다.

기본 검색 범위는 그 문서 하나입니다. 여러 문서를 함께 검색하려면 신뢰된 서버 구성의 scope_selector가 허용 목록을 정해야 합니다. HTTP 본문의 allowed_document_ids를 그대로 받지 않습니다. 조회 연결을 닫은 뒤 S1을 실행하고 저장할 때 소유권과 상태를 다시 확인합니다.

make_document_answer는 검증된 후보를 복사하고 그 후보만 검색하는 함수를 만듭니다. 정규식으로 추출한 2자 이상 한글·영문·숫자 토큰이 본문에 포함되는지 보는 간단한 방식이므로 의미 검색이나 형태소 분석이 아닙니다. 제공 “과제” 질문은 두 문단에 모두 포함되어 sources 두 개를 확인하기 위한 사례입니다.

새 문서는 course-guide-v1이 아닙니다. 후보 전체의 해시로 owned-txt-v1 자료 버전을 만들고 use_skill=False를 명시합니다. 과정 안내의 답변 지침을 다른 TXT의 사실인 것처럼 가져오지 않습니다. 생성기는 S1이 만든 근거 문맥을 그대로 반환하는 제공 함수입니다. 실제 외부 모델이 아닙니다.

S1은 사용자 지정 함수의 외부 호출 수를 null/미확인으로 표시합니다. 이 값을 임의로 0으로 바꾸지 않습니다. 별도 로컬 관측에 이 어댑터의 네트워크 호출 0을 남기는 것과 S1 계약 필드를 덮어쓰는 것은 다릅니다.

한 트랜잭션에서 턴·답변 저장

save_a1_turn은 질문과 A1을 검증하고 JSON·UTF-8 왕복 확인을 DB 연결 전에 끝냅니다. 트랜잭션 안에서는 서버 지정 문서 상태와 실제 인용 객체를 다시 대조합니다. ID가 같아도 text, source, page가 바뀌면 저장을 거부합니다.

그다음 기존 _insert_turn으로 텍스트 이력을 넣고 course_turn_results에 전체 A1과 metadata를 넣습니다. 두 INSERT와 commit이 함께 성공한 뒤에만 turn_id를 반환합니다. 두 번째 INSERT가 실패하면 첫 번째 turn도 rollback되어야 합니다. 이 동작을 실제 PostgreSQL 제약·잠금과 SQL 대역 검사에서 구분해 확인합니다.

DB 연결 단절은 commit 효과가 미확정인 상황일 수 있습니다. persistence.status=failed_or_unknown과 automatic_retry=false를 반환하면서 생성된 A1은 보존합니다. 현재 구현에는 요청 중복 제거가 없으므로 저장 실패 응답을 받았다고 바로 같은 질문을 반복하는 자동 재시도는 만들지 않습니다.

기존 이력과 새 결과 복원

list_a1_turns는 owner와 conversation_id로 조회합니다. LEFT JOIN을 사용하므로 A1 확장이 없는 이전 turn도 나타납니다. 이전 행은 answer를 유지하고 result=null, record_format=legacy_text_no_a1입니다.

새 행은 저장된 A1을 다시 검증하고 기존 answer 열과 A1 answer가 같은지 확인합니다. sources의 여러 객체를 그대로 돌려줍니다. 이 조회는 소유 대화·행 필터·A1 형식·answer 일치를 확인합니다. 현재 문서의 ready 상태와 출처 매핑을 다시 검사하는 함수는 아닙니다. 그 준비 조건과 인용 내용 대조는 질문 전 조회와 저장 경계에서 확인합니다.

명시 기억과 대화 이력

memory.py는 60일 공유 구현을 같은 바이트로 복사한 참조입니다. put_memory/get_memory/delete_memory는 owner와 memory_key로 명시적인 문자열 기억을 관리합니다. 대화 이력을 저장할 때 이 함수를 자동으로 호출하지 않습니다.

기본 문서 질의에는 개인 선호 기억이 필요하지 않아 채택하지 않았습니다. 기억을 추가하고 싶다면 무엇을 저장할지, 사용자에게 어떻게 확인할지, 삭제가 어떤 값에 영향을 주는지 별도 설계가 필요합니다. 오늘은 기억 HTTP CRUD나 새 인증 서비스를 만드는 대신 기존 함수의 관계와 채택 이유를 설명합니다.

기본 로컬 검사는 실제 S1과 SQL 호출 대역을 연결합니다. SQL 대역은 전달한 SQL과 매개변수, rollback 의도를 관찰하지만 PostgreSQL의 외래키·CHECK·잠금·격리 수준을 실행하는 엔진이 아닙니다. 전체 앱 코드가 있어도 실제 DB PASS는 별도입니다.

check_postgres_prepared.py는 무작위 schema를 만들고 migration 두 번 적용, 이전 행 보존, 새 업로드와 실제 S1 답, 재조회, 실패 트리거 rollback을 검사하도록 준비되어 있습니다. 검사 끝에는 자신이 만든 schema만 정리합니다. 실제 DB 재시작이나 다른 프로세스 복구 검사를 대체하지 않습니다.

배포용 앱과 저장 인터페이스

71일의 작은 컨테이너 입문 앱과 이 전체 문서 앱을 구분합니다. 72일은 같은 course-b1 프로젝트와 기존 볼륨을 유지하면서 API 서비스를 추가하고, API 내부 PGHOST=db·PGPORT=5432를 사용합니다. 73일에 검색 저장소를 바꾸더라도 owner·문서 UUID·원문/청크 ID·A1·HTTP 계약을 보존해야 합니다.

현재 상태는 원고와 준비 앱의 로컬 확인입니다. 실제 HTTP, PostgreSQL, 컨테이너, 재시작, 브라우저, 사용자 인증과 학생 성취의 검증은 따로 남깁니다. 이 한계를 숨기지 않고 후속 교재에 넘기는 것이 오늘의 완료 근거입니다.
