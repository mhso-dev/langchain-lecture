CREATE TABLE로 열과 규칙을 정하기

53일에는 제공된 표를 읽었습니다. CREATE TABLE은 새 표의 이름, 열 이름, 자료형과 제약을 정합니다. integer는 정수, text는 문자열입니다. PRIMARY KEY는 행 식별자, NOT NULL은 값이 빠지는 것을 금지하는 제약입니다. CHECK는 행의 값이 만족해야 할 조건을 적습니다.

다음 실험 표는 문서 서비스의 네 표를 대체하지 않습니다. 테이블 정의를 읽기 위한 작은 연습입니다. minutes > 0은 시간 값이 양수여야 한다는 이 연습의 규칙입니다. title이 NULL인 경우와 빈 문자열인 경우는 다르므로 NOT NULL만으로 공백 제목까지 막았다고 생각하지 않습니다.

BEGIN과 ROLLBACK은 잠시 실행한 변경을 되돌리기 위한 경계입니다. 바로 뒤 절에서 자세히 다룹니다. 지금은 파일 전체를 실행해 중간 SELECT를 보고, 실제 서비스 테이블은 그대로 있는지 확인하세요. 이 파일을 실행한 결과는 아직 제작 환경에서 검증하지 못했습니다.

행을 넣고 같은 행의 제목 바꾸기

INSERT INTO 다음에 대상 테이블과 열 목록을 쓰고 VALUES에 같은 순서의 값을 적습니다. 문서 ID는 미리 정한 UUID 문자열, owner는 이미 있는 alice입니다. ID를 바꾸지 않고 같은 행의 title만 바꾸려면 UPDATE를 씁니다.

UPDATE의 SET은 새 값, WHERE는 바꿀 행의 조건입니다. 실행 전에 동일한 WHERE로 SELECT를 해 보세요. 이 습관은 수정 대상이 예상과 다를 때 변경을 멈출 수 있게 합니다. RETURNING title은 이번 명령이 바꾼 행의 제목을 바로 돌려주는 PostgreSQL 구문입니다.

문서 id와 owner를 모두 조건에 남깁니다. 타인 문서에 자기 user_id를 붙여 요청하면 조건에 맞는 행이 없어 변경 수가 0입니다. 실제 서비스에서 이 사용자 ID를 누가 결정하는지는 인증 계층의 역할이며, 오늘은 가상 사용자 값으로 저장 함수의 경계를 확인합니다.

DELETE의 범위를 확인하고 행 지우기

DELETE는 조건에 맞는 행을 지웁니다. 열 하나를 비우는 UPDATE와 다릅니다. 아래 문장은 오늘 만든 새 실습 문서 한 행만 대상으로 삼습니다. WHERE가 빠진 DELETE는 테이블의 모든 행을 대상으로 하므로 그대로 실행하지 않습니다.

sql/054_changes.sql은 BEGIN부터 COMMIT까지 한 묶음으로 제공합니다. 삽입한 제목은 초안, 수정 후 제목은 수정한 초안, 삭제 뒤 조회는 0행이 예상됩니다. 마지막에 행이 없는 이유는 오류로 되돌렸기 때문이 아니라, 묶음 안에서 그 행을 삭제하고 확정했기 때문입니다.

COMMIT과 ROLLBACK으로 묶음의 결과 정하기

트랜잭션은 함께 확정하거나 함께 되돌릴 변경의 묶음입니다. BEGIN으로 시작하고 COMMIT으로 확정합니다. ROLLBACK은 아직 확정하지 않은 묶음의 변경을 취소합니다. 이미 COMMIT한 이전 작업을 ROLLBACK 하나로 되돌리는 것은 아닙니다.

psql에서 명시적으로 BEGIN하지 않고 일반 변경문을 실행하면 그 문장이 성공할 때 보통 바로 확정됩니다. 오늘 연습 파일에 BEGIN과 종료문을 적은 이유는 묶음의 경계를 직접 확인하기 위해서입니다. Python 연결의 기본 트랜잭션 동작은 뒤에서 따로 확인합니다.

규칙을 어긴 변경이 실패하는 이유

잘못된 데이터를 함수에서 먼저 거를 수 있지만 DB에도 규칙을 남깁니다. 이미 쓰는 기본키를 다시 넣으면 중복 키 오류, 없는 owner를 넣으면 외래키 오류가 납니다. 오류를 무시해 성공 메시지를 출력하면 저장되지 않은 기록을 사용자에게 저장됐다고 알리게 됩니다.

트랜잭션 중 SQL 오류가 발생하면 그 연결의 묶음은 실패 상태가 됩니다. 계속 다른 SQL을 보내기 전에 ROLLBACK으로 정리해야 합니다. Python 예제에서는 예외가 연결의 with 블록 밖으로 나가게 하여 정리하도록 합니다. 오류를 블록 안에서 잡고 성공한 것처럼 계속 진행하지 않습니다.

오류의 실제 문장에는 표·제약 이름과 버전 정보가 포함되어 환경마다 달라질 수 있습니다. 오류명과 원인을 기록하고 비밀번호를 포함한 접속 설정 전체를 복사하지 않습니다.

Python에서 PostgreSQL에 연결하기

Psycopg는 Python 코드와 PostgreSQL 사이에서 SQL과 값을 전달하고 결과를 읽는 드라이버입니다. 가상환경에 패키지를 설치한 뒤 같은 셸의 PGHOST·PGPORT·PGDATABASE·PGUSER·PGPASSWORD를 읽습니다. .env.example 파일은 변수 이름을 보여 주는 참고 자료이며 Python이 자동으로 읽지 않습니다.

이 장은 Python 3.12와 B1의 psycopg 3.3.9 후보를 사용합니다. 제작 환경에서는 드라이버와 실제 DB를 실행하지 못했으므로 설치 성공을 보장한 잠금 목록으로 보지 않습니다. 설치·접속에 실패하면 오류를 기록하고 강사 환경에서 먼저 확인합니다.

connection()은 DB 연결을 만듭니다. with connection() as conn 안에서 conn.execute(...)를 실행합니다. 이 Psycopg 연결 문맥은 정상 종료하면 commit, 예외로 나가면 rollback하고 연결을 닫습니다. Python의 모든 with가 DB를 commit한다는 뜻은 아닙니다. 이 연결 객체가 정한 동작입니다.

문자열에 값을 붙이지 않고 별도 인수로 전달하기

제목에 작은따옴표가 들어갈 수 있습니다. SQL 문자열을 더하거나 f-string으로 제목을 끼워 넣으면 SQL 문법과 사용자 값이 섞입니다. Psycopg에서는 SQL에 %s 자리를 두고 값은 execute의 두 번째 인수로 전달합니다.

%s는 Python의 % 문자열 치환을 하라는 뜻이 아닙니다. 자리표시자 주변에 작은따옴표를 추가하지도 않습니다. 드라이버가 값의 형식과 전달을 처리합니다. 값 하나의 튜플은 ('alice',)처럼 쉼표가 필요합니다. 테이블·열 이름을 사용자 입력으로 받는 동적 SQL은 오늘 범위에 넣지 않습니다.

문서 ID가 같아도 owner가 맞지 않으면 결과가 없습니다. 값 바인딩은 SQL과 값을 분리하는 방법이고, owner 조건은 접근할 행을 제한하는 규칙입니다. 두 가지를 함께 확인해야 합니다. 드라이버 사용만으로 사용자 인증까지 완성되는 것은 아닙니다.

저장·조회 함수를 호출하고 결과 읽기

repository.py에는 같은 SQL을 여러 곳에서 다시 쓰지 않도록 문서 저장·조회, 대화 생성, 질문 저장 함수를 모았습니다. create_document는 제목과 본문이 공백이면 DB를 호출하기 전에 ValueError를 냅니다. get_document는 소유 문서가 없으면 None을 돌려줍니다.

다음 전체 demo.py는 문서와 대화를 하나씩 만들고 질문 한 개를 저장합니다. uuid4()는 새 식별자를 만드는 표준 라이브러리 함수입니다. 출력 ID는 실행할 때마다 달라지므로 특정 UUID와 비교하지 않습니다. 제목, 타인 조회 결과, 해당 대화의 질문 수를 비교하세요.

demo.py는 호출마다 새 기록을 남깁니다. 53일의 전체 질문 수를 다시 세면 이전보다 늘어나는 것이 정상입니다. 저장 함수 하나의 with가 종료된 뒤 다음 함수가 새 연결에서 값을 읽으므로, 실제 실행에 성공하면 commit된 값이 다른 연결에서도 보이는지를 확인할 수 있습니다.

제공 파일의 _insert_turn과 FOR KEY SHARE는 대화·문서의 소유 관계를 확인하고 동시 접근 중 관계가 바뀌는 상황을 다루기 위한 코드입니다. 오늘 직접 구현하는 목표는 문서 저장·조회와 제목 변경입니다. 잠금 설계를 암기하거나 미래 기능을 만들 필요는 없습니다.

두 번째 INSERT가 실패하면 첫 변경도 남지 않게 하기

별도 함수 두 개를 차례로 호출하면 각 함수가 따로 commit할 수 있습니다. ‘함수 두 개를 불렀으니 자동으로 한 트랜잭션’이라고 생각하면 안 됩니다. transaction_demo.py는 두 INSERT를 같은 connection의 with 안에서 실행합니다.

첫 문서는 alice 소유로 정상 입력하고, 두 번째는 존재하지 않는 missing-user를 owner로 넣습니다. 외래키 오류가 with 밖으로 전달되면 같은 묶음의 첫 문서도 rollback되어야 합니다. 그 뒤 새로운 연결로 첫 문서를 조회해 None인지 검사합니다.

이 출력은 실제 실행 전에 기대하는 결과입니다. 드라이버가 없거나 DB에 접속할 수 없다면 이 검사 결과를 얻은 것이 아닙니다. 오류가 나지 않거나 첫 문서가 남으면 프로그램은 AssertionError로 끝나도록 작성했습니다. 성공 문장만 출력하는 데모와 구분해서 읽으세요.

A54-3 · 소유 문서의 제목 변경 함수 만들기

먼저 끝난 학생은 문서와 대화 생성이 모두 성공했을 때만 확정하는 별도 함수를 설계해 보세요. 두 함수를 단순히 호출하는 것과 같은 연결을 전달하는 것의 차이를 그림으로 설명하는 선택 활동입니다. 기본 과제의 세 경계 사례를 먼저 확인합니다.

정상 예상 출력은 ‘자기 문서·타인 문서·빈 제목 검사 통과’입니다. 시작 파일 그대로이면 NotImplementedError가 나며, 실제 DB가 없으면 연결 단계에서 중단됩니다. 전체 검사 코드는 아래 개별 파일 링크로 열 수 있습니다.

단위 검사와 실제 DB 검사를 나누어 기록하기

test_unit.py는 가짜 연결 객체로 SQL과 값이 분리됐는지, owner 조건을 사용하는지, 잘못된 입력을 DB 호출 전에 거부하는지 확인합니다. 가짜 객체는 PostgreSQL의 SQL 문법·외래키·commit을 실행하지 않습니다. 이 검사가 통과해도 실제 저장 성공으로 적지 않습니다.

test_postgres.py는 B1_TEST_DATABASE=1을 명시할 때만 실제 DB에 임시 스키마를 만들고 저장·조회·rollback·복합 FK를 확인합니다. 그 임시 스키마만 정리하며 기존 수업 테이블은 지우지 않습니다. 기본 명령에서 SKIP된 네 검사는 통과 수에 넣지 않습니다.
