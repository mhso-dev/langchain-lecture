05

관련 개념 더 읽기

검색과 답 중 어디에서 처음 어긋났을까요?

검색 단계에서는 질문에 필요한 원문이 결과에 포함됐는지를 봅니다. 답변 단계에서는 검색된 근거를 인용하고 숫자와 조건을 맞게 옮겼는지 봅니다. 마지막 답변만 읽으면 검색 실패와 생성 실패가 섞이므로 검색 문서도 함께 저장합니다.

운영 오류는 정상 검색 결과가 아닙니다. timeout이 났다고 빈 목록으로 바꾸면 원문이 없어서 답하지 못한 것처럼 보입니다. 정상적으로 검색했지만 필요한 원문이 없었던 경우와 호출 자체가 실패한 경우를 나누어야 다음 조치를 정할 수 있습니다.

k는 검색 함수에 요청한 최대 결과 수입니다. Recall@k는 그 결과에서 기대 근거를 얼마나 찾았는지 보는 비율입니다. 이 교재에서는 청크를 원문 ID로 바꾼 집합을 사용합니다. 분자는 검색 원문 집합과 기대 원문 집합의 교집합 크기이고, 분모는 기대 원문 집합의 크기입니다.

예를 들어 기대 원문이 library-1과 library-3 두 개인데 검색 결과가 library-1과 library-2라면, 맞게 찾은 원문은 하나라 recall은 1/2=0.5입니다. 검색 결과가 두 개라는 이유로 분모를 2로 정한 것이 아니라, 질문에 필요한 원문이 두 개여서 분모가 2입니다.

검색과 답변을 나누어 확인하기

좋아 보이는 답변 하나만으로 RAG의 어느 부분이 잘 작동했는지 알 수는 없습니다. 필요한 원문을 못 찾았을 수도 있고, 원문을 찾고도 숫자를 잘못 썼을 수도 있습니다. 오늘은 35장에서 고정한 같은 질문을 사용해 검색 결과와 답변을 따로 기록하고 실패가 생긴 위치를 찾습니다.

35장 질문과 판정표 확인

기본 실행은 개발 3문항과 공개 확인 2문항을 각각 보고합니다. 두 묶음의 평균을 합쳐 일반 성능처럼 설명하지 않습니다. 다음 최적화 장에서는 개발 문항만 설정 비교에 사용하며 공개 확인을 비공개 평가라고 주장하지 않습니다.

여러 청크를 같은 원문으로 묶기

검색된 두 청크가 library-1:0과 library-1:1이면 같은 원문을 두 번 찾은 것입니다. 기대 근거가 library-1 하나일 때 분자를 2로 세면 recall이 2가 되는 잘못된 계산이 나옵니다. source-map으로 원문 ID를 찾고 set으로 중복을 제거합니다.

매핑이 없는 청크 ID를 문자열의 콜론 앞부분만 잘라 원문이라고 가정하지 않습니다. 팀 자료의 ID 규칙이 다를 수 있고 잘못된 스냅샷을 섞은 것일 수도 있습니다. 위치표가 없으면 mapping 오류로 기록하고 점수를 보류합니다.

정답이 없는 질문과 관측하지 못한 값

자료에 답이 없는 질문은 기대 원문 집합이 비어 있습니다. 이때 0으로 나누는 recall을 억지로 1로 채우지 않습니다. JSON에서는 null, CSV에서는 NA로 표시하고 recall_na_reason=empty_gold로 적습니다. 대신 정상 검색이 빈 결과였는지, 답변이 근거 없는 내용을 만들지 않았는지를 별도로 봅니다.

검색 오류도 recall을 계산하지 못해 null이지만 이유가 다릅니다. retrieval_error나 mapping_error를 함께 적어야 구분할 수 있습니다. 빈 정답 집합은 데이터의 의도이고 검색 오류는 실행의 실패입니다.

empty_when_unanswerable은 그 교육용 검색이 빈 결과를 냈는지만 관측합니다. 실제 의미 검색은 관련 없는 후보를 반환할 수도 있으며, 빈 결과 여부 하나가 모든 무응답 품질을 평가하는 일반 지표는 아닙니다.

기준선과 의도적 실패를 실행하기

위 1.0은 공개된 작은 자료에서 키워드 검색으로 원문을 찾은 로컬 관측입니다. 실제 서비스 정확도 100%라는 뜻이 아닙니다. 분모는 개발의 답변 가능 2문항, 공개 확인의 답변 가능 1문항이며 답변 불가 문항은 recall 평균에 넣지 않았습니다.

failure_examples.py는 같은 대출 질문에 timeout·누락 매핑·잘못된 인용·맞는 인용을 붙인 틀린 숫자를 의도적으로 넣습니다. 마지막 사례의 failure_stage가 비어 있는 것은 의미 검사를 하지 않았기 때문입니다. 이 4사례를 기본 평가 5문항에 더해 실패율을 계산하지 않습니다.

실패를 빼면 분모가 달라집니다

답변 가능한 질문 2개 중 하나는 검색에 성공하고 다른 하나는 timeout이라면, 성공한 한 문항만의 평균은 계산할 수 있습니다. 그러나 그 값을 전체 두 문항의 평균처럼 표시하면 실패를 숨깁니다. 이 교재는 전체 평균을 보류하고 관측한 문항만의 평균과 그 분모를 따로 적습니다.

summary에는 전체 질문 수, 답변 가능 수, recall 관측/미관측 수, 불가 질문 수, 실패 질문 ID가 함께 있습니다. 검색이 성공하고 생성만 실패한 경우에는 검색 recall이 관측된 상태로 남으며 failure_count에도 포함됩니다. 무엇이 성공했는지 단계별로 읽습니다.

자동으로 확인한 것은 ID와 계산 조건입니다. 답변 내용은 원문 문장을 읽어야 합니다. 숫자·단위·기간·예외·주체가 같은지 확인하고, 틀렸다면 답변의 어느 구절이 어떤 근거와 어긋나는지 남깁니다.

검토자끼리 판정이 다르면 다수결만으로 끝내지 않습니다. 질문이 모호했는지, 원문에 필요한 조건이 없었는지, 기준을 다르게 읽었는지 확인합니다. 판단 보류도 이유를 적으면 유용한 기록입니다. 사람 검토를 실제로 하지 않았으면 양식의 빈칸을 통과로 채우지 않습니다.

LLM 평가 예시의 오판을 찾기

LLM을 평가 보조자로 사용할 때도 판정이 맞는지 확인해야 합니다. 평가 입력에는 질문·원문·후보 답변·판정 기준을 분리해 주고 판단 근거를 읽습니다. 모델이 점수를 출력했다는 사실만으로 교사의 확정 판정이 되지는 않습니다.

학생이 읽는 examples/judge-cases.json은 작성자가 만든 모의 판정 사례입니다. 판정과 근거 해설은 별도 강사용 instructor/simulated_judge_examples.json에 있습니다. 실제 LLM 호출이나 실제 사람 점수는 없습니다. 첫 사례는 관련 문서를 인용했다는 이유만으로 틀린 숫자를 승인하고, 둘째 사례는 14일과 2주의 표현 차이만 보고 정답을 거부합니다. 우리는 원문과 기준을 다시 읽어 이 두 오류를 찾습니다.

Zheng 등의 LLM-as-a-judge 연구는 평가 모델의 위치·장황함 등에 따른 편향과 추론 한계를 조사했습니다. 여기의 두 가상 예시는 그 연구 실험을 재현한 결과가 아니며 특정 모델의 오판율을 뜻하지 않습니다.

실패 원인을 적었다고 바로 성능 개선이 증명된 것은 아닙니다. 다음 장에서는 원문·질문을 고정하고 청크 크기·중첩·k를 하나씩 바꾸어 결과가 어떻게 달라지는지 살펴봅니다. 운영 오류가 계속되는 상태에서 설정만 바꾸어 낮은 값을 개선했다고 말하지 않습니다.

파일·인계·출처

37장에는 질문·판정표·manifest와 baseline.csv/JSON·summary·run-manifest를 함께 넘깁니다. CSV만으로는 검색 본문과 A1 출처를 복원할 수 없습니다. 파일이 없으면 37장 input-baseline의 같은 시작 스냅샷으로 재개합니다.

현재 코드·지표 계산은 로컬에서 확인했습니다. 실제 Chroma/LLM·브라우저 조작·학생 환경과 학습 시간은 미확인입니다. 자세한 범위는 VALIDATION.md를 확인하세요.
