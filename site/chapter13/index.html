06

관련 개념 더 읽기

한 번의 요청을 단계로 나누는 이유

여러 작업을 한 번에 요청하면 어디에서 잘못되었는지 구분하기 어려울 수 있습니다. 요약·분류·문장 작성을 따로 실행하면 중간 결과를 볼 수 있지만 호출 수와 대기 시간도 늘어납니다. 작업을 나눈다는 사실만으로 품질이 좋아진다고 단정하지 않습니다.

이번 흐름에서는 Python 코드가 항상 요약, 분류, 작성 순서를 정합니다. 모델이 다음 함수를 선택하는 에이전트가 아닙니다. 모델은 각 단계에서 입력을 받아 텍스트를 돌려줄 뿐입니다.

요약과 분야를 함께 전달합니다.

summary: 결제 영수증 확인 문의
category: billing

분류가 billing이라는 단어만 반환하면 그 안에는 사용자의 구체적인 문의가 없습니다. 작성 단계에는 분야뿐 아니라 요약도 전달해야 합니다. 중간 단계 하나의 출력만 계속 덮어쓰면 앞에서 필요한 정보를 잃을 수 있습니다.

단계 실행을 함수로 묶기

step은 단계 이름과 입력을 받아 호출하고 결과를 검사합니다. 입력과 출력, 시간을 log에 함께 남기므로 어느 단계에서 문제가 생겼는지 읽을 수 있습니다. 이번 실습은 가상 문의만 로그에 남깁니다. 실제 서비스에서는 개인정보가 로그에 남지 않도록 범위와 보관 규칙을 정해야 합니다.

run_workflow의 call 인자는 모델 호출을 담당하는 함수입니다. 기본 실행은 mock_call을 전달합니다. 이처럼 호출 경계를 분리하면 인터넷 없이도 연결 순서와 실패 경로를 검사할 수 있습니다.

모의 실행과 SDK 연결 범위

기본 응답은 입력 내용과 무관하게 준비된 값을 반환합니다. 질문을 바꿔도 같은 결과가 나오므로 분류 정확도 시험으로 사용할 수 없습니다. 이 실행은 세 단계의 데이터 전달과 중단 조건을 검사합니다.

sdk_call은 11장의 준비된 OpenAI 클라이언트와 모델을 받아 같은 호출 인터페이스를 만듭니다. 실제 사용 시 run_workflow(sdk_call(client, model), request)로 연결할 수 있습니다. 실제 경로는 정상 흐름 한 번에 모델 요청 세 번을 수행하므로 사전 예산과 계정 확인이 필요합니다. 이번 제작에서는 호출하지 않았습니다.

중간 실패를 성공 값처럼 넘기지 않기

분류 단계가 빈 문자열을 반환했는데 작성 단계로 계속 진행하면 정상처럼 보이는 안내문을 만들 수 있습니다. 빈 출력과 허용하지 않은 분류를 즉시 거부하고 뒤 단계를 실행하지 않도록 합니다.

이 예제는 오류를 예외로 알립니다. 실패 시 앞 단계 로그를 외부에 반환하는 구조까지 구현하지 않았습니다. 실제 운영 로그를 만들 때는 성공 단계와 실패 단계를 함께 보관하되 민감한 입력 전체를 무조건 저장하지 않습니다.

요약 길이를 늘리는 방법과 원문을 뒤 단계에도 전달하는 방법은 서로 다른 설계입니다. 어떤 정보를 남겨야 하는지 먼저 정하고, 입력 크기와 확인 부담을 함께 비교하세요.
