직접 구현할 작은 함수의 약속

validate_request는 호출 요청을 검사해 bool을 반환합니다. 딕셔너리가 아닌 값이나 잘못된 요청에는 False를 반환합니다. 실제 도구나 모델을 실행하지 않고 입력도 수정하지 않습니다.

허용 이름은 get_loan_rule 하나입니다. call_id는 공백이 아닌 문자열, arguments는 JSON 문자열이며 파싱 결과가 빈 객체 {}여야 합니다. bytes나 이미 만들어진 딕셔너리는 JSON 문자열이 아니므로 거부합니다. 잘못된 JSON·추가 인자·누락된 필드에도 False를 반환합니다.

처음부터 한 줄로 모든 조건을 쓰지 말고 이름, ID, JSON 파싱, 객체 내용의 순서로 나누세요. JSON 읽기가 실패하는 경우는 try/except로 처리합니다. 파싱이 성공해도 리스트나 숫자이면 객체 조건을 통과하지 못해야 합니다.

각 조건을 추가할 때 하나의 정상 사례와 하나의 실패 사례를 직접 호출해 봅니다. True와 "True"는 다릅니다. 이 함수는 문자열이 아닌 bool을 반환해야 합니다.

도구 실행 흐름과 연결해서 설명하기

함수 검사를 마쳤다면 제공한 agent_loop.py를 실행하고 validate_request가 들어갈 위치를 설명합니다. 실제로 연결하려면 get_hours 요청까지 허용하는 기존 루프의 계약과 지금의 단일 도구 계약을 조정해야 합니다. 서로 다른 범위를 그대로 섞지 않습니다.

이번 통합 과제의 핵심은 코드 위치와 책임을 설명하는 것입니다. 사용자 질문 → 모델 응답 → 함수 이름·인자 검사 → 도구 실행 → 결과 반환 → 다음 모델 응답의 순서를 기록하세요.

20개 루프 검사는 bool 상한·질문형·공백 답변·잘못된 ID도 확인합니다. 공백 답변은 empty_answer, 잘못된 질문이나 상한은 호출 전 예외입니다. 도구 상한 0은 유효하며 요청 실행을 금지합니다. 검사 통과와 자신의 구현·설명은 다른 증거입니다.

동료가 실행할 수 있게 기록하기

동료에게 비밀키나 가상환경 폴더를 주지 않습니다. 이번 기본 실행은 표준 라이브러리만 사용하므로 파일을 복사하고 같은 명령으로 실행할 수 있습니다. 동료의 운영체제에서 실행하지 않았다면 확인하지 않았다고 기록합니다.
