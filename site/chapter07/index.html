06

관련 개념 더 읽기

변경할 작업을 브랜치로 구분하기

브랜치는 커밋을 가리키는 이름입니다. 브랜치를 나누면 같은 시작점에서 다른 변경을 기록한 뒤 비교할 수 있습니다. 브랜치를 바꾸기 전에 git status로 현재 변경을 확인하세요. 아직 정리하지 않은 변경이 있다면 먼저 내용을 확인해 커밋하거나 강사와 정리합니다.

이번 실습은 새 git-lab 폴더 안에서만 진행합니다. 기존 강의 저장소나 업무 저장소에서 명령을 실행하지 않습니다. 한 사람이 두 작성자 역할을 맡아 로컬 브랜치로 협업의 충돌을 재현하며, 원격 서버에 올리지는 않습니다.

같은 이름의 폴더가 이미 있으면 재사용하지 말고 git-lab-2처럼 새 이름을 정합니다. Git 2.28 이상에서 -b로 초기 브랜치 이름을 정할 수 있습니다. git --version으로 버전을 확인하세요. 작성자 설정은 이 저장소 안에만 적용됩니다.

printf는 지정한 글자를 출력하고 > banner.py는 그 내용을 파일에 저장합니다. 이 실습에서는 새 파일과 지정한 한 줄을 덮어쓰는 데만 사용합니다. 마지막 status가 비어 있으면 기록하지 않은 변경이 없는 상태입니다.

두 브랜치에서 같은 줄 바꾸기

git diff는 아직 스테이징하지 않은 변경을 보여 줍니다. 줄 앞의 -는 이전 내용, +는 새 내용입니다. 파일 변경을 확인한 뒤 git add로 선택하고 커밋합니다.

충돌 표시를 읽고 합의한 결과로 해결하기

위 문장은 대표적인 충돌 출력이며 Git 버전과 언어 설정에 따라 표현이 달라질 수 있습니다. 종료 코드가 1이고 banner.py가 충돌 파일로 표시되는 것이 예상 동작입니다. 이때 병합은 아직 완료되지 않았습니다.

banner.py를 열면 <<<<<<< HEAD와 ======= 사이가 현재 main의 변경, =======와 >>>>>>> 사이가 feature/title의 변경입니다. 충돌 표시는 Python 코드가 아니므로 그대로 실행하면 안 됩니다.

실행 결과를 먼저 확인하고 병합 커밋을 남깁니다. 커밋 해시는 PC마다 달라지므로 고정된 문자열을 정답으로 요구하지 않습니다. 마지막 status가 비어 있고 두 브랜치의 이력이 병합 커밋에 연결되는지 확인하세요.

해결을 시작하기 전에 이번 병합 자체를 취소해야 한다면 git merge --abort를 사용할 수 있습니다. 이는 진행 중인 병합에서만 사용하며, 병합 전에 작업 트리가 정리되어 있었는지 확인해야 합니다. 이미 완료한 커밋을 무작정 초기화하는 명령은 사용하지 않습니다.

동료에게 넘기기 전에 변경 검토하기

리뷰에서는 변경 목적, 영향을 받는 입력, 실행한 검사, 아직 확인하지 못한 환경을 전달합니다. “잘 됩니다” 대신 어떤 명령과 입력에서 어떤 결과를 얻었는지 적습니다.

실제 원격 협업에서는 담당 저장소·브랜치와 업로드 권한을 먼저 확인합니다. fetch는 원격 이력을 가져오고, pull은 가져온 이력을 현재 브랜치에 통합하며, push는 로컬 이력을 원격에 보냅니다. 이번 8H 기본 실습은 로컬 이력과 충돌 해결을 대상으로 하며 원격 업로드 성공을 검증하지 않습니다.

틀린 합계의 중간 값을 추적하기

다음 buggy.py는 문법 오류 없이 실행되지만 합계가 틀립니다. 의도적으로 넣은 결함이며 30+20+40의 예상값은 90입니다. 처음부터 줄을 무작정 바꾸지 말고 반복이 진행될 때 total을 관찰하세요.

디버거는 실행을 멈추고 변수 값을 볼 수 있는 도구입니다. 아래 명령은 Python 기본 디버거 pdb를 시작합니다. (Pdb) 표시가 나오면 b 4로 4행 중단점을 두고 c로 진행합니다. p total과 p record로 값을 보고 n으로 한 줄씩 실행합니다. q는 종료입니다.

두 번째 반복에서 4행 실행 전 total은 30인데, 그 줄을 실행하면 0으로 돌아갑니다. 초기화를 반복문 바깥에 한 번만 두면 이전 합계가 유지됩니다. 제공 stats.py는 이 위치를 고치고 입력 분의 범위를 검사합니다.

logging은 실행 과정의 진단 정보를 남기는 표준 모듈입니다. getLogger(__name__)은 모듈 이름으로 로그를 구분합니다. debug는 자세한 점검용, info는 주요 진행, warning은 주의 상황, error는 실패를 기록할 때 사용합니다. 로그에는 입력 전체나 비밀값을 그대로 남기지 않습니다. 여기서는 가상 기록의 순서·분·합계만 남깁니다.

enumerate(records, start=1)은 기록과 함께 1부터 시작하는 순서를 줍니다. index와 record 두 이름으로 나눠 받습니다. 실제 로깅 설정은 다음 main.py의 시작점에서 정합니다.

pytest로 정상·경계·실패를 모아 실행하기

pytest는 test_로 시작하는 파일과 함수를 찾아 실행합니다. 각 함수 안에서 assert로 예상값을 비교합니다. pytest.raises(ValueError)는 안쪽 코드가 해당 예외를 발생시켜야 통과하도록 확인합니다.

여기서 입력 계약은 minutes 키를 가진 딕셔너리들의 리스트입니다. 정상 합계, 빈 목록, 경계값, 잘못된 분 값 네 가지를 검사합니다. 테스트 함수는 4개지만 마지막 함수는 잘못된 값 4개를 반복 확인합니다. 테스트 개수와 입력 사례 개수를 구분하세요.

로그는 기본적으로 표준 오류(stderr), print는 표준 출력(stdout)으로 나옵니다. 도구가 두 흐름을 따로 수집하면 보이는 순서가 달라질 수 있습니다. 출력 순서만으로 프로그램 순서를 판단하지 마세요.

이 예제는 분 값 계약을 확인하는 작은 처리기입니다. 임의 형태의 모든 JSON을 검증하는 범용 스키마 도구는 아닙니다. 함수가 받는 리스트·행 구조는 README에 명시합니다.

list[dict] 타입 힌트는 딕셔너리들의 리스트를 뜻합니다. except 뒤의 괄호 안에는 처리할 예외 종류를 여러 개 나열할 수 있습니다. 이 예제는 파일·JSON·키·자료형 문제를 입력 확인 메시지로 묶습니다.
