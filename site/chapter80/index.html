05

관련 개념 더 읽기

작업 폴더와 이전 자료 확인

첫 15분에는 78일의 label/input/button/목록을 찾고, 79일에 입력 값과 JSON·화면 표시가 어떻게 이어졌는지 설명합니다. DOM id는 화면 요소의 이름입니다. Todo의 id는 데이터 레코드의 식별자입니다. 79일 과정 안내 답변을 오늘 할 일 목록에 저장하지 않습니다.

도구 사용이 준비된 학생은 강사가 확인한 Codex 환경에서 작업합니다. 제공 파일의 존재나 버전 메타데이터만으로 로그인·모델 이용이 된다고 판단하지 않습니다. 준비가 안 되면 요청 초안과 코드 분석을 진행하고 실제 Codex 수행은 미확인으로 남깁니다.

관찰 가능한 작은 앱 목표

“투두 앱을 만들어 주세요”만으로는 언제 작업이 끝났는지 합의하기 어렵습니다. 사용자가 제목을 입력했을 때 목록에 어떤 값이 생기는지, 공백이면 무엇을 유지해야 하는지까지 적으면 파일과 실행 결과를 비교할 기준이 생깁니다.

예를 들어 “ 공부 ”를 추가하면 제목은 “공부”, completed는 false입니다. 같은 “공부”를 다시 추가해도 두 레코드가 생깁니다. 첫 항목을 지웠을 때 둘째 항목이 남는 것이 요구사항입니다. 이처럼 기대를 입력과 결과로 표현하면 Codex의 설명만 읽고 완료라고 판단하는 일을 줄일 수 있습니다.

오늘은 한 사용자가 브라우저 메모리에서 쓰는 앱입니다. 제목 수정은 81일, 검색·완료 필터와 DB 영속성은 82일의 계약으로 이어집니다. 지금 모든 기능을 넣기보다 오늘 관찰할 동작을 완성합니다.

제목·ID·완료 값 읽기

레코드는 한 할 일을 묶은 객체입니다. id는 숫자, title은 문자열, completed는 boolean입니다. 문자열 "true"는 boolean true와 다릅니다. 화면에 같은 제목이 보이더라도 id가 다르면 다른 할 일입니다.

T1은 이 세 값과 동작의 약속입니다. 앞뒤 공백만 제거하고 제목 가운데 공백이나 대소문자는 그대로 둡니다. 공백만 남으면 거부합니다. 78일 정적 input의 maxlength=100은 당시 화면 예시의 속성이며 T1 제목 제한으로 옮기지 않습니다.

80의 ID는 같은 저장소 인스턴스에서 증가합니다. 삭제해도 같은 ID를 재사용하지 않습니다. 새 저장소를 만들면 목록과 번호가 초기화됩니다. 다음 DB 단계의 ID와 메모리 생명주기를 혼동하지 않습니다.

Codex에 계획을 요청하기

먼저 현재 파일을 읽고 작은 계획을 설명해 달라고 요청합니다. 목표, 사용할 파일, 유지할 계약, 이번 변경 범위, 확인 방법을 함께 주면 계획을 검토할 근거가 생깁니다. 계획을 받았다고 실제 파일이 바뀐 것은 아닙니다.

제공 plan.txt는 아직 도구에 보낸 기록이 아닙니다. 학생은 자신의 작업 폴더와 목표에 맞춰 수정하고 실제 요청과 응답을 따로 남깁니다. 응답에 나온 파일 이름이 존재하는지, 오늘 필요하지 않은 저장소나 새 프레임워크가 포함됐는지 읽습니다.

프로젝트 지침은 반복해서 지켜야 할 작업 범위를 적는 곳입니다. 예시 지침에는 T1, 단일 사용자, 메모리 범위, 실제 실행/미실행을 나눠 보고하는 기준을 적었습니다. 도구가 지침을 읽었다는 말과 실제 변경이 지침을 지켰는지는 별도로 확인합니다.

코드 역할과 diff 읽기

todo-core.js는 데이터만 다룹니다. add는 검증한 제목을 레코드에 넣고, setCompleted는 완료 값을 설정하며, remove는 ID로 항목을 찾습니다. app.js는 입력 값과 클릭을 읽어 이 함수들을 호출하고 화면을 다시 그립니다. 상태 함수는 HTML 요소를 찾지 않습니다.

const는 이 이름에 다른 값을 다시 대입하지 않겠다는 선언입니다. 객체의 속성 값까지 바뀔 수 없다는 뜻은 아닙니다. 배열과 객체의 세부 문법은 제공 코드에서 필요한 부분을 읽습니다. value가 어디서 오는지, titleOf에서 실패하면 어디까지 실행되는지, items.push 뒤 무엇을 반환하는지 순서대로 읽습니다. 검증이 먼저이므로 빈 제목이 다음 ID를 소모하지 않습니다.

diff는 파일의 변경 전후를 비교한 자료입니다. +와 -의 개수는 품질 점수가 아닙니다. 실제 목적과 관련된 값·조건·함수가 바뀌었는지 확인해야 합니다. 본문의 발췌는 읽기용이며 실행할 때는 전체 파일을 사용합니다.

첫 추가 기능을 구현하도록 요청하기

첫 구현은 정적 화면에 제목 검증·메모리 추가·목록 표시를 연결하는 일입니다. Codex에 add/list 상태 함수와 submit 처리, 필요한 스크립트 연결을 한 작업 단위로 요청합니다. 정적 시작 화면의 비활성 버튼을 활성화했는지, 새 파일을 실제로 저장했는지도 확인합니다.

정상 제목에서 레코드를 만들고 공백에서 상태를 바꾸지 않는지 읽습니다. 오류 표시는 app.js의 errorText처럼 코드와 문구를 연결할 수 있습니다. 아래는 제공 전체 참조의 방식이며 실제 Codex 산출물로 표시하지 않습니다. 문구 한 곳의 후속 수정은 10~11절에서 검토합니다.

추가와 공백 오류를 관찰하기

공백 입력에서 store.add가 오류를 던지면 입력 초기화 줄로 진행하지 않습니다. act가 오류를 안내합니다. 이 순서를 읽고 정상 입력 뒤 목록·입력 상태, 공백 입력 뒤 목록·오류 상태를 직접 비교합니다. Node 검사와 실제 화면 관찰은 서로 다른 근거입니다.

완료·해제와 ID별 삭제

앞 단계에서 추가·공백 결과를 확인했다면 같은 작업 사본에 완료·삭제를 다음 변경으로 구현하도록 요청합니다. 파일이 바뀐 뒤 실제 diff와 아래 참조를 대조합니다. 체크박스가 바뀌면 현재 checked 값을 전달합니다. setCompleted(1, true)는 “1번을 완료로 설정”한다는 의미입니다. true를 두 번 전달해도 true입니다. “지금 값을 반대로 바꾸기”와 의미가 다릅니다. 후속 API에서도 명시적인 값 설정을 유지합니다.

삭제는 제목이 아니라 ID를 사용합니다. 같은 제목 두 개 중 하나를 지운 뒤 남은 ID를 확인합니다. 이미 없는 ID의 삭제는 NOT_FOUND이며 나머지 목록은 보존합니다. 이 경계는 Node 함수로 관찰할 수 있고, 화면에 없는 항목을 가리키는 버튼을 따로 만들 필요는 없습니다.

메모리 수명과 문자 표시

이 앱은 createStore의 배열에 할 일을 둡니다. 서버나 DB에 쓰지 않습니다. 실제 브라우저 새로고침 때 목록이 어떻게 되는지는 직접 관찰해야 하며, 현재 제공 Node 기록은 새 저장소를 만들었을 때 빈 목록인 것만 보여 줍니다.

제목에 <b>복습</b>처럼 보이는 문자가 들어갈 수 있습니다. 상태 함수는 그 문자열을 보존하고 app.js는 textContent로 표시합니다. Node 출력으로는 실제 브라우저에서 글자가 어떻게 보이는지 확인할 수 없습니다. 태그처럼 생긴 입력·긴 제목·키보드 이동은 직접 화면에서 남길 관찰입니다.

관찰 근거로 수정 요청 만들기

“삭제가 안 됩니다”만으로는 같은 문제를 다시 만들기 어렵습니다. 어떤 제목을 몇 개 넣었는지, 어느 ID를 지웠는지, 기대한 목록과 실제 목록은 무엇인지 적습니다. 근거를 모은 뒤 관련 파일과 수정 범위를 정합니다.

가상의 요청 작성 연습은 실제 장애 기록과 구분합니다. 예를 들어 같은 제목 두 개를 한꺼번에 지우는 코드가 보인다는 가정이라면 제목 비교 대신 ID 비교를 검토하라고 요청할 수 있습니다. 제공 참조 코드는 이미 ID별로 지우므로 그런 장애가 실제로 발생했다고 쓰지 않습니다.

실제 결함이 없다면 정상 관찰과 아직 확인하지 않은 항목을 남깁니다. 오류 메시지를 숨기거나 모든 코드를 다시 생성하는 요청보다, 관찰한 차이와 한 변경의 목적을 연결한 요청이 검토하기 쉽습니다.

설명용 변경안은 안내 문구 한 줄입니다. 실제 Codex 실행이나 적용된 패치가 아닙니다. 이 변경으로 titleOf의 빈 제목 거부가 달라져야 하는 것은 아닙니다. 실제 화면에서 안내가 바뀌었는지와 기존 추가·완료·삭제가 유지되는지를 따로 확인합니다.

회귀 확인은 이전에 정상인 동작이 수정 뒤에도 유지되는지 보는 일입니다. 제공 13개 상태 검사는 UI 문구를 읽지 않으므로 그 검사만으로 새 안내 문구가 화면에 보였다고 말할 수 없습니다. 변경 파일·Node 결과·브라우저 관찰·미확인을 나란히 남깁니다.

같은 T1을 81일에 인계하기

다음 장은 오늘의 id/title/completed와 동작 의미를 CRUD API로 옮깁니다. UI가 보낸 값과 서버가 검증할 값을 구분하고 제목 수정이 추가됩니다. DB 영속성은 82일에 이어집니다. 오늘 메모리 목록을 실제 DB에 저장했다고 설명하지 않습니다.

전달할 것은 현재 코드와 T1, 작은 계획과 변경 이유, 직접 관찰한 사례, 아직 실행하지 못한 범위입니다. 실제 Codex 응답이 없다면 제공 참조를 읽고 작성한 계획이라고 표시합니다. 동료가 같은 폴더와 사례로 이어갈 수 있는지 마지막으로 확인합니다.
