# 22장 벡터 거리와 Chroma·FAISS 검색

2026년 11월 24일 · [학생 교재](../site/chapter22/index.html) · [실습 노트북](../site/chapter22/chapter22.ipynb) · [재현 검사](../scripts/check_chapter22.py)

분관 안내 데스크의 토요일 마감 시각은 15:00이다. 검색기는 해당 문장의 위치를 어떻게 찾아줄까? 같은 2쪽에 있는 분실물 안내에도 ‘안내 데스크’가 등장한다. 학생은 이 두 청크를 같은 단어 순서로 벡터화해 두 저장소에 넣고, 첫 후보가 가리키는 원문을 확인한다. 기존 23장의 세 문서와 세 좌표는 그대로 사용한다.

## 원자료와 배정 시간

강의자용 `6-4_VectorStore/01-Chroma.ipynb`의 7·9·11·13·15번째 셀에는 메모리 컬렉션, 디스크 저장, 재열기, 일반 질의와 결과 두 건 조회가 나온다. `02-FAISS.ipynb`의 6·8·10·12·14번째 셀은 두 자료 모음을 입력으로 받아 인덱스를 생성하고 검색·저장·재로딩한다. 이번 장에서는 두 저장소에 같은 문서·벡터·질문을 주고 출처가 있는 답을 복원하는 데 집중한다. 단어의 유무를 인코딩하므로 별도의 임베딩 API 키는 필요하지 않다.

| 시간 | 수업에서 확인하는 값 |
|---|---|
| 1시간 | ‘대출·휴관·반납’ 좌표로 도서관 세 쪽과 휴관 질문 사이의 제곱 거리를 구한다. |
| 2시간 | 21장의 분관 안내 2쪽을 연다. 인계 JSON의 시작·끝 위치가 맞으면 해당 원문이 청크 본문과 같아야 한다. |
| 3시간 | Chroma에 두 청크의 ID·벡터·본문·출처를 저장한다. 같은 ID를 다시 쓴 뒤 건수를 확인하고 같은 폴더의 컬렉션을 다시 연다. |
| 2시간 | FAISS에 같은 벡터를 넣는다. 행 번호와 문서 ID의 연결을 일부러 뒤집어 본 뒤 바로잡고, 새 질문의 근거까지 확인한다. |

## 과제와 관찰값

| 노트북 과제 | 확인할 결과 |
|---|---|
| 02 · 휴관일 질문 | 1~3쪽까지 거리는 2, 0, 2다. 두 번째 문서가 가장 가깝다. |
| 07 · Chroma 등록 | 실습 컬렉션의 두 번째 ID에 시간표를 쓴다. 정상 설치 환경에서 확인할 건수는 2다. |
| 09 · FAISS 등록과 검색 | 분관 청크를 분실물·시간표 순서로 넣었을 때 토요일 질문은 위치 1, ID `branch-2:225`, 거리 0.0을 돌려준다. |
| 10 · ID 목록의 순서 복구 | 같은 위치를 뒤집힌 목록에서 찾으면 분실물 안내가 나온다. 원래 순서를 되살리면 2쪽 표에서 토요일 10:00~15:00을 읽을 수 있다. |
| 11 · 새 질문 | 습득물 문의에서 FAISS는 `branch-2:133`을 찾는다. Chroma가 설치된 커널에서는 같은 질의 벡터로 양쪽 첫 ID도 대조한다. |

주차 요금 질문은 세 좌표가 모두 0이고 두 후보까지의 제곱 거리는 각각 2다. 어느 후보에도 요금이 적혀 있지 않다. [웹 실험](../site/chapter22/index.html#evidence-lab)에서 후보를 누르면 같은 안내문 위에 그 범위를 표시한다. 이 화면은 브라우저에서 거리를 계산한다. 실제 저장소 호출은 노트북에서 한다.

## 검증과 수정

21장 풀이를 실행해 저장한 시간표를 22장으로 가져왔다. 기준 범위는 2쪽 `[225:279]`다. 독립 검수자가 분할 크기를 70에서 82로 바꾸자 범위가 `[225:300]`까지 늘어나 무인 반납함 행도 포함됐다. 처음 풀이처럼 청크의 마지막 행을 읽으면 ‘24시간’을 잘못 가져온다. 안내 데스크 행을 찾아 읽도록 수정한 후 두 범위 모두에서 토요일 15:00을 확인했다. 학생이 Chroma의 `upsert`와 FAISS의 `add`를 직접 작성하도록 과제를 보완했다.

macOS의 Python 3.12.15, NumPy 2.5.4, faiss-cpu 1.15.1에서 시작본과 풀이본을 각기 새 Jupyter 커널로 실행했다. 두 실행의 코드 셀 12개와 접힌 풀이 5개의 코드를 웹과 대조했다. 정상 범위를 바꾼 입력 외에 청크 ID·본문·쪽 등을 틀리게 넣은 사례도 검사했다. 검수용 스크립트의 `--require-chroma` 옵션은 실제 저장과 별도 프로세스 재열기를 필수로 확인한다.

Chrome에서 개정판 목차와 22장을 열고 1728·390·320픽셀 너비로 확인했다. 22장에서 21·23장으로 이동할 때 장 탐색과 인쇄 도구가 겹치는 문제를 고친 뒤, 본문을 스크롤한 상태에서도 마우스로 두 장을 오갈 수 있었다. 좁은 화면에서 원문 표시와 과제 풀이를 확인했고, 브라우저에서 받은 노트북은 두 GIF가 포함된 배포 파일과 바이트가 일치했다.

거리와 질의 형식의 근거는 [Chroma 인덱스 설정](https://docs.trychroma.com/docs/collections/configure), [Chroma Query와 Get](https://docs.trychroma.com/docs/querying-collections/query-and-get), [FAISS 거리 기준](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances)에 있다.

## 확인 필요 항목

검수용 Mac에는 Chroma가 설치되어 있지 않고 패키지 서버에 연결되지 않았다. 이 환경에서 확인한 출력은 미설치 분기다. 실제 Chroma 적재·재열기·검색과 두 저장소 결과의 일치는 보류 판정이다. 수강생 Windows·WSL에서의 설치와 8시간 수업의 실제 소요 시간도 남아 있다.
