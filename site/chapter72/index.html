Docker Compose 네트워크와 볼륨

02

서비스 이름과 내부 포트

Compose는 여러 서비스를 하나의 설정에 적습니다. 서비스 사이의 주소, 외부에서 접속할 포트, 데이터를 보관할 볼륨은 서로 다른 설정입니다.

호스트 컴퓨터에서 보는 127.0.0.1과 API 컨테이너 안에서 보는 127.0.0.1은 각자의 네트워크 공간입니다. Compose의 공통 네트워크에서는 API가 db라는 서비스 이름과 DB의 컨테이너 포트 5432로 접속합니다.

03

볼륨과 컨테이너 교체

선언된 볼륨은 DB의 데이터 디렉터리에 연결됩니다. 같은 컴퓨터·프로젝트의 같은 볼륨을 다시 연결해야 기존 자료를 읽을 수 있습니다. 다른 호스트에 같은 이름만 만들어도 이전 데이터가 생기는 것은 아닙니다.

셀 03 · Compose 구성 검증

Docker Compose가 설치된 커널에서는 실제 config 명령이 선언을 해석합니다. 이미지를 받거나 컨테이너를 띄우지 않습니다.

실행 결과

/var/lib/postgresql/data

CLI가 구성 해석에 성공하면 /var/lib/postgresql/data가 보입니다. 이 경로가 컨테이너 안에서 볼륨을 연결할 위치입니다. 실제로 재시작한 뒤 같은 문서가 남았는지는 데이터베이스에서 다시 조회해야 합니다.

04

연결을 다시 열어 저장 데이터 검증

볼륨 위에 DB가 유지된다는 말은 새 연결에서 원래 행을 다시 읽을 수 있다는 뜻입니다. 아래는 임시 파일 하나에 실제 SQLite DB를 만들고 연결을 닫았다가 다시 여는 연습입니다. Docker 컨테이너와 PostgreSQL의 재시작은 이 코드에서 일어나지 않습니다.

셀 04 · DB 재연결과 영속성 확인

행 수만 비교하면 내용이 달라져도 알아채기 어렵습니다. 같은 소유자·문서 ID로 원문을 읽고 대조하세요.

셀 03은 Compose 설정에서 연결 대상을 읽습니다. 셀 04가 다시 여는 대상은 SQLite 파일입니다. 실제 볼륨 보존을 확인하려면 같은 볼륨을 연결한 DB 컨테이너를 다시 띄우고 이전 행을 조회해야 합니다.

실행 결과

과제함에 제출합니다. True

과제함 문장과 True가 함께 나옵니다. 실제 Compose 환경에서는 재시작 전후 같은 요청을 보내 이 세 값, 즉 소유자·문서 ID·원문을 비교합니다. 이전 DB 볼륨이 연결되지 않았다면 이 조회에서 원래 행을 찾을 수 없습니다. 볼륨을 확인할 때는 수업용 Compose 환경에서 한 행의 ID를 기록한 뒤 같은 볼륨을 연결해 DB 서비스를 재시작하세요. 그 ID로 다시 조회한 값을 SQLite 실습 결과와 따로 적으세요.

05

복습과 실습 점검

실제 수업 환경에서 보존을 확인할 때는 과제 안내 한 건을 저장하고 문서 ID와 원문을 적어 두세요. API와 DB를 재시작한 뒤 같은 소유자·같은 ID로 조회한 원문까지 일치해야 합니다.

06

Docker Compose 네트워크와 볼륨 심화 읽기

API 이미지와 기존 DB

오늘의 목표는 새 DB에서 비슷한 답을 만드는 것이 아니라, 이전에 사용한 B1 데이터와 같은 API를 연결하고 보존 여부를 확인하는 것입니다. course_users, course_documents, course_conversations, course_turns는 사용자·문서·대화·질문 이력을 연결합니다. 60일의 명시 기억과 70일의 문서 상태·A1 확장은 이 관계에 단계적으로 추가됩니다.

첫 15분에는 53일 query-results.sql, 54일 repository-tests.md, 70일 document-db-tests.json, 71일 runbook을 엽니다. 기존 owner와 문서·대화 ID, migration 목록, Docker context, 실제 volume 이름을 찾습니다. 자신의 관측이 없으면 구조와 제공 코드만 읽고 실제 ID·행 수 칸은 비워 둡니다.

볼륨 이름과 프로젝트 범위

Compose는 여러 서비스를 하나의 프로젝트로 관리합니다. 제공 compose.yaml의 name은 course-b1이며 db 서비스가 course-data 볼륨 키를 사용합니다. 이 파일은 53·54일에서 사용한 B1 구성과 같은 바이트입니다. API만 별도 compose.api.yaml에 추가합니다.

하지만 YAML 이름이 같다는 것만으로 이전 데이터를 사용한다고 확정할 수 없습니다. Docker context가 다른 엔진을 가리키거나 -p/COMPOSE_PROJECT_NAME으로 프로젝트가 바뀌면 다른 실제 볼륨을 사용할 수 있습니다. 기존 실행 기록과 프로젝트 label, 컨테이너 mount의 실제 volume 이름을 대조한 뒤 진행합니다.

호스트가 달라지면 같은 이름의 명명 볼륨도 같은 저장 장치가 아닙니다. course-data라는 문자열을 복사한 것은 백업 복구가 아닙니다. 기존 volume이 보이지 않을 때 새 DB 초기화로 성공처럼 채우지 말고 연결 대상과 필요한 이관 절차를 먼저 확인하세요.

서비스 이름을 이용한 접속

같은 Compose 네트워크에서는 서비스 이름으로 서로를 찾습니다. API 컨테이너는 db:5432에 접속합니다. 호스트에서 실행하는 Python은 로컬 공개 포트인 127.0.0.1:55432를 사용합니다. 주소가 다른 것은 DB가 두 개이기 때문이 아니라 접속 출발점이 다르기 때문입니다.

API 컨테이너의 127.0.0.1은 API 자신입니다. 이 주소로 PostgreSQL을 찾으면 DB 서비스에 도달하지 못합니다. 반대로 호스트에서 db라는 Compose 내부 이름을 무조건 해석할 수 있다고 가정하지 않습니다. 고정 IP를 적어두기보다 같은 네트워크의 서비스 이름을 사용합니다.

DB 이미지의 POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD는 DB 컨테이너를 초기 준비할 때 쓰는 설정입니다. PGHOST, PGPORT, PGDATABASE, PGUSER, PGPASSWORD는 Python 클라이언트가 어디에 어떻게 접속할지 읽는 값입니다. 변수 이름이 비슷해도 읽는 프로세스와 시점이 다릅니다.

기존 DB 볼륨을 사용하면서 환경 파일의 POSTGRES_PASSWORD만 바꿨다고 기존 계정의 비밀번호가 변경되지는 않습니다. 이 장은 비밀번호 변경 절차를 구현하지 않습니다. 기존 B1의 실제 비밀번호를 신뢰된 수업 환경에서 주입하고 코드·Dockerfile·학생 관측 파일에는 남기지 않습니다.

image에는 71일에 직접 확인한 image ID 또는 저장소 digest를 둡니다. pull_policy: never는 현재 엔진에 준비한 이미지를 사용하도록 정한 수업 구성입니다. 이미지가 없으면 실패를 기록하고 준비 단계를 해결합니다. 임의로 latest를 받아 같은 앱이라고 가정하지 않습니다.

DB 관계와 출처 필드

문서는 owner에 속하고 대화도 owner에 속합니다. 질문 이력은 그 대화와 owner의 조합으로 저장됩니다. 70일 course_turn_results는 turn_id만 따로 저장하지 않고 owner·conversation_id와 함께 기존 turn을 가리킵니다. 다른 사람의 문서와 자신의 대화를 임의로 묶는 요청은 정상 입력이 아닙니다.

A1은 답변 문자열 하나가 아니라 status, answer, sources, generation_calls를 가진 결과입니다. 출처 객체의 id/text/source/page를 원문·청크 매핑과 함께 보존해야 같은 답을 재검토할 수 있습니다. 기존 텍스트 이력에는 과거에 없던 A1 상태를 만들어 넣지 않고 legacy_text_no_a1/result=null로 구분합니다.

70일 문서 검색은 소유한 ready TXT 문서의 매핑 후보 안에서 토큰 포함 여부를 확인하는 로컬 어댑터입니다. pgvector 이미지가 DB에 포함되어 있다는 사실만으로 이 검색이 벡터 검색으로 바뀌지는 않습니다. 실제 벡터 검색 비교는 다음 장의 별도 준비와 검증입니다.

처음 B1을 만든 53일 setup은 기본 테이블·가상 데이터를 준비하고 course_schema_migrations에 적용 파일 이름을 남깁니다. 이후 apply_schema.py는 같은 이력을 읽어 필요한 단계만 순서대로 적용합니다. 70일의 apply_a1_schema.py는 그 적용기를 먼저 호출한 다음 A1 확장을 한 번 추가합니다.

순서는 053_core → 053_seed → 060_memory → 070_document_status → 070_a1_results입니다. 54일까지 적용한 DB라면 뒤의 세 단계가 남습니다. 이것은 정적 적용 계획이며 실제 DB commit 성공 증거가 아닙니다. API를 시작할 때마다 별도 schema.sql로 새 테이블을 초기화하지 않습니다.

Compose의 API 이미지 지정

71일 integration Dockerfile과 70일 application 사본을 그대로 제공합니다. 새 API를 다시 작성하지 않고 image 선택만 Compose의 api 서비스에 연결합니다. 이 장의 INPUT_MANIFEST.json은 원본 70 앱과 B1 구성 사본을 대조합니다. source manifest가 달라졌다면 먼저 인계 버전을 확인합니다.

앱 코드는 같은 파일이어도 실행 환경이 다르면 결과가 달라질 수 있습니다. Python/플랫폼·설치 의존성·설정·기존 DB 상태를 함께 기록하세요. 제공 이미지 태그를 실행 증거로 복사하지 말고 실제 image ID를 입력합니다. API 컨테이너에는 application 전체가 들어가며 강사 답안은 포함되지 않습니다.

DB 준비와 API 시작 순서

Compose 파일을 파싱한 것과 Docker가 구성 해석에 성공한 것, 컨테이너가 시작한 것, 실제 업무 요청이 성공한 것은 네 가지 다른 확인입니다. 준비된 환경에서만 다음 순서로 진행하며 각 단계가 실패하면 이후 성공 칸을 채우지 않습니다.

depends_on의 service_healthy는 db의 healthcheck가 통과한 뒤 API를 시작하도록 준비한 조건입니다. pg_isready는 접속 준비를 확인하는 신호이며 테이블·owner·매핑·정답 품질까지 검사하지 않습니다. 따라서 단계 DDL을 별도로 적용하고 같은 질문 회귀가 필요합니다.

기존 70일에서 이미 A1 확장이 적용된 DB도 같은 적용 이력으로 건너뛰는지 확인합니다. 수업 데이터가 사라졌다면 새 행을 만들어 덮지 않고 context·볼륨·DB·migration을 먼저 대조합니다. 비밀번호나 접속 URI 전체를 로그에 출력하지 않습니다.

재구성 전후의 검증값

영속성은 시간이 지난 뒤에도 같은 기록을 읽을 수 있는지를 보는 활동입니다. 비교 전에는 context·project·실제 volume·DB·owner·document_id·conversation_id와 기존 turn ID, 전체 A1, 적용 이력을 적습니다. 재시작 후 같은 대상을 다시 조회해야 합니다.

compare_identity는 이런 기록의 식별자가 같은지 비교하는 학습 보조 함수입니다. 빈 값이면 missing_evidence, 다른 식별자가 있으면 identity_mismatch, 같으면 identity_matches_content_still_unverified를 반환합니다. 마지막 값도 내용 보존 PASS가 아닙니다. 실제 이력·출처·행 수를 추가로 대조해야 합니다.

동시에 새 요청을 보내면 행 수가 증가할 수 있으므로 비교하는 짧은 구간에는 학생 본인의 쓰기 요청을 멈추고 동료의 작업 조건도 기록합니다. 행 수만 같은데 owner나 내용이 바뀌는 경우를 놓치지 않도록 구체적인 ID와 값을 함께 봅니다.

재시작과 재생성의 차이

API restart는 기존 컨테이너의 프로세스를 다시 실행합니다. DB에 저장된 기록이 계속 읽히는지 확인하는 한 단계이지만 새 이미지나 변경한 환경 설정을 반영한 결과는 아닙니다. 같은 질문을 새로 저장해서 결과를 만드는 대신, 기존 conversation_id의 이력을 재조회하세요.

API 컨테이너 재생성은 새 컨테이너를 만들되 같은 image·설정·DB를 사용하도록 정한 별도 실험입니다. 다음에는 DB 재시작을 별도 단계로 관찰합니다. 한 번에 여러 조건을 바꾸면 어느 변화가 원인이었는지 설명하기 어렵습니다.

같은 볼륨 재연결은 실제 mount가 유지됐는지 확인해야 합니다. 그 볼륨이 살아 있는 동안 데이터가 읽혔다는 관찰을 호스트 장애 뒤 복구나 백업 파일 검증으로 확대하지 않습니다. 제공 기록에는 이 실제 실험을 수행한 값이 없습니다.

저장 실패와 백업 복구

답변 생성 완료와 저장 완료는 다릅니다. 70일 H1은 저장 실패 때 완료된 A1을 보존하고 persistence를 따로 실패로 표시할 수 있습니다. commit 직후 연결이 끊기면 효과를 확정하지 못할 수 있으므로 자동 재시도로 같은 turn을 중복 생성하지 않습니다. 실제 실패·재조회 근거를 남긴 뒤 대응을 정합니다.

백업은 원래 볼륨과 별도의 복구 가능한 자료를 만드는 일이고, 복구 검증은 별도 대상에 되돌린 뒤 owner·ID·행 수·출처 관계를 확인하는 일입니다. API restart나 같은 volume 재조회만으로 이 두 과정을 완료한 것은 아닙니다. 이 장의 실행에는 실제 백업·복구가 포함되지 않았습니다.

다른 프로젝트의 스키마나 비-B1 데이터가 보이면 자동 삭제·초기화하지 않습니다. 먼저 데이터 목록·owner·대화 매핑·백업 위치·복사 후 대조·전환 조건을 별도 계획으로 남깁니다. 기존 볼륨을 삭제하는 명령은 수업의 오류 해결책이 아닙니다.

검색용 DB·볼륨 인계

73일에는 같은 문서·원문·청크·owner·source 매핑을 이어서 검색 비교를 준비합니다. DB 이미지에 pgvector가 있다는 사실과 실제 벡터 어댑터가 검증됐다는 사실을 구분하세요. 지금은 고정 70 앱의 토큰 포함 검색을 새 검색 성능으로 포장하지 않습니다.

인계에는 70 manifest SHA, 71 이미지 식별자와 플랫폼, course-b1·실제 volume·접속 위치, 단계 적용 이력, 같은 질문·전체 A1·저장 실패·전후 ID 기록이 필요합니다. 수행하지 못한 항목은 null/HOLD로 남깁니다. 후속 담당자가 없는 실측을 있다고 추정하지 않게 하는 것도 재현 문서의 일부입니다.
