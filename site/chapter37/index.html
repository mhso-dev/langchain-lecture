관련 개념 더 읽기

비교할 두 실행에서 무엇을 고정할까요?

한 번에 size와 overlap을 모두 바꾸고 결과가 달라졌다면 어느 변경이 원인인지 구분하기 어렵습니다. 먼저 변경할 변수 하나를 정하고 나머지 설정과 입력을 유지합니다. 다음 변경은 바로 앞 설정을 기준으로 삼습니다.

청크 크기를 바꾸면 청크 본문과 벡터가 함께 달라집니다. 이는 바꾼 크기에 따라 다시 계산해야 하는 산출물입니다. 벡터 모델까지 바꾸는 것과는 다릅니다. 여기서는 동일 키워드 표현·차원·거리로 새 청크의 벡터를 다시 계산합니다.

두 조각에 같은 문장이 왜 남을까요?

중첩은 앞 청크의 끝부분을 다음 청크에도 넣는 것입니다. size=8/overlap=4이면 시작 위치는 4문자씩 이동합니다. 경계에 걸린 내용을 함께 남길 수 있지만 같은 문자가 여러 청크에 반복됩니다.

중첩을 늘려도 모든 질문의 필요한 정보가 한 청크에 모이는 것은 아닙니다. 이번 휴관 질문은 B의 첫 검색 본문이 “에 휴관합니다.”이고 C에서는 “ 월요일에 휴관”입니다. 요일이 검색 결과에 들어오는 변화가 있지만, 이것만으로 실제 의미 검색 성능이나 모든 문장의 완전성을 증명하지 않습니다.

36장의 평가 기록에서 필요한 근거가 검색됐는지와 답변 내용이 충분한지를 나누어 보았습니다. 오늘은 같은 원문과 개발 질문을 유지하고 청크 크기, 중첩, 검색 개수 k를 차례로 바꿉니다. 결과가 좋아지지 않거나 지표가 같게 나오는 것도 관측으로 남깁니다. 미리 원하는 결론을 정하지 않습니다.

원문·위치표·기준선 이어받기

21장에서는 청크의 문자 위치를 원문으로 연결했고, 22장에서는 문서와 벡터의 조건을 맞췄습니다. 36장의 baseline.csv는 질문별 검색·답변 기록을 제공합니다. 이 입력들은 실험에서 바꾸지 않을 조건을 정하는 출발점입니다.

36장의 기본 인덱스는 짧은 원문당 전체 청크 1개였습니다. 이번에는 16문자/중첩 0/k 1로 새 실험 기준을 만듭니다. 36장 결과와 37장 결과를 바로 빼서 한 변수의 효과라고 해석하지 않습니다. 이 장에서 지정한 세 인접 비교 쌍끼리만 변경 변수를 확인합니다.

크기가 문장 경계를 바꾸는 모습

size는 Python 문자열에서 한 청크에 넣는 최대 문자 수입니다. 토큰 수가 아닙니다. size=16을 8로 줄이면 원문 하나가 더 많은 조각으로 나뉩니다. 숫자·조건·주어가 서로 떨어질 수 있으므로 청크 개수만 비교하지 말고 실제 문자열을 읽습니다.

대출 원문은 “도서 대출 기간은 14일입니다.”라는 규칙입니다. 제공 코드가 만든 8문자 첫 청크는 “도서 대출 기간”이고 숫자 14가 없습니다. 원문 ID는 맞게 찾더라도 답변에 필요한 부분이 검색 결과에서 빠질 수 있습니다.

k는 반환받을 최대 청크 수입니다. C→D에서는 청크·위치표·벡터·E1이 모두 같고 요청 개수만 1에서 2로 바뀝니다. 결과가 늘어도 같은 원문의 중복 청크일 수 있어 원문 recall이 더 커지지 않을 수 있습니다.

dev-01의 D에서는 첫 청크 “도서 대출 기간”과 두 번째 “출 기간은 14”라는 조각을 받습니다. 숫자는 더 보이지만 단위와 전체 조건까지 충분한지는 사람이 읽어야 합니다.

고정 생성기는 첫 검색 문장만 반환합니다. k를 늘려 추가 문서를 받아도 이 생성기의 답변이 자동으로 두 문서를 종합하지 않습니다. 이것을 실제 LLM의 동작이나 성능이라고 해석하지 않습니다.

size나 overlap이 바뀌면 이전 청크의 벡터를 그대로 사용할 수 없습니다. 같은 모델이라도 입력 본문이 달라졌기 때문입니다. build_index는 각 실험 폴더에 documents, source-map, chunk-policy, vectors, embedding을 함께 만듭니다. 입력 원문 자체가 바뀌면 새 원문 버전이 필요하다는 오류를 냅니다.

E1에는 provider/model/dimension/normalization/distance와 원문·청크·정책 해시가 남습니다. 이번 표현은 course-local/keyword-presence-v1의 3차원 벡터이고 거리는 squared_l2입니다. 실제 의미 임베딩으로 교체하는 실습은 이 비교에 포함하지 않습니다.

make_search는 파일 해시와 E1을 검사하고, 청크 ID 순서와 저장 벡터가 입력 청크에 대응하는지 확인합니다. 질문 벡터와 저장 벡터의 제곱 L2 거리로 정렬하며 동점이면 청크 ID로 순서를 정합니다. 그래서 입력이 같을 때 로컬 결과를 다시 읽기 쉽습니다.

알려진 키워드가 없는 질문은 교육용 규칙으로 빈 결과를 반환합니다. 이 규칙을 실제 의미 임베딩에서 영벡터가 뜻하는 일반 규칙으로 사용하지 않습니다. 주차 질문의 NA는 기대 근거가 없는 질문이라는 의미이며 실제 운영 장애와 구분합니다.

네 설정을 실행하고 같은 질문끼리 비교

CSV의 12행은 4설정×개발 3질문입니다. 공개 확인 2문항은 기본 설정 비교에 넣지 않았습니다. 각 설정의 JSON에는 그 설정의 질문 수 3, 답변 가능 2, 불가 1과 실패 수가 함께 기록됩니다.

이번 고정 자료에서 개발의 답변 가능 두 문항은 네 설정 모두 원문 recall 1입니다. 이는 설정들이 실제 검색에서 동등하거나 모두 최적이라는 결론이 아닙니다. 앞에서 본 것처럼 검색 본문은 달라지며, 원문 기준 지표만으로 문맥 부족을 놓칠 수 있습니다.

한 지표가 그대로라고 아무 변화도 없었다고 말할 수는 없습니다. 이 예제의 원문 recall은 “어느 원문에서 왔는가”를 보기 때문에, 그 원문의 일부만 가져와도 기대 원문을 찾았다고 셉니다. 필요한 답의 조건을 모두 포함하는지는 별도의 내용 검토가 필요합니다.

실험 보고는 관측과 해석을 나누어 씁니다. “B에서는 dev-01의 첫 검색 본문에 14가 없었다”는 관측입니다. “짧은 경계가 답변 문맥을 나누었을 수 있다”는 해석입니다. “size 8은 항상 나쁘다”는 현재 세 원문과 개발 질문만으로 뒷받침할 수 없는 일반화입니다.

실패가 있으면 실패한 행도 남깁니다. 검색이 미관측인 답변 가능 문항이 있으면 전체 평균은 보류하고 관측 평균의 분모를 적습니다. 실패한 실행을 제외한 뒤 설정을 더 좋다고 선택하지 않습니다.

38장에서는 같은 개발 질문과 기준선을 사용해 추가 기법을 비교합니다. consumer-contract.json은 정식 인계 9파일의 해시와 필드, NA·분모 규칙을 정리합니다. 이 파일을 확인하고 baseline의 상세 JSON과 실험별 result.json도 같이 읽어야 검색 문서와 A1 출처를 추적할 수 있습니다.

개발 문항을 보며 설정을 고른 뒤 공개 확인 문항을 읽을 수 있지만, 이미 공개된 문항이므로 블라인드 평가가 아닙니다. 확인 결과를 보고 다시 고쳤다면 그 사실을 개발 기록에 남기고 새 확인 문항을 준비합니다.
